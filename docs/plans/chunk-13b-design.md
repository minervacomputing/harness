# Chunk 13b design: delete the old paths

Status is proposed, as of 2026-10-16. It settles the choices that chunk 13b of [remaining-chunks.md](remaining-chunks.md) leaves open, so that each unit below can be done by one fresh agent and checked before the next. Line numbers are at `a5cbd05`. It follows [chunk-13a-design.md](chunk-13a-design.md): its rule for a case (a case is ported when the internal path has the behaviour, deleted only when its world needs the Workspace, and the commit names each deleted case) holds here too.

## Decisions

**Every check runs each tsconfig project alone.** `pnpm typecheck` chains `tsc -p` with `&&` (`cloudflare/package.json`), so a deletion check runs `tsc -p tsconfig.json`, `tsc -p tsconfig.node.json` and, while it exists, `tsc -p files-worker/tsconfig.json`, each on its own, and fixes every error. A trial deletion of the whole inventory at `a5cbd05` gave 96 Worker and 15 Node errors. Each is assigned to a unit below. A file reached only at run time (a vitest config, a package script, a workflow step) is found with `grep -rn`, not tsc.

**The retired classes stay exported until 13c.** 13c replaces `Workspace` and `FaultMailbox` with deleted-class tombstones. Until then a deploy that dropped an export would change the namespaces, and `scripts/reset.ts` stops on a namespace whose class the build does not export. So `src/retired.ts` (new) holds `class Workspace extends DurableObject { alarm() {} }`, exported by `src/index.ts` and `src/faults/index.ts`, and `src/faults/index.ts` exports an empty `FaultMailbox` beside it. The no-op `alarm()` ends a Workspace object's pending outbox, refresh or purge alarm quietly. Their bindings go (`WORKSPACE`, `FAULT_MAILBOX`, `cloudflare.config.ts:192`, `:199`); their `exports` entries stay (`:251`, `:255`).

**`/api/*` answers 404 to anyone without a token.** The router keeps Hono, the internal mount, the run stream and `/api/probe`, which already answers 404 without its token (`src/http/probe.ts:24`). `/api/health` goes (no kept caller: only the verify skill and the suites that test it). The faults build's `/api/faults/*` stays where it is and answers 404 without its token. The security headers move from the three prefixes to `*` (`src/http/router.ts:50`), so a 404 for `/` carries them too. With the `assets` config gone (`cloudflare.config.ts:175`), `GET /` reaches the Worker and is `NOT_FOUND`.

**The Conversation keeps its tables and columns.** `src/lib/sqlite.ts:1` requires steps that the previous version can run beside: a busy object keeps the old code, and a rollback runs it on storage the new code touched. The old code inserts into `messages` on every completed run (`conversation.ts:1186`), so a `DROP TABLE` step would fail its runs. No schema step is added. `messages`, `starts`, `releases`, `start_keys`, and the `activated` and `released` columns stay in `src/conversation/schema.ts` with a comment saying they are unused since 13b. The new code still writes `activated = 1`, so the old code's gate (`conversation.ts:973`) reads a new run as activated. Chunk 15a may drop them once no rollback can reach 13a.

**The messages table loses its last reader.** On the internal path, `#complete` writes the answer to `messages` (`conversation.ts:1186`) and `#finishedFact` reads it back for `run.finished`'s `message` (`store.ts:971`). Instead, `#complete` passes `{ id, content }` to `finish`, which hands it to `#finishedFact`. Only `#complete` ever wrote an assistant message, so the fact is unchanged. The history comes only from `startRun`. `internal/start.ts:126` already applies Decision 7's selection, clipping and file notes (`historyOf`, `recentHistory`, `withFiles` in `history.ts`) to `command.history`. `RunSnapshot.turn` becomes required (`store.ts:72`). `history.ts` loses `promptOf` and `HISTORY_LIMIT`, which read the object's own messages. `clip`, `notePaths`, `withFiles`, `historyOf`, `recentHistory`, `sessionInstructions` and the `StoredMessage` shape stay, since `internal/start.ts:77` maps the command's history into it.

**Activation commits with the run.** A Laravel start activates with no I/O (`laravel-runs.ts:19`), so the final write of `#startOnce` (`conversation.ts:664` to `:699`) inserts the run, appends `queued`, then applies `store.activate` (status `provisioning`, `activated = 1`, its event) in the same write, and defers `#startLoop` in place of `#activate` (`:701`). The events and facts Laravel sees do not change. `#activate`, `#activations`, `#recover`'s `!run.activated` branch (`:923`), the watch's activation retry (`:1063` to `:1066`), `store.activate`'s not-queued branch (`store.ts:622`), `GateRun.activated` (`gate.ts:33`, `:55`) and the `activated` checks at `conversation.ts:880`, `:973`, `:1020` go. A crash after the write and before the loop is the watch's existing case, an acting run pi has no submission for, which it submits (`:1074`). A run the previous version stored but never activated stays `queued` until its deadline; it needs a crash within that version's deferred activation, so none is expected.

**One credential path.** `#credentials` (`conversation.ts:1542`) returns `laravelCredentials` only. The sealed lease, `CredentialLease`'s union and the port's `open` go (`gateway/executor.ts:171`, `:189`), and the executor reads `HeldLease.payload`. The key ring and `lib/encryption.ts` go with `MINERVA_ENCRYPTION_KEYS`.

**A conversation the Workspace made is inert.** Rows with no organization exist on staging and the test instances. `#portsContext()` answers null for one, as for no conversation, and `PortsContext.organization` becomes `string`. `#recover` ends such a conversation's active run as `cancelled` in one write. `store.bind` already refuses every Laravel command for it (`store.ts:417`). A leftover `release` job meets the Agents SDK's default, which logs and drops an unknown job (`agents` `_onHostJob`).

**The byte counter stays for 14d.** `FOLDER_PORTS.counter` and the Workspace choice go (`files/folder.ts:24`, `:33`). `ByteCounter` and `UNCOUNTED` stay, since 14d replaces `UNCOUNTED` with a real counter.

**Dead connector code.** `tokenRequest`, `planRefresh` and the rest of `workspace/credentials.ts`, and `consentNeeded`, `requestedScopes` and `kindsOut` in `workspace/out.ts`, go with `src/workspace/`. Nothing under `src/connectors/` holds token-request code (one comment, `connectors/hubspot/connector.ts:13`). The internal catalog (`internal/catalog.ts`) already serves Laravel what consent needs: `scopes`, `tokenBody`, `clientAuth`, and each operation's `consent`. The connector suites keep every case that runs tools, discovery, describe, records or validation. Cases about token requests, refreshes and consent go, since Laravel lends the token and refreshes it (`app/tests/Feature/Connections/ParityTest.php` carries the refresh parity). An assertion that describes the catalog Laravel reads, such as `connectors-web.test.ts:119`'s kinds, is ported to `catalogOf`. In `connectors-stripe.test.ts`, the `saveKey` cases through `WorkspaceCore` (`:634` to `:716`) go and its tool cases stay. In `connectors-web.test.ts`, the cases on `harness` and `accessOf` go unless `internal/connections.ts` (`checkGrantEdit`, `listResources`) has the behaviour they assert. Then they are ported there.

**Client pairs.** No kept path reads a `MINERVA_<APP>_CLIENT_ID` or `_SECRET`. The only readers are `workspace/env.ts` (`oauthClients`) and the faults build's fake clients (`faults/ports.ts:198`). The engine leases tokens from Laravel and never refreshes. So `connectorSecrets` (`cloudflare.config.ts:93`), `connectorClientSecrets`, `clientSecretNames` and `OAUTH_APPS` (`src/config.ts:163` to `:189`) go. `MINERVA_GITHUB_APP_SLUG` stays, since the catalog's `manage` link reads it (`connectors/github/connector.ts:562`).

**Origins are derived.** No setting names an origin once `MINERVA_SITE_URL` and `MINERVA_DOWNLOAD_ORIGIN` go. The build's origin check (`cloudflare.config.ts:117`) and the deploy's (`scripts/deploy.ts:193` to `:205`, app only) go. The suites' origin becomes `https://<app>.<accountSubdomain()>.workers.dev` (`test/account/client.ts:36`, after `pinSuite`). `scripts/origins.ts` keeps `instanceOrigin`, `subdomainOf` and `labOrigin`. Old `vars.env` lines stay harmless: `buildSettings` reads only the names it knows (`scripts/build-settings.ts:63`). CI's masks keep reading the origins from `MINERVA_CI_VARS_ENV` (`scripts/masks.ts:30`), which 13b does not change.

**Secrets are uploaded as the build declares them.** The app's upload goes through `secrets.ts subset`, the download Worker's mechanism (`scripts/deploy.ts:243`). It takes the names the app's build declares as `secret` bindings (`readBuild`, as `scripts/builds.ts:114` reads them) and writes them to an owner-only temporary file. A retired line left in an instance's `secrets.env` is then never uploaded. A name that `cf` might refuse never reaches it either. `secrets.ts` generates and requires `MINERVA_SECRET_KEY` alone.

**What stays for later chunks.** `r2-lifecycle.json`'s `static/` rule stays: a reset refuses a bucket whose rules differ from the file's, and every bucket has it. `names.download` stays in `scripts/instance.ts` for 13c's deletion of the download Workers. `design/` stays: `design/logo/export.py` writes into `frontend/`, and where the logo's sources live is open question 2. `dev:offline` stays without `.assets/`. Its internal API is on when the shell sets the four internal settings, as any setting is (`build-settings.ts:63`). The docs (README.md, AGENTS.md, ARCHITECTURE.md, cloudflare/README.md, docs/connectors.md) are 13c's. Until then AGENTS.md's frontend steps are stale, so implementing agents skip `pnpm check` in `frontend/` from unit 1 on.

## Risks

- A deploy of 13b leaves `Workspace` and `FaultMailbox` objects with data until 13c. The no-op `alarm()` stops their alarms from retrying.
- A rollback to 13a's code works on Conversation objects (tables and columns kept, `activated` written) but brings back an API whose Workspace data is still there. Roll back only to undo a failed 13b deploy, before 13c.
- An organization-less conversation's active run ends `cancelled` on its next wake. That is acceptable on staging and the test instances; production has no users and 13c resets it.
- `test:deployed`'s cases change by design. The regression box compares `test:faults` case for case and `test:deployed` against the list above.
- Deleting suites can drop kept coverage silently. Every deleted case is named in its unit's commit with its cover or the reason it has none, as 13a did.

## Amendments after opencode's review

opencode (`plan` agent) reviewed this design against `a5cbd05`. Each finding below was checked in the code, and all eight hold. These amendments win over the body.

1. **A legacy conversation ends in the gate, not in `#recover`.** `#recover` runs after the factory has opened and resumed pi (`conversation.ts:1035`), and the gate and the model's upstream cast `#portsContext()` to non-null (`:944`, `:979`). So `#portsContext()` and `PortsContext.organization` stay as they are. `#gate` (`:971`) first checks the conversation: one with no organization has its active run finished `cancelled` in the gate's write, as the gate's `timed_out` end is, before pi opens. `#stopEnded` (`:1002`) then aborts that run's pi tasks and queued submissions, since its session is no longer active. The new platform case restarts such an object with pi work pending and checks the run is `cancelled` and no model call or tool ran after the restart.
