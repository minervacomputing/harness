# Browser reads design: pages that need scripts, rendered in Cloudflare's browser

Status: proposed, 2026-10-25. Not built, and nothing deployed. Line numbers are at `61a9b15` (harness) and at `b0df0eb` of `minervacomputing/app` ("the app's" below). Browser Run's behaviour comes from Cloudflare's docs, read 2026-10-25 (each cited with the date its page was last updated), and from the runtime types the build generates (`cloudflare/.cloudflare/types/index.d.ts`, "the types" below, workerd 1.20261006.1). A claim about code with no label was read at the lines cited; one marked (inferred) follows from code or docs that were read, and one marked (guess) rests on platform behaviour no document states. Once built, what stays true moves into ARCHITECTURE.md, docs/connectors.md, docs/data-processing.md and cloudflare/README.md, and this file is deleted.

Review: opencode and two adversarial reviewers, one for security and one for operations, reviewed the draft on 2026-10-25. The first security reviewer's findings were never delivered, so a second security pass ran the same day, and both of its reviewers delivered: opencode's security pass and an adversarial security reviewer. The findings that held and can happen in real use are folded in (Amendments after the review), the improbable ones are under Accepted, not fixed, and the wrong ones are listed as dropped.

## Why

- **Some pages arrive empty.** `read_page` fetches a page once and reduces its HTML to text (`cloudflare/src/connectors/web/connector.ts:149-155`). A site that builds its content with scripts sends a shell: a root element, scripts and a `<noscript>` line. The reducer drops scripts and `<noscript>` with what is inside them (`cloudflare/src/lib/markdown.ts:3`, `:11-15`), so the model gets a title and almost no text (inferred).
- **How often is not known.** The only recorded real use is four `read_page` calls on staging, three of which failed with `PAGE_ERROR` (the app's `docs/architecture/connectors.md:136`), which this design does not change. Unit 1's P6 measures the shares on real addresses before any code is written.
- **The model has no way around it.** It can only report an empty page or try another site.
- **Cloudflare can render the page in one call.** Browser Run's Quick Actions load a page in a browser, run its scripts and return the result, with no session kept between calls (developers.cloudflare.com/browser-run/quick-actions, Oct 10 2026). Its lighter engine, Kitesurf, is free during its beta.
- **A working reference exists.** The open-source project bdots tries Kitesurf first and Chromium when Kitesurf throws, answers under 200 characters or answers with a status of 400 or more (its `src/agents/web-tools.ts:125-146`, `:207-212`). It was read, not run.

## The owner's requirements and what they change

The owner's requirements, 2026-10-25:

1. When `read_page`'s plain fetch comes back with too little text, because the site fills its content in with scripts, the engine asks Browser Run for the page through a Quick Action.
2. Kitesurf first, Chromium as the fallback.
3. No browser session stays open between calls.
4. Per-site grants keep working exactly as today.

What this design changes:

- **A thin https page with a script is rendered.** After a plain fetch of an https address answers 200 with HTML whose text is under 200 characters and which has a script element, the engine asks Browser Run's `content` action for the same address and reduces the rendered HTML with the same reducer.
- **The browser reaches only the granted host.** Every request the browser makes must match the page's own origin (`allowRequestPattern`), for the kinds of request Unit 1 shows the pattern covers. A result that a redirect took to another host is not shown.
- **The page's scripts run.** They can send requests of any method to that same host, as a visit in a browser would, and a link that signs in signs the browser in for that render. Today's `read_page` sends one GET. Whether that fits a read grant is owner question 2.
- **A failed render never fails the call.** The model gets the plain page's text with a short note instead.
- **At most 30 browser calls per run.** Past that, a thin page keeps its plain text with a note.
- **Nothing is charged for browser time** in this chunk. Each read that renders is logged with its engines and times (owner question 5).
- **One setting,** `MINERVA_WEB_BROWSER` (`off`, `kitesurf`, `kitesurf-chromium`), **off by default** and turned on per instance in its `vars.env`, and the `BROWSER` binding on every build but the dev server offline and the test build. With the setting off or no binding, `read_page` is exactly today's.
- **No change to the contract or to Laravel's code.** The site kind's note says that pages may open in Cloudflare's browser (owner question 8), so Web is approved once more on staging and production. `read_page`'s fingerprint changes only if the owner answers question 2 with a new revision.

**What this does not promise.** Pages behind bot protection, a login, video or WebGL stay empty: Browser Run "does not bypass CAPTCHAs, Turnstile challenges, or any other bot protection mechanisms" (crawl endpoint docs, in llms-full.txt), and Kitesurf cannot "negotiate a bot-challenge handshake with real TLS fingerprints" (/browser-run/kitesurf, Oct 6 2026). A page whose scripts or data come from another host stays thin, since the browser may not reach that host (Per-site grants), and so does a thin http page, which is not rendered (Private addresses). Text inside web components' shadow DOM may stay missing, since the serialized HTML may leave it out and the reducer drops `<template>` (`markdown.ts:11-15`) (guess; P5 checks).

## What Browser Run offers

- **The call.** `env.BROWSER.quickAction("content", options)` returns a `Response`. Success is JSON `{success: true, result, meta: {status, title, headers?, finalUrl?, redirectChain?}}`, where `result` is the rendered HTML (the types, `:11687-11697`, `:11752-11757`, `:12054-12068`). `finalUrl` and `redirectChain` are optional, and `redirectChain` leaves out client-side moves such as a meta refresh. `markdown` is the same with Markdown in `result`. There is no plain-text action.
- **The engine.** `browser: "kitesurf"` picks Kitesurf, and leaving it out picks Chromium. Kitesurf works with any Quick Action (the types, `:11543-11546`, `:11677-11678`; /browser-run/kitesurf, Oct 6 2026). Kitesurf's HTML extraction has a median of 820 ms against Chromium's 472 ms (/browser-run/kitesurf).
- **Errors are answers.** An error is JSON `{success: false, errors}` with status 400, 422, 429, 500 or 503 (the types, `:11839-11847`). A 422 is usually a timeout or a crashed page (/browser-run/faq, Jul 17 2026). A 429 carries `Retry-After` (/browser-run/limits, Oct 14 2026).
- **Time.** `gotoOptions.timeout` defaults to 30 s, at most 60 s; `waitUntil` defaults to `domcontentloaded` (/browser-run/reference/timeouts, Apr 21 2026). `actionTimeout` bounds "the browser action after page load", at most 120 s in the types and 5 minutes on the timeouts page, and `bestAttempt` continues "when awaited events fail or timeout" (the types, `:11529-11532`; the timeouts page does not mention it). The timeouts page states no overall limit on a Quick Action and says of several timers only that "as long as one is complete, the request will fire". `quickAction` takes no abort signal (the types, `:12068`). So how long a render can run at Cloudflare is not documented (P4 measures it).
- **Requests.** `allowRequestPattern` takes regular expressions on request URLs, and `rejectResourceTypes` takes resource types (the types, `:11489-11496`, `:11437`). Neither matches a request's method. The types say only that each allow option excludes its matching reject option, and the content endpoint's page says only "only allow requests that match `allowRequestPattern` or `allowResourceTypes`" (Sep 26 2026), so how `allowRequestPattern` and `rejectResourceTypes` combine is not documented. Hostname guardrails "are unavailable for Quick Actions" and "not supported with Kitesurf", and limit only "HTTP and HTTPS requests" where they apply (/browser-run/features/guardrails, Sep 26 2026). Outbound Workers route only HTTP, only for sessions, and other hosts "use the browser's normal network path" (/browser-run/features/outbound-workers, Oct 12 2026). Which kinds of request the pattern covers (frames, WebSockets, beacons, workers, new windows, navigations, redirect hops, traffic that is not HTTP), and whether Kitesurf honours it, is not documented (Unit 1 measures it).
- **State.** Kitesurf is "an ephemeral, fully-isolated, stateless engine designed to exist only for the duration of a task" (/browser-run/kitesurf, Oct 6 2026). For Chromium, the FAQ says only that Quick Actions "manage sessions and tabs automatically, so you do not need to handle reuse yourself", and nothing about cookies or storage between calls (/browser-run/faq, Jul 17 2026). Whether one Chromium render can see another's state is not documented (P4 measures it).
- **Measurement.** Every Quick Action response carries `X-Browser-Ms-Used`, the browser time in milliseconds (/browser-run/pricing, Apr 21 2026); the types say it is set when the status is under 500 (`:12066`). Whether Kitesurf sets it is not stated (guess; P4 checks). Monthly usage is on the Browser Run page of Cloudflare's dashboard (/browser-run/pricing).
- **Price.** Quick Actions are "charged for browser hours only": 10 hours a month included on Workers Paid, then $0.09 an hour. Concurrent browsers are billed for sessions only. A request that fails on `waitForTimeout` is not charged (/browser-run/pricing). Kitesurf "is in beta and available for free, behind per-account limits", with no numbers and no price stated for after the beta (/browser-run/kitesurf).
- **Limits.** Quick Actions are capped at 30 requests a second. The 200 concurrent browsers and 3 new browsers a second apply to sessions only. The limits page does not mention Kitesurf (/browser-run/limits).
- **Where and what is kept.** "Browser sessions open on Cloudflare's global network, close to the incoming request" (/browser-run/faq). Quick Action content is "immediately discarded" after the response, and output is cached for 5 s per account unless `cacheTTL` is 0 (/browser-run/faq). Nothing is said about how long addresses or request metadata are kept. Browser Run is not in the data localization compatibility table (developers.cloudflare.com/data-localization/compatibility, Oct 15 2026).
- **What a site sees.** Every request carries `cf-brapi-request-id`, `cf-biso-devtools` and Web Bot Auth signature headers, from Cloudflare's IP ranges (/browser-run/reference/automatic-request-headers, Jun 16 2026). "Requests from Browser Run will always be identified as a bot" (/browser-run/quick-actions/markdown-endpoint, Sep 26 2026). So a site can always tell Browser Run from Minerva's plain fetch, and answer it differently.
- **No local simulator.** Without remote mode, `quickAction` fails with "The RPC receiver does not implement the method" (/browser-run/quick-actions). `bindings.browser({dev})` exists in the config package (`@cloudflare/config` 0.24, `public-QtVVYn2k.d.mts:1264-1275`).

## Decisions

### When a page is rendered

- **Only after a plain fetch that answered 200 with HTML.** `outcome.form` is `html`: `text/html`, `application/xhtml+xml`, or a body with no Content-Type that starts as HTML (`fetch.ts:139-142`). Text types (JSON, XML, plain text, Markdown, CSV) are never rendered: they have no scripts to run.
- **Only an https page.** `outcome.url.scheme` is `https`. A thin http page keeps today's result. Every request the browser may then make goes over TLS to the granted name, so a name that resolves to a private address for the browser meets a server without that name's certificate (Private addresses). Thin http pages are rare (guess; P6 records their share).
- **Only when its text is under 200 characters** after `htmlToText`, trimmed, with the title not counted. A shell reduces to almost nothing, since `<noscript>` is dropped (inferred). bdots uses 200 for the same judgement.
- **Only when its HTML has a script element** (`<script` followed by a space, `>` or `/`, any case). A page without scripts cannot gain text in a browser, so a short static page is never rendered.
- **Never after an error or a move.** `SITE_NOT_PUBLIC`, `PAGE_ERROR` (a 403 or a challenge page included), `SITE_TIMEOUT`, `PAGE_TOO_LARGE`, `UNSUPPORTED_CONTENT` and `Moved` keep today's result. A site that refuses Minerva's fetch has answered Minerva, and Browser Run does not pass bot protection.
- **The address rendered is the one the fetch ended at,** `outcome.url`, after same-host redirects. So server-side moves to another host that the plain fetch sees are returned as `redirect_to` before any browser starts.

### Kitesurf, then Chromium

- **Kitesurf first** (`browser: "kitesurf"`). It is free during its beta and lighter.
- **Chromium next** (no `browser` field) after any Kitesurf outcome but a full render or a move: thin, refused, a throw, any error status, a 429 included, a timeout, too large or malformed. Kitesurf's limits are not published and may be its own, so a Kitesurf 429 does not say that Chromium is busy. bdots falls through the same way (`web-tools.ts:125-146`). After a thin Kitesurf render the page's scripts have already run once, so Chromium runs them a second time (owner question 2).
- **A move ends the browser stage.** A render that a redirect took to another host (Per-site grants, step 4) gives the `redirect_to` record, and Chromium is not tried: it would run the same script.
- **The setting picks the engines.** `kitesurf-chromium` tries both, `kitesurf` only Kitesurf, `off` neither. The default is `off`; an instance turns it on in its `vars.env`, with the engines Unit 1 passed (Deploy order).
- **No session.** Each render is one `quickAction` call. Nothing stays open between calls, and the engine holds no browser state.
- **At most 30 browser calls per run.** The run's browser port counts every `quickAction` call it sends, Kitesurf and Chromium, fallbacks and continuations included. Past 30, `read_page` sends no browser call and returns the plain text with the cap's note (What the model sees). The count lives in memory with the run's executor, so a restart or a deploy starts it again, which a user or a page cannot cause on purpose and which allows at most 30 more each time. This bounds what one run can spend and how much of Kitesurf's per-account limits it can use (Pricing and budgets).

### Per-site grants

Today a grant on a site means that only that site receives the address the agent opens, and a move to another site needs that site's own grant. This design keeps both, for the kinds of request Unit 1 shows covered.

1. **The plain fetch runs first,** with today's checks: authorization before anything is sent (`connector.ts:144-149`), the host rules of `lib/sites.ts`, same-host redirects only.
2. **The browser gets only `outcome.url`,** on the host just authorized.
3. **Every request the browser makes must match the page's own origin.** `allowRequestPattern` is `^https://`, then `host` regex-escaped (built from `WebURL`, which has no origin field), then `/`. `^data:` and `^blob:` are allowed, since they reach no network themselves; a worker built from one is still a worker, and P1 tests it. Everything else, analytics, CDNs and other hosts' APIs included, is blocked. A request on the same host with another port, or a WebSocket (`wss:`), does not match. Unit 1 decides which kinds of request this covers, with `read_page`'s exact options: sub-resources, fetch and XHR, beacons and `<a ping>`, EventSource, frames, WebSockets, dedicated, shared and service workers and workers built from `blob:` and `data:`, new windows (`window.open`, links and forms with `target=_blank`), form submissions, navigations by script and by meta refresh, HTTP redirect hops, speculation-rules prefetches, connection hints (`preconnect`, `dns-prefetch`) and WebRTC. ARCHITECTURE.md lists the kinds measured as covered, and docs/connectors.md claims only those. An engine that lets any of these kinds send a request to another host is not used. A connection hint that only resolves a name or opens a connection, and sends no request, is accepted if it gets through and recorded in ARCHITECTURE.md (owner question 7): it carries only a host name that the granted page chose, which that page could also receive itself.
4. **A result that a redirect took elsewhere is not shown.** `meta.finalUrl` is parsed with `parseUrl`. If it is missing or not a web address Minerva opens (`about:blank`, a `chrome-error:` page), the render failed. If it is on another host, or went from https to http, the record is the `redirect_to` record with its own note (What the model sees), and the content is dropped. If it is on the same host, it is the record's `url` and the base for relative links, since the browser may follow a same-host redirect that the plain fetch did not get. `finalUrl` is the "URL that served the response, after any redirects the browser followed" (the types, `:11694-11695`), so it catches HTTP redirects only. A move made in the page (a script, a meta refresh, a form submission) and a path changed with `history.pushState` are not in it (inferred; P2 records it). Moves made in the page are stopped by the pattern alone, which P2 checks at the destination.
5. **The record names the page's host,** `site(binding, host)`, so the executor checks it against the policy again (`executor.ts:292`).

**A site that answers the browser differently.** A site can always tell Browser Run apart (What Browser Run offers), so it can send the plain fetch a thin script page and the browser a 302 or a script move to another host, on purpose. Step 3 stops that move if P2 shows the pattern covers it on that engine; otherwise the engine is not used. Step 4 also drops the content of an HTTP redirect to another host. A move made in the page has only step 3.

What a site sees that it did not before: a second request for the same page, requests for its own scripts and data, and whatever its scripts send, from Cloudflare's browser with Minerva's user agent. It already had the address.

**Same host, not the run's grants.** A pattern built from the run's whole policy would let a page load from every host the user granted. It needs the policy inside the connector, denies under an allow written as lookaheads, and a probe that both engines run such patterns. Same host is what the grant that authorized this call covers in every case, so it is the rule here (owner question 3).

### What the page's scripts can do

- **Inside one render, the page is a visit.** Its scripts run, and they can send GET, POST or any other method to the page's own host, with the cookies the site set during that load. `allowRequestPattern` matches URLs only, and Quick Actions cannot block by method (What Browser Run offers).
- **So a read can now act on the granted site.** A page that confirms an email address, approves a request or unsubscribes by submitting itself with a script, as such pages do to defeat link scanners, is thin with a script, which is the trigger. An agent that opens such a link from a user's mail on a granted host would perform the action. Today's single GET does not.
- **A link that signs in signs the browser in.** Today's fetch sends no cookies and keeps none between same-host hops (`fetch.ts:333-347`), so a sign-in, invitation or reset link handled by the server ends on an anonymous page. A single-page app that handles such a link in the page sets its session during the render. The rendered page then holds that account's pages, which come back to the model and pass through Browser Run, and the page's scripts act inside that session. Agents that read mail and open its links do this in ordinary use, and an injected message can ask for it on purpose.
- **The model can choose what is sent.** A granted page that turns its address's query into a form submission, or has a script flaw reachable through the query, lets the model, or a page that injected it, choose what is posted to that host. Today the site receives the same address, but only as one GET.
- **An action can run more than once per read.** Chromium after a thin Kitesurf render runs the page's scripts a second time. Each continuation with `offset` renders again. `read_page` stays a read: it declares no `mutates`, so it skips the write ledger (`executor.ts:601`), is advertised with `readOnlyHint: true` (`executor.ts:431`), and is replayed after a restart or a deploy up to twice (`replay: "safe"`, `REPLAYS_ALLOWED`, `cloudflare/src/conversation/tools.ts:38`, `:103`). The plain fetch and the render also request the same address, so a link that works once may be used up by the first.
- **A failed render may still have run the scripts.** A render that timed out or answered 422 after its scripts ran says so in its note (What the model sees), so the model does not report that nothing happened.
- **No cookies or credentials from Minerva.** None are sent. Whether one render can see another's state is documented for Kitesurf (stateless) and not for Chromium (What Browser Run offers). Every tenant renders through one account, so a Chromium that kept cookies, storage or a service worker between calls would carry one tenant's session, a signed-in one included, into another's render of the same site. P4 measures it, and an engine that keeps state is not used unless the owner accepts it (owner question 7).
- **The owner decides** (owner question 2) whether this fits the read grant. The default is to accept it, bump `read_page`'s `revision` to 2, and say it in the description, the site kind's note (owner question 8), docs/connectors.md and ARCHITECTURE.md's Connectors section, repeats and replays included. A new revision changes the fingerprint, so a run in progress at the deploy loses `read_page` for the rest of that run: every call is refused `OPERATION_CHANGED` until a new message (`registry.ts:383-388`, `executor.ts:510-515`). The catalog's version does not cover revisions (`catalog.ts:49-60`). The alternatives are to skip Chromium after a Kitesurf render that reached the site but stayed thin, so scripts run once per read except on a continuation or replay, at the cost of the pages only Chromium fixes (P5 and P6 count them), or not to render.

### Private addresses

- **The address is public a moment before.** The render starts only after the plain fetch got a 200 from the same host, through the platform's refusal (`fetch.ts:1-17`). That says nothing about where the browser connects later: the check must hold on every hop and against the address actually connected to (`fetch.ts:4-6`).
- **The browser's requests stay on that host name** (the pattern), so an IP literal or another name is never requested, for the kinds of request P1 shows covered.
- **What remains is a name that resolves to a private address for the browser** but not for the Worker: a name whose answers change during the render, or one that answers a public and a private address at once. Someone can arrange that on purpose, so it is not improbable.
- **TLS closes it.** Only https pages are rendered, and the pattern admits only `https://` on the granted name, so every request the browser makes goes over TLS to a server that must present that name's certificate. A private address behind Cloudflare's network does not hold a certificate for a name the attacker chose (inferred). That holds only if Browser Run's browsers check certificates, which is not documented (guess); P3 checks it with pages whose certificates are invalid.
- **Kitesurf's requests go through a Worker,** "SandboxOutbound" (blog.cloudflare.com/kitesurf, Aug 6 2026), so they probably meet the same platform refusal (inferred). Chromium's network is not documented.
- **Unit 1 decides.** P3 asks each engine directly for the set the Worker's own refusal was measured against, and passes only on an observed refusal by Cloudflare, and every invalid certificate must fail the render. An engine that cannot be shown to do both is not used.

### Size and time

- **The response is read up to 8 MB,** through a capped reader, and parsed with `parseJson` (no `.json()`, `sources.test.ts:27`). 8 MB leaves room for JSON's escaping of a 3 MB page (guess; P4 measures the ratio). A larger response is a failed render.
- **The rendered HTML is at most 3 MB** in UTF-8, today's `MAX_BODY` (`fetch.ts:48`). A larger one is a failed render, and the plain text is kept.
- **Kitesurf:** `gotoOptions: {waitUntil: "networkidle2", timeout: 8_000}`, `actionTimeout: 3_000`, and the engine stops waiting after 15 s. **Chromium:** `timeout: 12_000`, `actionTimeout: 5_000`, and the engine stops waiting after 25 s. `bestAttempt: true` on both, so a page whose network never goes quiet is read as it is. Cloudflare recommends `networkidle0` or `networkidle2` for single-page apps (/browser-run/faq).
- **The local wait has room over Cloudflare's timers:** about 4 s on Kitesurf and 8 s on Chromium, for starting a browser and sending the answer back. It covers the call and reading the body.
- **How long a render runs at Cloudflare is measured, not assumed.** No overall limit is documented (What Browser Run offers), so P4 times a page that never goes quiet. If a render outlives its two timers by much, `timeout` and `actionTimeout` are lowered or `bestAttempt` is dropped, and Strict revocation and Pricing and budgets use the measured figures.
- **Fewer bytes:** `rejectResourceTypes: ["image", "media", "font"]`. Images become alt text anyway. Any type P1 shows the pattern alone does not block is added.
- **`cacheTTL: 0`,** so a render reflects the site now and no output stays in the account's cache.
- **`userAgent` is `USER_AGENT`** (`fetch.ts:34`), so a site sees one identity on both paths (owner question 10).
- **A call takes at most about 65 s:** 25 s of plain fetch, then 15 s on Kitesurf and 25 s on Chromium. A typical render is a few seconds (guess; Verify, perf measures it).

### What the model sees

The record keeps today's fields. Two optional fields are added: `rendered: true` when the text came from the browser, and `note` when a render was tried and no render reached 200 characters. Of the outcomes of the renders tried, the highest row in this table decides:

| The renders gave | Text | `rendered` | Note |
|---|---|---|---|
| A render that succeeded with 200 characters or more | That render's | true | None |
| A render that a redirect took to another host (this ends the stage) | None: the `redirect_to` record | Absent | "This page moved to another address when Minerva's browser opened it. Open redirect_to to follow it; that site needs its own permission." |
| At least one thin render | The longest of the plain text and the thin renders' | true if a render's text is the longest | "This page shows little text, also in Minerva's browser." |
| No browser call sent, since the run had made its 30 | The plain text | Absent | "This page shows little text, and Minerva's browser has opened as many pages as it may in this run." |
| No thin render, and a 429 or 503 from the last engine tried | The plain text | Absent | "Minerva's browser is busy and could not open this page. Try again in a minute." |
| No thin render, and the site answered the browser with a status of 400 or more | The plain text | Absent | "The site answered Minerva's browser with HTTP {status}." |
| Only failures (a throw, Browser Run's own 400, 422 or 500, a timeout, too large, malformed, no usable `finalUrl`, a `meta.status` other than 200 under 400) | The plain text | Absent | "Minerva's browser could not finish opening this page, and its scripts may have run." |

A render succeeded when `meta.status` is 200, as on the plain path, and `finalUrl` is on the same host. Only a render that succeeded supplies text: an error page of 200 characters or more, Cloudflare's own refusal page included, takes the status row. A render that succeeded is thin under 200 characters. With both engines on, a Kitesurf 429 goes on to Chromium, so the busy note comes from Chromium's 429 or 503, or from Kitesurf's with the setting `kitesurf`.

The description gains one sentence: "A page that shows little text without its scripts may be opened in Minerva's browser, which runs its scripts, may act on the site as a visit would, and takes longer." A continuation with `offset` renders the page again, and a rendered page can differ between renders, so docs/connectors.md's Limits says so.

### Strict revocation

- **No render starts once the run is revoked.** The browser call goes through the call's io, which checks `admits()` synchronously right before it, as `#send` does (`http.ts:276-283`). Chromium after Kitesurf is checked again. The io's own `NotSent` and `ProgrammingError` pass through as they are, as on the plain path (`fetch.ts:377`), and are never a failed render with a note. Anything `quickAction` itself throws is a failed render, so none of it reaches the executor's log of unexpected errors (`executor.ts:478`).
- **A render already sent is handed off.** `quickAction` takes no signal, so a cancel only stops the engine waiting (`unlessAborted`, `executor.ts:602`), and the result is dropped. The browser at Cloudflare goes on loading the authorized host, its scripts included, until Cloudflare ends it. The options above suggest about 11 s on Kitesurf and 17 s on Chromium after it started, but no document says those timers bound the whole call (guess; P4 measures it, and the measured figures replace these).
- **This changes what today's rule covers.** "A request already sent may complete" (ARCHITECTURE.md, Strict revocation) meant one HTTP request. A render is browser activity that can make new requests to that host after the cancel, bounded by Cloudflare rather than by the engine. Owner question 4, and ARCHITECTURE.md's Strict revocation says so, with P4's figures, in Unit 2's commit.

### Pricing and budgets

- **Browser time is not charged** to the run's allowance in this chunk.
- **Why not.** A charge needs a price for Kitesurf, which Cloudflare has not set; a record port from the executor to the store; a column in a Conversation migration; and a new term in `chargedMicros`. Laravel's `minerva:usage` fails every run whose `chargedMicros` is not the three sums (the app's `CheckUsage.php:139`), and recovery runs it (the app's `app/Console/Commands/Recover.php:221`), so Laravel would have to be deployed first. That is two repositories and a deploy order for a cost that is small and bounded.
- **The bound, per render.** Chromium's timers should stop a render after about 17 s, about 20 s with its start (P4 measures it): about 500 µ$ at $0.09 an hour (25 µ$ a second). Kitesurf costs nothing during its beta. A render the engine stopped waiting for, and each continuation with `offset`, is billed too.
- **Nothing else bounds renders per model call.** Only model calls check the allowance (ARCHITECTURE.md, Budgets), and a turn has no limit on tool calls (ARCHITECTURE.md, Permissions, No caps on work): the executor counts calls without limiting them (`executor.ts:484-487`). One model response can ask for dozens of direct `read_page` calls, which queue on the run's 4 slots, and a scripted call is never cut once sent (`conversation.ts:1371-1373`). A page that serves thin script shells and tells the model to read more of them can do this by prompt injection, and a user can do it on purpose. Without a cap, a run could keep 4 Chromium renders going for as long as it runs, about $0.36 an hour, outside the allowance, and use up Kitesurf's per-account limits for every tenant.
- **The bound, per run.** The cap of 30 browser calls per run (Kitesurf, then Chromium) bounds a run at about 30 Chromium renders of about 20 s, 600 browser seconds, 15,000 µ$, until a restart starts the count again. The account's ceiling is 30 Quick Actions a second of about 20 s each, roughly 600 browser hours an hour, $54, which would need about 150 runs rendering at once. A pilot hour of about 200 renders, 30% of them on Chromium at about 8 s, is about $0.012. The account's 10 included hours are about 4,500 Chromium renders of 8 s a month.
- **What that means.** Laravel's monthly spend and the allowance leave out browser time, and Minerva pays it. Each read that renders writes one log line: each engine tried with its outcome, `meta.status`, Browser Run's numeric error code if any, `X-Browser-Ms-Used` (or none, which leaves that render out of a sum while its duration is still logged) and its duration, then the plain fetch's duration and the whole read's. An outcome is one of a fixed set: `rendered`, `thin`, `moved`, `busy`, `site_status`, `timeout`, `too_large`, `malformed`, `no_final_url`, `failed`, `capped`. The line never names the address or host, and never holds Browser Run's error `message`, `detail` or `path`, or a thrown error's message, since those can quote the address and any token in it (guess). Workers Logs keep 7 days (docs/data-processing.md, Logs), so they show a week; the month's browser hours come from the Browser Run page of the dashboard (cloudflare/README.md gains the monthly check).
- **Later.** When Kitesurf gets a price, or the account's Chromium time passes the included hours, a later chunk charges it: `browser: {perHour}` in the price table (additive, and Laravel ignores `prices`, the app's `app/Engine/EngineClient.php:74-80`), optional `browserMs` and `browserMicros` on `run.settled`, and Laravel's `CheckUsage` deployed first (owner question 5).

### The setting, the binding, and instances without them

- **`MINERVA_WEB_BROWSER`:** `off`, `kitesurf` or `kitesurf-chromium`, parsed with `oneOf` like `MINERVA_MODEL_API` (`cloudflare/src/config.ts:107`), with its default `off` in `build-settings.ts`. Any other value fails the build. A default other than `off` would turn rendering on for every instance at its next deploy, production's included, whatever that deploy was for.
- **Turning it on or off is one step:** a line in the instance's `vars.env` and `pnpm run deploy` of the same commit, which needs no new CI run (AGENTS.md, Git). Busy objects keep the old settings for minutes (ARCHITECTURE.md, Emergency stop).
- **`BROWSER: bindings.browser({ dev: { remote: true } })`** in `cloudflare.config.ts`, left out offline and in the test build (`target.faults`), with a comment like the Images binding's (`cloudflare.config.ts:166-171`).
- **A port,** `ConversationPorts.browser(context)`, returns null when the binding is absent or the setting is `off`, and otherwise the engines in order and a `content` function that counts its calls against the cap. It is called once per run's executor (`conversation.ts:1295-1314`), so the count is the run's. `ExecutorContext` gains an optional `browser`, `CallIo` takes it, and `ProviderIo` gains `browser: BrowserIo | null`, gated as `fetch` is. `settingsIo` has none, so `discover` and `describe` never render.
- **The test build has no browser.** Its ports return null (`faultConversationPorts`, `cloudflare/src/faults/ports.ts:207`), as its network reaches only `*.fake.invalid`, so a Worker the token-gated driver controls never reaches Browser Run, which reaches the whole web.
- **Without a browser, `read_page` is exactly today's:** same records, no note. That covers the dev server offline, the platform tests, the test instances and any instance with the setting off. `offered` does not depend on it, so the catalog is the same with the setting on or off.
- **Mode `development`** (`pnpm exec vite`) has the binding, and renders on the account's Browser Run, against its included hours and its shared limits, when the shell sets the setting.
- **A binding that fails** (for example, an account without Browser Run) is a failed render: the plain text and the "could not finish opening" note.
- **The deployed probe renders one fixed page.** `/api/probe` gains `browser`: for each engine the setting turns on, one render of `https://example.com/` with `read_page`'s options, answering its status, the text's length, whether `finalUrl` and `X-Browser-Ms-Used` came back, and its duration. It takes nothing from the request, so it cannot be used as a proxy, and it answers `null` without a browser. `test:deployed` checks it, so every deployed instance with the setting on proves its binding after each deploy.

### The contract, the catalog and the fingerprint

- **No contract change.** No fact, command or price changes, so Laravel needs no deploy and the engine's deploy has no order (docs/plans/contract.md, Versions). Only the catalog's approval follows it.
- **The site kind's note changes** (owner question 8). The person who grants a site sees that note (`connector.ts:206`), and neither the description nor `revision` reaches them (`registry.ts:256-271`, `catalog.ts:49-60`). Today's note says only that an agent can send information to the sites it may read. It gains: "A page may open in Cloudflare's browser, which runs its scripts and can act on the site as a visit would." The catalog's version changes, so the operator runs `minerva:catalog --approve --only=web` once on staging and once on production (the app's `docs/architecture/connectors.md:28`). Until then, Laravel shows the old note and Web stays offered, since everything reads the approved entry (`:27-31`).
- **The fingerprint follows owner question 2.** The input, needs and output action are unchanged, and the description is not covered. With the default answer, `revision` becomes 2: a read can now act on the site, a change of meaning the declaration does not show. The pin at `connectors-web.test.ts:105` then changes for `read_page` only, and a run in progress at the deploy loses `read_page` for the rest of that run (`OPERATION_CHANGED` on every call until a new message). With `revision` kept at 1, the pin stays.
- **What the user sees in Laravel** is unchanged: the tool call's label, arguments and decision (the app's `resources/js/components/chat/thread.tsx:500-523`). A rendered read takes a few seconds longer.

### Where it runs and what Cloudflare sees

- **What reaches Browser Run:** the address the agent opens, which can carry whatever the agent put in it, tokens included, and the page and the same host's resources it loads. When the address signs in, that includes the session the page sets and the account's pages it shows (What the page's scripts can do). The rendered HTML comes back to the Conversation object.
- **Where:** "close to the incoming request" (/browser-run/faq), with no location guarantee and no jurisdiction option. It may run anywhere on Cloudflare's network, outside the EU included, also for an EU workspace's conversation, whose object is in the EU (`addressing.ts:21-27`). All of Laravel's conversations are EU (ARCHITECTURE.md, Addressing), so this covers every tenant. docs/data-processing.md says no more than that.
- **Kept:** page content and output are discarded after the response, and `cacheTTL: 0` turns the cache off (/browser-run/faq). How long addresses and request metadata are kept is not documented.
- **docs/data-processing.md** gains a row for it, and its Subprocessors' Cloudflare row lists Browser Run (owner question 1).

## Deploy order and rollback

Deploys of staging and production ask the owner first (AGENTS.md, Cloudflare). Laravel is not deployed.

1. **Unit 1, the probes,** with the owner's go. They decide which engines may be turned on. If Kitesurf fails P1 to P3, or P5 or P6 fall below their marks, the design goes back to the owner before Unit 2.
2. **Unit 2** in one commit, with the setting `off` by default: `pnpm check --instance minerva-cf-test`, push `main`, green `main.yml`, and `account.yml` (`gh workflow run account.yml --ref main`), which runs the suites the change needs: all of `test:faults` and `test:deployed`, since it changes `cloudflare.config.ts` (cloudflare/README.md, CI's test instance). Production's or staging's next deploy for any other reason carries the code with rendering off, which gives today's `read_page` results (and, if owner question 2 gives a new revision, a run in progress loses `read_page` until its next message).
3. **`minerva-cf-staging`,** once the owner says so: with Unit 2's code deployed there, `minerva:catalog --approve --only=web` on Laravel's staging, so the new site note shows before any page renders; then `MINERVA_WEB_BROWSER` set in its `vars.env` to the engines Unit 1 passed, `pnpm run deploy`, `pnpm test:deployed --instance minerva-cf-staging`, and the live checks.
4. **`minerva-cf`,** only after staging's live checks pass, and only when the owner says so (owner question 6): the Web approval on Laravel's production once Unit 2's code is deployed there, then the same line in its `vars.env`, and a deploy.

**Rollback.** `MINERVA_WEB_BROWSER=off` in the instance's `vars.env` and `pnpm run deploy` of the same commit; busy objects follow within minutes. The note stays approved; it says only that a page may open in the browser. Rolling the code back is also free: no storage or contract changed, and Laravel shows the approved new note until Web is approved again. A run in progress during either sees `read_page` change its results, and loses `read_page` until its next message if the revision changed. ARCHITECTURE.md's Status says which instances have browser reads on.

## Risks

- **Kitesurf is a beta** with no price for after it and unpublished limits. A price, or new limits, may make Chromium the only engine or turn rendering off. The monthly check in cloudflare/README.md watches for it, and the deployed probe shows a beta change on staging at the next `test:deployed`.
- **A Browser Run outage or slowdown.** While it lasts, each thin read waits up to 40 s on the browsers (15 s and 25 s) and holds one of the run's 4 slots, so the run's other calls queue behind it and a script that reads several thin pages can reach its 120 s. Each read then gets the plain text with a note. The lever is `MINERVA_WEB_BROWSER=off` and a deploy of the same commit (cloudflare/README.md, Deploy), which busy objects follow within minutes.
- **A read can act on the granted site,** sign in through a link and repeat an action (What the page's scripts can do). Owner question 2 decides whether that is accepted.
- **Chromium may fail P1 on WebSockets or new windows,** since request interception in Chromium commonly misses them (guess). Then `kitesurf` alone is the setting (owner question 7).
- **Same host may leave many pages thin.** Single-page apps often load scripts from a CDN or data from an API host. P5 and P6 show how many. Owner question 3 is the lever.
- **A site may treat Browser Run as a bot,** since it is always identified as one, and refuse it. The plain text is kept.
- **Kitesurf may ignore an option** it does not support, such as `rejectResourceTypes` or `networkidle2` (guess). P4 checks, and a render that ignores the resource types only costs time.
- **Renders are not deterministic.** A continuation's slice can overlap or skip text when the page renders differently. docs/connectors.md says so.

## Accepted, not fixed

- **Browser Run ignoring `cacheTTL: 0`** would be a platform misbehaving in a way it is not known to. A render could then be up to 5 s old, and come from the account's cache.
- **A render that outlasts its local wait** needs Browser Run to overrun its own timers by more than 4 s on Kitesurf or 8 s on Chromium beyond what P4 measured. The call then frees its slot while the browser still works, so a run briefly has a fifth browser, still bounded by Cloudflare, and the result is dropped.
- **A request or a move of a kind neither P1 nor P2 tests** getting past the pattern needs a channel that no reviewer or probe named. If it occurs, another host receives what the granted page already holds, a private address could receive a request whose answer a page on another origin cannot read, and for a move the record shows the other host's text under the granted host's address, since `finalUrl` does not follow moves made in the page.
- **The account's 30 Quick Actions a second** are shared by every tenant and instance. Reaching it needs about 8 runs rendering at the same moment, since one run makes at most about 4 renders a second, which is unlikely at pilot scale. When it happens, thin reads get the busy note or the plain text for that second. The monthly check revisits it, and Cloudflare can raise the limit when the pilots grow.

## Owner questions

1. **Processing outside the EU.** Browser Run has no jurisdiction option and is not in Cloudflare's data localization table. It opens "close to the incoming request", with no location guarantee, so it may run outside the EU, for every tenant, since all of Laravel's conversations are EU. It receives the address the agent opens, which can carry tokens and whatever the agent put in it, and the page, which the site itself receives anyway, wherever the site is; when the address signs in, also that account's pages. It discards page content after the response; how long it keeps addresses and request metadata is not documented. Default: acceptable for this feature, documented in docs/data-processing.md as having no location guarantee.
2. **A read that runs the page's scripts.** Inside a render the page's scripts can send requests of any method to that site, with cookies it set during the load. So: a page that confirms, approves or unsubscribes by submitting itself does so when an agent reads it; a sign-in, invitation or reset link handled in the page signs Minerva's browser in, and the model then reads that account's pages; a page that turns its address into a form submission lets the model, or a page that injected it, choose what is posted; and such an action can run more than once per read (Chromium after a thin Kitesurf render, each continuation, up to two replays after a restart), since `read_page` stays a read. A render that failed may still have run the scripts, and its note says so. Quick Actions cannot block by method. Default: accepted for the read grant, `read_page` at revision 2 (a run in progress at the deploy loses `read_page` until its next message), the new site note (question 8), and sentences in the description, docs/connectors.md and ARCHITECTURE.md. Alternatives: skip Chromium after a Kitesurf render that reached the site but stayed thin, so scripts run once per read except on a continuation or a replay, losing the pages only Chromium fixes (P5 and P6 count them); or not render.
3. **Which hosts the browser may load from.** Same host only keeps grants exactly as today and leaves pages that need a CDN or an API host thin. The alternative, every host the run's grants allow, renders more pages and needs the policy compiled into a pattern. Default: same host only, revisited with P5's and P6's numbers.
4. **Revocation and a render in flight.** A render already sent goes on at Cloudflare after a cancel, and can make new requests to its authorized host, scripts included, for as long as Cloudflare lets it, about 11 s on Kitesurf and 17 s on Chromium by the options (guess; P4 measures it); its result is dropped. Today's rule allows one request already sent to complete. Default: acceptable within P4's figures, and ARCHITECTURE.md's Strict revocation says so.
5. **Charging browser time, and the cap.** Not charged in this chunk, logged per read. A turn has no limit on tool calls, so one model response can ask for many renders; a cap of 30 browser calls per run bounds a run at about 15,000 µ$ of Chromium time, and a pilot hour is about $0.012; Kitesurf is free in its beta. Charging needs Kitesurf's price and a Laravel change deployed first. Default: not charged now, the cap at 30; a later chunk charges it when Kitesurf gets a price or Chromium passes the included 10 hours a month.
6. **Which instances, and Kitesurf in production during its beta.** The setting is off by default. Default: staging first, with the engines Unit 1 passed; production only after staging's live checks, when the owner says so.
7. **Chromium as the fallback, and what Unit 1 may let through.** Each engine is used only if Unit 1 shows it honours the pattern for every kind of request P1 and P2 test, with `read_page`'s exact options, refuses every private case and invalid certificate in P3, and keeps no state between renders in P4. Chromium may fail on WebSockets or new windows (guess). A connection hint that only resolves a name or opens a connection, with no request, carries only a host name the granted page chose. Default: `kitesurf` alone if Chromium fails any of these; hints of that kind accepted and recorded in ARCHITECTURE.md; any other kind that gets through, or state kept between renders, keeps that engine off unless the owner accepts that one kind.
8. **The site note.** The person who grants a site sees only that note, so it says that a page may open in Cloudflare's browser, run its scripts and act on the site as a visit would. That changes the catalog's version and needs one Web approval on staging and one on production, before rendering is turned on there. Default: changed. The alternative keeps today's note, so a grant made after the change gives a power its screen does not describe.
9. **The trigger.** Under 200 characters of text and at least one script element, after a 200 on https; a thin http page is not rendered, so TLS keeps a private address from answering for the name. Default: as proposed, revisited with P6's shares.
10. **The user agent.** Minerva's own, as the plain fetch sends, rather than Browser Run's Chrome string. Some sites may serve less to an unknown browser (guess). Default: Minerva's.
11. **Time.** Up to 15 s on Kitesurf and 25 s on Chromium, so a read takes about 65 s at worst. Default: as proposed.

## How this design was chosen

Three readers mapped the engine's Web connector, executor, budgets, settings and test build; Browser Run's docs and the generated types; and Laravel's use of the Web connector, its catalog approval and its billing. bdots' `web-tools.ts` was read as a reference. The design takes bdots' order of engines, its fall-through on any Kitesurf failure and its 200 characters, and differs where Minerva's grants and budgets need it: the plain fetch first, `content` instead of `markdown`, the same-host pattern, the gated io, and no failed call from a failed render.

## Alternatives rejected

- **`markdown` instead of `content`.** It returns remote images as `![](…)`, which would carry image links into the conversation, while `content` reduced by `htmlToText` keeps only alt text, so the conversation never gains a remote image that could carry data out (`markdown.ts:1-5`). `content` also keeps one converter for both paths.
- **Rendering every page.** Slower, costs browser time on pages that need none, and sends every address to Cloudflare's browser.
- **Rendering after a 403 or a challenge.** Browser Run does not pass bot protection, and the site has refused Minerva.
- **A `render` input the model sets.** A new input changes the fingerprint and gives running runs `OPERATION_CHANGED`, and the model cannot tell better than the engine when a page needs scripts. Later, if pages with enough text but missing content turn out common.
- **Blocking requests other than GET from the render.** Quick Actions match URLs and resource types only, and blocking the `fetch` and `xhr` types would break the pages that need rendering.
- **A browser session with request interception** (`acquire` and Puppeteer, closed after each call). It could check every request's host and method against the run's grants, but it is not a Quick Action, adds a dependency and startup CPU, counts against 3 new browsers a second, and its guardrails do not work with Kitesurf.
- **Passing the fetched HTML as `html`.** The page's origin would not be the site's, so relative scripts and same-origin requests fail.
- **Outbound Workers or hostname guardrails** to keep the browser on the host. Neither works for Quick Actions.
- **Skipping Chromium after a Kitesurf 429.** Kitesurf's limits are not published and may be its own, so Chromium may still have room; trying it adds at most one refused request.
- **A default other than `off`.** It would turn rendering on for production at its next deploy for any reason.
- **Charging browser time now.** See Pricing and budgets.
- **Rendering http pages.** Their requests have no TLS, so a name that resolves privately for the browser would reach the private address, and only a probe of Browser Run's local-network checks, which are not documented, could show otherwise. Thin http pages are rare (guess; P6 records their share).
- **Marking `read_page` as a write.** It would put each read through the write ledger, run reads one at a time and stop replays, for the few pages whose scripts act. Owner question 2 keeps it a read and says so.
- **A fake browser in the test build with fault points.** Its `read_page` reaches no page, so the browser would be unreachable code.
