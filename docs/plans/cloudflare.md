## Goal

The same product on Cloudflare's platform, deployed with one command to one Cloudflare account:

- the same React app and the same JSON API (`frontend/openapi.json`); sign-in moves from allauth's headless API to Better Auth's client (`frontend/src/lib/auth.ts` and the auth pages), and the rest of the frontend needs no changes beyond its dev proxy (the frontend cleanup later replaced that API with the oRPC contract in `contract/`, in camelCase);
- the same permission model and pipeline, and all 20 connectors;
- the same agent: pi-durable with Minerva's tools, history, code mode and files, durable across crashes, with today's guarantees for writes (deduplicated, never replayed, uncertain ones pause the run);
- a sandbox per turn with no network, now a Firecracker microVM;
- fewer moving parts: no supervisor, no Docker socket, no socket relay, no run tokens, no VPS, no Postgres.

What it should show: which of Minerva's hard problems the platform removes (sandbox runtime, the Docker socket, approvals that hold compute, downloads, deploys, logs), and what it costs (laptop and VPS self-hosting, compliance scope, beta dependencies, a larger trusted code base).

Not in scope: Minerva Cloud's control plane (a separate, private repository, below), self-hosting on a laptop or VPS (retired), the demo's features (`backend/demo/`), WebAuthn, social login, data migration from an existing Postgres, team workspaces (as today).

**Parity** (decided 2026-10-12; narrowed by the cleanup the same week). Users see the same product: the React app, the JSON API's paths and shapes (`{detail}`, the 422 list), error codes and permission rules; sign-in's wire format is Better Auth's. Wording and edge cases follow the runtime and its libraries (`JSON.stringify`, zod's messages, `URL`, `Intl`, htmlparser2, postal-mime), not Python; the cleanup's commits list each difference the model or a user sees. **Instances start fresh**: they do not read data from today's Django deployments (encrypted credentials, fingerprints, folder digests, password hashes); moving a real customer would be a one-off export and import.

## Instance and control plane

Decided 2026-10-11. Everything a company needs to run Minerva for its own people is an **instance**: one deployment of `cloudflare/` into one Cloudflare account, holding its own users, data and secrets, and needing nothing outside that account. Self-hosting means deploying an instance into your own account. Everything needed only to sell Minerva to many customers is Minerva Cloud's **control plane**, which is a Laravel application on Laravel Cloud (decided 2026-10-13, [self-hosting-and-cloud.md](self-hosting-and-cloud.md); earlier Python and Django), lives in a separate private repository, and is used only by the operator. The test for a feature: would a company running Minerva for itself need it? Then it belongs in the instance.

| In the instance (this repository) | In the control plane (private) |
|---|---|
| Users, sign-in, two-factor, sessions; SSO and directory sync for organizations | Customers, billing contacts, the signup site |
| Organizations, workspaces, teams, roles, ceilings, connections, agents, permissions | Plans and the entitlements an instance enforces |
| Runs, sandbox, files, code mode, connectors | Creating, upgrading, suspending and deleting instances (Cloudflare's API) |
| The audit log, retention, quotas enforced locally | Billing (Stripe) from the usage instances report |
| Model settings: an instance key and a key per workspace | Minerva's platform model key and shared OAuth apps, configured into cloud instances like any instance's |
| An instance admin, emergency stop, a support-access switch the organization controls | Support workflows that use that switch, abuse handling |

The two meet through Cloudflare's API and a small, signed **management API** in the instance (create or suspend organizations, set entitlements, read usage, version and health, emergency stop). An instance keeps working without the control plane: it caches its entitlements and decides everything else itself, and the control plane never holds an organization's content or credentials.

**Databases.** An instance has no Postgres, self-hosted or in the cloud: D1 holds accounts and the directory, each Workspace and Conversation object its own SQLite, R2 the files. Laravel MySQL on Laravel Cloud is the control plane's own database, for customers, billing, entitlements, the list of instances and usage totals; the two never share a database.

- **Organizations** sit above workspaces: an organization owns its members, SSO settings, ceilings, audit log, entitlements and data region (jurisdiction). A self-hosted instance usually has one; a shared cloud instance has many.
- **Cloud hosting** starts with shared instances, each holding many organizations. A dedicated instance for one customer is the same deployment with one organization, so it needs nothing beyond what self-hosting needs (any instance name, any account, the setup script); only the control plane's automation for running many of them waits until a customer asks.
- **Licence.** The instance is meant to be released as MIT or Apache 2.0; the control plane stays private.

## Trust model

| Zone | Trusted? | Holds |
|---|---|---|
| Browser | The signed-in user | Session cookie, CSRF token |
| Worker and Durable Objects | Yes: our code and its dependencies | Secrets, all state, decrypted credentials for one provider call at a time |
| Sandbox container | **No**, hostile | The turn's files; no token, no route out |
| Script guests | **No**, hostile | One RpcTarget that queues tool calls |
| Model output, provider content, files | **No** | — |

**What changes from today, stated plainly.** Today the agent loop (pi-durable and its extensions) runs inside the hostile container, and a compromise of it reaches nothing but the gateway. Here the loop is trusted code in the Conversation DO, in the same Worker script as the secrets and the executor, so the trusted code base now includes pi-durable, pi-ai, the Agents SDK and their dependencies. A bug or supply-chain compromise in any of them runs with the Worker's bindings and secrets: it could address any workspace's objects and decrypt **every** workspace's credentials, not only its own conversation's. Model output cannot execute as host code: it reaches the loop only as tool names, arguments and text, which go through the permission pipeline as today. Code the model writes runs only in the container and in script guests, which hold nothing and reach nothing.

Mitigations in this plan: dependencies pinned with exact versions and lockfile hashes; credentials decrypted only in the executor, for one call, never stored in pi's state, events or logs; the model request built by our own provider wrapper, which still refuses anything but text input and function tools (a defence in depth, now that the request is not hostile). Later (open question 1): the executor and the decryption key move to their own Worker script, so the loop's isolate never holds a credential.

## Data placement

Each piece of state has one authoritative home; everything else is an index that can be rebuilt from it.

- **D1** (one database per instance, primary near Frankfurt): Better Auth's tables (users, sessions with their credential stamps, accounts, verifications, two-factor secrets and backup codes, organizations with members and invitations, rate limits; organizations also carry `personalOwner` and jurisdiction, and later SSO settings and entitlements), and ours: `workspaces` (id, organization, kind, name, `personal_owner`, jurisdiction; organization and owner RESTRICT), `memberships`, `oauth_clients`, `oauth_flows` (one per session, 600 s), `totp_steps` (the last TOTP step each authenticator accepted), `rate_limits` (our per-address and per-user limits), `instance_setup` and `instance_settings`. Auth transitions use conditional SQL (`UPDATE … WHERE attempts < 3 RETURNING`) or atomic `batch()`, since D1 has no interactive transactions; reads go to the primary (no read replicas).
- **Workspace DO**: authoritative for `connections` (encrypted credentials, status, generation, scopes, refresh state), `layers`, `grants`, `agents`, `uploads` (unattached, per user, with reservations), the `runs` registry (run, conversation, user, agent, connection ids, state, revoked), the cancellation `outbox`, byte counters. Index only: `conversations` (id, user, agent, title, timestamps).
- **Conversation DO**: authoritative for its owner, workspace and agent (fixed at creation), `messages`, `runs` and `attempts`, `run_events`, the write ledger (`run_writes`), `page_tokens`, `start_keys` (Idempotency-Key, kept 24 hours), `folder_versions` (manifests split into rows under 2 MB), the run's checkpoint, the script store, and pi's `pi_*` tables.
- **Sandbox DO**: authoritative for the container's lifecycle: incarnation id, owning run and attempt, hardening state, cleanup pending.
- **Scripts DO**: nothing durable.
- **R2 `minerva-cf-files`**, and **`minerva-cf-files-eu`** (created in R2's EU jurisdiction) for EU workspaces: `blobs/<ws>/<conv>/<sha256>/<random>` and `uploads/<ws>/<user>/<id>`; the default-jurisdiction bucket also holds `static/assets/...`, the earlier builds' hashed frontend files (see Step 5, chunk 404s). Content is deduplicated within a conversation, not across conversations. A lifecycle rule deletes `uploads/` objects a day after they were written, attached or not, so a folder never names one (see Starting a run).

**Addressing.** One module (`src/addressing.ts`) maps a workspace's id and jurisdiction (from D1) to its objects (`jurisdiction('eu')` when set) and to its bucket, since the same name with and without a jurisdiction is a different, empty object. The Worker never routes a request to a Durable Object by a client-chosen name without checking it; there are no generic Agent routes (`routeAgentRequest` is not used); objects are reached only through typed RPC from our own code. Local workerd has no jurisdictions (`jurisdiction()` throws), so with `MINERVA_DEBUG` on, and only then, an EU object is named `eu:<name>` in the plain namespace; a production build refuses `MINERVA_DEBUG`. Where an EU workspace's container runs is unmeasured: `durable_object` scheduling has no placement constraint, so the VM may sit outside the EU even when its Sandbox DO does not (measured in step 3). The deployed Worker's `/api/probe` (token-gated) reports each class's jurisdiction as the account tests see it.

## Protocols

These are the parts where a port is most likely to be subtly wrong. Each has fault-injection tests (see Testing) before anything is built on it.

### Starting a run

A message that is refused (409 while a run is active, an unknown agent, a missing or foreign upload, attachments over the folder's limits) must leave nothing behind, as the frontend expects; one that is accepted stores its message and run together.

1. **Conversation DO:** checks that no run is active (409), picks the run id, and records a private `starting` marker for it (invisible to the API).
2. **Workspace DO `beginRun(runId, conversation, user, agent, uploadIds, folderUsage)`**, idempotent by run id and synchronous inside (no awaits): checks the agent, the uploads (the user's own, unattached, complete) and the folder limits with the attachments, reserves the uploads for the run, computes the snapshot, registers the run as active, and returns the snapshot or a refusal. Called again with the same run id, it returns the same answer; it refuses a run it has since revoked or expired.
3. **Conversation DO, copying the attachments** (files spec 15.2, option A): for each reserved upload whose contents the conversation does not hold yet, it records a loose blob key `blobs/<ws>/<conv>/<sha256>/<random>`, then copies the upload's object to it with `get` and `put` with the upload's SHA-256, which R2 checks. The folder then names only the conversation's own blobs, never an `uploads/` key, which the lifecycle rule deletes a day after it was written. An upload already gone refuses the start ("An attached file is no longer available. Remove it and attach it again."). Up to 10 × 50 MB per message pass through the object; its time and CPU are measured in step 3, with a crash during the copy among the fault tests (loose keys not claimed are deleted by an alarm).
4. **Conversation DO, in one transaction:** on a refusal, deletes the marker and answers the API with today's status and message; on success, stores the message, the run (`queued`, attempt 1, `activated` false), the snapshot, and the base version with the copies (claiming their loose keys), sets an alarm, and answers. If a cancel arrived during the awaits, the run is stored as cancelled, as today when a grant change races a start.
5. **Activation:** the Conversation DO then calls `activate(runId)`, which turns the reservation into consumption (the Workspace deletes the upload rows and objects). It is idempotent and answers where the registration stands: active, revoked with its reason, expired, or ended. Until an answer arrives, the Conversation DO sends it again on its alarm and whenever its constructor runs, for every stored active run not yet `activated`; a run that comes back revoked stops with that reason, and one that comes back expired fails (`start_expired`). A Conversation DO that restarts with a `starting` marker calls `beginRun` again; the Workspace DO's alarm releases reservations not activated within ten minutes and marks those runs expired, so a late `beginRun` result cannot start them.

The snapshot holds everything today's does: policy layers, tool refs and fingerprints, instructions with the start time, model alias, base folder version, attachments, deadline.

### Strict revocation

The Workspace DO's transaction that changes grants, removes a connection or changes an agent's connection set is the commit point; the acknowledgement barrier after it is the enforcement point.

1. In that one transaction it applies the change, marks every affected registered run `revoked`, and writes one outbox entry per run.
2. It delivers each entry: `cancel(runId, reason)` on the run's Conversation DO, which sets the run's local `revoked` flag and stops the run with "Stopped because permissions changed." and the matching code (a deletion's cancel and an emergency stop end with "Stopped.", codes `cancelled` and `emergency_stop`).
3. The API answers the browser only after every delivery is acknowledged. An entry that fails is retried by the Workspace DO's alarm until acknowledged; the request answers 503 if that takes over 10 s (the change stays saved and the runs are stopped shortly after).
4. A cancel for a run the Conversation DO has not stored yet leaves a tombstone, so step 3 of a start stores it as cancelled.

The executor checks the local `revoked` flag and the run's state synchronously, with no await in between, immediately before it dispatches any provider request, and again before it returns a result. The guarantee is the same as today's from the user's side: once the browser is told the change is saved, no new provider request starts under the old permissions; a request already sent may complete ("no further effects", not rollback). Between the commit and the acknowledgement, a run may still start a request, which today's database check would have stopped a few milliseconds earlier. Which runs a change affects follows today's rules exactly (a grant change cancels all of the user's active runs, queued included).

**Emergency stop.** Busy objects keep running their old code for minutes after a deploy, so a security fix cannot rely on a deploy reaching running turns. An operator command cancels every active run in a workspace or in all of them, through the same outbox.

### The harness

PiHarness (`agents/harness/pi`, agents 0.28.0) runs pi-durable 1.1.0 in the Conversation DO, which extends the Agents SDK's `Agent` and attaches it with `this.lifecycle.use(...)`; pi's tables live in the object's SQLite. Requirements, each from the spike:

- `settings.contextRetentionMs: 0`, since pi otherwise keeps every object active, and billed, for 10 minutes after each turn;
- one extension, `minerva`, registers the tools; a new pi session per run (`sessions.create()`), submitted once with `operationId: run:<id>` (idempotent) and today's history replay, so what the model sees does not change; steers and follow-ups (`whenBusy`) work and come later;
- the model through our provider wrapper (below), never `createAI`'s default AI Gateway, which logs prompts;
- tools honour `context.abortSignal`.

**Model.** pi-ai, with Workers AI by default (`@cf/zai-org/glm-5.3-flash`: all 10 models tried made the right calls; this one was the cheapest, about $0.00015 for a two-read, one-write turn) or an OpenAI or Anthropic upstream, both through the Worker's own AI Gateway `minerva-cf` with prompt logging off. Model settings come from configuration (`MINERVA_MODEL_*`), as today. The wrapper forces the model, the output cap and `store: false`, sends only text and function tools, and taps the stream for deltas. No provider text reaches pi's state, its events or the logs: a failure's text is replaced (a context overflow by our own words that pi-ai still classifies as one, so pi compacts and asks again), createAI's diagnostics, which copy it, are dropped from every message, and the log gets the failure's kind, status, class and createAI's code.

### Attempts and recovery

pi has no restart limit and no notion of Minerva's attempts, so the Conversation DO keeps them. The first execution is attempt 1; there are at most 3.

Measured in step 2a (112 injected deaths across tool, model-stream, factory and submit crashes, memory-limit resets and caps, plus controls; reviewed adversarially):

- **Where the gate runs: first in PiHarness's harness factory**, before `Harness.open`. pi exists only once the factory returns, and every event that opens pi (alarms, requests, RPCs) goes through it, so nothing of pi runs before the gate. The constructor is not usable: the platform sometimes builds an instance, never delivers it an event and discards it (6 times in about 115 restarts), and a constructor counter counted each of those as an attempt.
- **What counts as a restart:** the factory running in a new instance while an *activated* `provisioning` or `running` run has unsettled pi work: its submission (`storage.submissionByRequest(conversationId, "run:<id>")` on the factory's `storage`) is queued or placed, or its session has live tasks (`storage.scanTasks`), background ones included. Queued runs belong to the start protocol: they get no attempt and no marker, and are never submitted to pi before activation. A settled submission with no live tasks is no restart; the run is reconciled from pi's record. PiHarness's own `pending()`, `busy()` and `sessions.list()` cannot be used here: they wait for the open in progress. Controls that must not count, and did not: a turn, idle hibernation and a second turn; an 11-minute tool across 24 alarms; a 150 s model retry handed to the alarm; a redeploy during a turn.
- **The gate's decision**, in one `transactionSync`, then `await ctx.storage.sync()` before `Harness.open`, so a crash right after the gate cannot lose the count: if the deadline has passed, the run ends as `timed_out` ("The run took too long."); if this would be attempt 4, or under 30 s remain, it ends as `worker_exited` ("The worker stopped unexpectedly."); otherwise the attempt is incremented and the restart marker `{status: "provisioning", attempt: N}` appended (then `running` when the loop resumes), before pi does anything. The once-per-instance flag is set only after the decision is committed, so a factory that throws retries the gate on the next event.
- **Stopping pi** when the gate ends a run: after `Harness.open` and before the factory returns, every live task of the run's session, background compactions included, is marked with `pi.abortTask` and queued inputs are withdrawn with `pi.abortSubmission`, all in one synchronous stretch, so the scheduler reserves nothing meanwhile; the abort handlers run after `pi.resume()`. Measured: no tool execution or model call afterwards; the tool result reads "was aborted", the submission ends unanswered, and PiHarness's wake job and alarm are cleared. Deleting the wake job is not a stop (pi resumed on the next request), and `session.reset()` is not either. As a backstop, the model wrapper and the executor refuse calls for runs that are not current.
- **A start that crashed before pi had its input** has no wake-up of its own: a Lifecycle job (`watch:<run>`, 20 s) wakes the object. `this.schedule()` did not fire in the spike.
- **Timing.** The gate costs nothing measurable; recovery waits for PiHarness's 30 s heartbeat (p50 29 s, at most 60 s), so a crash in a run's last minute usually ends it. pi's retry delays stay at or under 60 s, so a long wait is never mistaken for a restart.
- **Deploys** usually leave a busy object on its old code until it is idle, but the platform can reset a busy object on a code update; that counts as a restart, as today ("restarts count whatever the cause").
- **Not covered:** a deterministic crash before the factory (in the Agent's own start-up or `openPiSessionStore`) would repeat without being counted; pi does not run in such an instance.
- Writes the dead instance left `dispatched` are marked uncertain by the gate, in the same transaction as its decision (see Writes); nothing waits in the gate, which runs under `blockConcurrencyWhile`'s 30 s limit.
- **Replay cap:** safe tools are wrapped with a per-call execution counter in SQLite; a call replayed more than twice is answered with an error instead of running again.
- **Fencing:** every asynchronous operation (a tool call, a credential lease, a script and its reset, a sandbox command, a checkpoint, an event append) carries the run id and the attempt it started under, and is refused when either is not current. The one exception is settling a write that an older attempt already dispatched, which is always recorded. The Workspace DO knows runs, not attempts, so the Conversation DO checks a lease's attempt before and after asking for it; the Scripts DO keeps the newest run and attempt it has run a script under and refuses a reset from an older one, since a reset aborts every guest it loaded.

### Writes

The write ledger is today's `RunWrite` protocol, ported to the Conversation DO's SQLite unchanged: the write key (SHA-256 of the label `minerva:write-key:` and the RFC 8785 canonical JSON of the tool and its normalized arguments; query hashes, operation fingerprints and folder-version digests hash the same way under labels of their own, `lib/canonical.ts`) is claimed before dispatch; one write is dispatched at a time per run, with its deadline fixed at dispatch; refused writes are forgotten, applied ones recorded (with `applied_without_result` when the response was unusable), unknown outcomes marked uncertain, which pauses every later write in the run; writes still dispatched 30 s past their deadline are marked uncertain by an alarm. Today a restart waits while a write is dispatched, because the old gateway process may still settle it; here the write was dispatched by the instance that died, which can never settle it, so the restart gate marks every write of the run still `dispatched` as uncertain in its own transaction (as today's supervisor does for writes whose gateway process died), and the new attempt's later writes pause. Deduplication is by key within the run, so it also catches a model that retries an interrupted write under a new pi call id (measured in the spike). A write settles in the DO that dispatched it, under `ctx.waitUntil`, even if the tool call that asked for it was cancelled. A claim and a settlement are made only while no asynchronous transaction of pi's is open on the object's storage: one made inside it would roll back with it, and a claim the executor was told was dispatched would leave nothing for the restart gate to mark uncertain.

### Credentials and refresh

Credentials stay encrypted in the Workspace DO with `MINERVA_ENCRYPTION_KEYS`, as do the secrets of dynamically registered OAuth clients in D1. Step 6b replaced Fernet with WebCrypto AES-256-GCM (`lib/encryption.ts`); instances read neither Django-era nor Fernet ciphertext. A value is one envelope, `m2.<key id>.<base64url(nonce ‖ ciphertext ‖ tag)>`: `m2` is the format version, the nonce 96 random bits, the tag 128 bits, and anything malformed, truncated, re-spelled or of another version is refused. Each purpose (`credential`, `oauth-client`) has its own key, derived from the secret with HKDF-SHA-256 (a fixed salt, `info` = `minerva/m2/<purpose>`). The associated data is the canonical JSON of the format version, the key id, the purpose and the row (a credential's workspace and connection ids, allocated before encryption; an OAuth client's provider, redirect URI and client id), so an envelope copied to another row, workspace or purpose does not decrypt. A derived key is good for at most 2^32 encryptions (random nonces); rotating the key is the remedy. AEAD does not stop an older envelope of the same row from being written back. The credential generation fences that for Minerva's own writes: every write of credentials (a reconnect or a refresh) is a compare-and-set on the generation it read and moves it to the next, so a stale result is discarded (below). Someone who can write the object's storage directly can roll a row back, which no key held beside that storage can detect. Data an instance stored with Fernet is refused with a message to reset the instance's data (a reconnect reads the old credentials first, so it cannot replace them). A refresh is single-flight per connection in memory and fenced by the credential generation in storage:

- Before calling the token endpoint, the DO records `refreshing` at generation g. On success it stores the new tokens as g + 1 and clears the state.
- A `refreshing` state found after a restart means the outcome is unknown: the provider may have rotated the refresh token. The connection becomes `refresh_uncertain`, and the next use makes exactly one refresh with the stored token. If that succeeds, the connection is normal again; if the provider refuses it (`invalid_grant`), the connection is marked "Needs reconnecting". No other request uses the connection while it is `refresh_uncertain`.
- A reconnect or delete during a refresh wins: the refresh's result is discarded when the generation moved.

### Checkpoints

The order from today's LocalCalls invariant, now driven by the Conversation DO:

1. close admission to new local calls; 2. wait for running ones; 3. `cgroup.kill` the agent cgroup and verify it is empty; 4. scan the folder as the dropped user; 5. stream changed files from the container into R2 (the Sandbox DO writes R2 itself, so file contents never cross an RPC, which is limited to 32 MiB) and verify each hash; 6. record the checkpoint for the current attempt on top of its previous one; 7. release the held tool results to pi.

If any step fails, the Conversation DO calls `ctx.abort()` before releasing results, so pi never commits them: the attempt ends, recovery starts the next one from pi's last commit, the held calls come back as interrupted, and the container is replaced from the last checkpoint. This is today's rule ("a failed checkpoint ends the attempt without recording the result").

### The sandbox lifecycle

A Sandbox DO per conversation runs one container per turn: `durable_object` scheduling policy, instance `standard-1` (1 vCPU, 4 GiB; `lite` takes about 100 ms per exec and moves 1–4 MB/s), `enableInternet: false`, and no outbound intercepts, so it has no route out (other ports time out; 80 and 443 accept and then reset). Nothing secret is passed to its environment, since a root process can read PID 1's.

Hardening is a state machine recorded with the container's incarnation id: `starting → hardening → verified → in_use → destroying`. Before `verified`, no agent command or file operation is admitted. One root `exec` runs, with `set -eu`:

1. a tmpfs `/workspace` with `size` and `nr_inodes` set to the folder limits, owned by uid 1000, so a full folder fails with `ENOSPC` at the size the store counts;
2. a tmpfs `/tmp`, `noexec`, with `/tmp/home` and `/tmp/matplotlib` owned by uid 1000 (bash's `HOME` and `MPLCONFIGDIR`);
3. a cgroup `/sys/fs/cgroup/agent` with `pids.max` (256) and `memory.max` set to the base (1 GiB) plus both tmpfs sizes, as today: pages the agent writes to a tmpfs are charged to its cgroup, so with the base alone a growing folder would OOM-kill commands instead of failing with `ENOSPC` at the folder's limit;
4. `mount -o remount,ro /`.

A second `exec` verifies each postcondition (mount options and sizes, `/tmp` not executable, the home directories and their owner, `/` read-only, the cgroup's limits equal to the spec's, that the dropped wrapper reports no capabilities and `NoNewPrivs: 1`). Any failure, or any doubt, destroys the container and fails the turn. A Sandbox DO that restarts never reuses a running container it did not verify in its current incarnation: it destroys it first. If `destroy()` fails, the DO keeps `cleanup pending` and retries on an alarm. Every operation on the Sandbox DO, `destroy` and cleanup included, names the incarnation (and the run and attempt) it is for, and is refused for any other, so a late cleanup from one attempt can never destroy the next attempt's container.

Every agent command runs through one wrapper: `echo $$ > /sys/fs/cgroup/agent/cgroup.procs || exit 125; exec setpriv --reuid=1000 --regid=1000 --clear-groups --inh-caps=-all --ambient-caps=-all --bounding-set=-all --no-new-privs timeout -k 5 <s> bash -c "$0"`, with the command as an argument, never interpolated. `cgroup.kill` replaces today's stray killer and catches `setsid` processes. A kill first closes the gate to new wrapped processes and waits for those already starting to join the cgroup (or fail), so none joins after it was found empty.

**File operations run as the dropped user too.** pi's `read`, `write` and `edit` go through `minerva-fs`, a Python helper on the read-only root, run as `python3 -I -S /opt/minerva/minerva-fs …` through the same wrapper: isolated mode, so nothing the agent writes can change it; paths as arguments, never interpolated; bounded reads. Where a path must stay inside `/workspace` (the scan, hydration, checkpoint reads), it is walked one component at a time with `openat`-style calls relative to directory descriptors, each with `O_NOFOLLOW`, so a symlinked parent cannot lead outside; files are opened with `O_NONBLOCK` and accepted only if `fstat` says regular file. pi's own tools keep pi's semantics for paths the agent names (as today on a laptop), but run without privileges, so a link out of `/workspace` reaches only what uid 1000 may read on a read-only root. Root is used only for hardening, verification and `cgroup.kill`. The SDK's `Files` (which runs as root) is not used on agent-controlled paths.

**The local tools** are pi's own, given an `ExecutionEnv` (`@earendil-works/pi-durable/env`, `FileSystem & Shell`) that forwards to the Sandbox DO; it must pass pi's conformance suite (24 cases). `read` is wrapped to be replay-safe, as today. If the Conversation DO restarts mid-turn it loses its `exec` handles: calls in flight come back as interrupted and the container is replaced from the last checkpoint.

### Code mode

`run_script` keeps its description and its rules, with these measured differences, which the description states: a guest may use about 256 MB (there is no lower setting; today 64 MB), computation is cut by `cpuMs` (30 s, or the wall clock when shorter) a few seconds late, timers exist, and `eval` does not. Each script is a Dynamic Worker loaded with `globalOutbound: null`, no `env` and `limits.cpuMs` by the per-conversation Scripts DO itself, so a CPU-bound script blocks that object, never the conversation. The Conversation DO enforces the wall clock (120 s, cut to the deadline); on timeout, pi's abort or the script's refusals it stops the RpcTarget (later calls get a promise that never settles, so a stopped guest that awaits one stops; past 100 of them more are answered at once, so they cannot fill its memory), lets dispatched writes settle, and the Scripts DO resets itself (`ctx.abort()`) as soon as it hears of the stop, or when its call to the conversation breaks (the conversation is gone). After every script, stopped or not, the conversation resets the Scripts DO with the script's fence, and its next script waits for that reset within its own wall clock, so timers and unawaited work a guest left end and the object's 10 Dynamic Worker slots stay free. The guest's only capability is that RpcTarget, which applies the caps (100 open calls, 256 KB of arguments, stop after 100 refusals, today's output limits) and queues calls with the direct ones; a long output or value crosses as its head and the size of the rest, and the conversation cuts the result exactly as pi would (1 MiB, pi's own note). `@cloudflare/codemode` is not used: its replay re-ran an interrupted write (measured), and its executor's timeout can be switched off by the script. Of the two teardown recipes the spikes found, step 4 measured that only the reset ends a guest that ignores its stop (Step 4 below).

### Events and the stream

Events are appended to the Conversation DO's `run_events` with today's types, payloads and dense per-run sequence numbers; a refused append takes no number. Text and reasoning deltas come from a tap on the provider stream, flushed every 0.25 s per model call with the call's 8-hex id; the restart marker before a new attempt makes the frontend drop the earlier attempt's text, as today. History replay into a run reads our `messages` table (final text and file notes only), never pi's transcript, so pi's aborted partial entries never reach the next turn.

**Reading runs.** Workers RPC refuses arguments and results over 32 MiB, and a conversation's events have no retention yet (open question 5), so no Durable Object method returns more than a page of them: `getConversation`, `getRun` and `cancelRun` return runs without events but with the seq of their last event, read with their status, and the Worker streams the API's body (each run with all its events, as today), paging each run's events with `getRunEvents` up to that seq. Step 5 adds a platform test with a conversation whose events pass 32 MiB.

The browser's `EventSource` connects to the stateless Worker, which checks the session and the run's owner, opens a hibernatable WebSocket to the Conversation DO with `after`, and relays frames (`id`, `event`, one-line `data`, 15 s keepalive comments, `end` when the run is inactive and caught up). The DO sends the backlog and subscribes in one synchronous step, so no event falls between them. Hibernatable sockets outlive the instance that accepted them, and one that died may have committed events it never sent: each socket is tagged with the instance that accepted it, and any other instance never writes to it (no frame, no `end`) but closes it with 1013, as it does every socket it inherited when it starts, so the client reconnects with `Last-Event-ID` and gets what it missed, then `end`.

- **Backpressure:** the DO drops a socket whose buffered amount passes a limit, and the Worker closes the SSE response when its own stream's queue stays full; either way the client reconnects with `Last-Event-ID` and loses nothing.
- **Session during a stream:** the Worker checks the session again every 60 s and on every reconnect, and closes the stream when the session has ended (sign-out, password change, expiry) or the user is no longer a member of the workspace.

## The web API

The Worker implements the JSON API of the web-api spec's endpoint table: paths, status codes, the `{detail}` error shape, the order of checks, and step 1's CSRF check (double submit plus `Origin`) for its own routes, so the frontend's API client is unchanged (one optional addition: `Idempotency-Key` on a message). What was built, its deviations and open items are in Step 5. Accounts and sign-in use **Better Auth** (MIT, version pinned) instead of an allauth-compatible port (decided 2026-10-12): the frontend's auth client and auth pages switch to Better Auth's client and keep their look.

- **Library and storage.** Better Auth 1.7.7 (exact) runs in the Worker at `/api/auth/*` on D1 through its Kysely adapter. Its tables (and its plugins') are created by our D1 migrations from the schema its CLI generates. Plugins: email and password, email OTP (verification, sign-in and reset codes), two-factor (TOTP with backup codes), organization (organizations and members, read-only through the API for now; invitations and roles come with team workspaces) and admin (the instance admin's role only; its endpoints are not exposed); later `@better-auth/sso` (OIDC, SAML) and `@better-auth/scim` for organizations' single sign-on and directory sync. Only the routes in an allowlist (`BROWSER_ROUTES`) reach it, and its own routes check its trusted origin.
- **Passwords** use Better Auth's custom hash and verify with scrypt from `node:crypto` (its default is a pure-JS scrypt, costlier on Workers), in a versioned format (`scrypt$<log2 N>$<r>$<p>$<salt>$<key>`, 16-byte salt, 32-byte key) so parameters can be raised later. Measured in local workerd on Apple silicon on 2026-10-12 (one hash, warm): N 2^14 r 8 p 1 15 ms; 2^15/8/1 30 ms; 2^15/8/2 58 ms; **2^15/8/3 85 to 88 ms (chosen: 32 MiB, under 100 ms)**; 2^16/8/1 63 ms; 2^16/8/2 124 ms. N above 2^15 doubles the memory (64 MiB of the isolate's 128 MiB), so p carries the cost instead. A login with an unknown address must take as long as a wrong password. On the edge the figures are about three times these: one hash alone per request on the test Worker (Workers Logs' CPU time, median of 10; step 7) took 2^15/8/3 about 260 ms (twice: 267 and 259), 2^14/8/5 189 ms, 2^13/8/10 223 ms, 2^16/8/2 307 ms and 2^17/8/1 320 ms. 2^15/8/3 stays: 2^14/8/5 would save about 70 ms by halving the memory, which is what makes a guess expensive in parallel, and the higher N cost more CPU and take half or all of the isolate's 128 MB, shared by concurrent sign-ins (Step 5, Step 7).
- **Sessions** are Better Auth's database sessions in D1 behind an HttpOnly, SameSite=Lax cookie (`minerva.session_token`; `__Secure-` and Secure with debug off), 14 days, extended daily. Each stores a stamp, an HMAC of its user's id, email and password hash, and a request whose session's stamp no longer matches deletes it, so changing the password or an email ends the other sessions in the same statement; our routes read sessions through `currentSession`, which runs that check.
- **Organizations and workspaces.** A sign-up creates, in Better Auth's hooks, a personal organization the user owns and our row for its personal workspace with our membership; the Workspace DO is initialized right after; if that failed, the next sign-in or `/api/me` repairs the organization, membership and workspace (all idempotent), and `/api/me` leaves out a workspace until it is initialized. Workspaces and their memberships stay our tables, keyed by Better Auth's organization and user ids. The UI does not show organizations yet.
- **Email** codes are written to the Worker's logs only when `MINERVA_DEBUG` is true; otherwise they go through the `EMAIL` binding (Cloudflare Email Sending, in beta, from a sending subdomain of the production zone), and `/api` answers 500 without one. The test build has no binding: its emails go to a mailbox the driver reads, for the account tests (Step 5).
- **Rate limits** are Better Auth's per IP (from `cf-connecting-ip` only), stored in D1, with a rule of our own for every route the browser reaches (`src/accounts/ip-limits.ts`; the numbers are under Step 5, follow-ups), with ours per address and per user beside them where today's are stricter (5 failed sign-ins in 300 s, code attempts, resends, resets, password changes).
- **Seed accounts** (`pnpm run seed`, the local `make seed`) are created or reset through Better Auth's API by `POST /api/dev/seed`, which exists only with `MINERVA_DEBUG`.
- Step 5a's allauth-compatible flows, sessions and `auth_flows` were replaced; its scrypt parameters, sign-up provisioning, email sender, seed and per-address limits carried over.

## Files

The store, versions, uploads, downloads and limits keep today's semantics (files spec). What changes:

- **Uploads** stream into R2 while hashing (`body.tee()` into `crypto.DigestStream` and `put`, about 550 ms CPU per 50 MiB). The edge buffers a request body before the Worker runs, so checks before the body cannot save bandwidth; the 100 MiB request limit is above the 50 MB file limit. Sending a message copies its uploads into the conversation's blobs (Starting a run, step 3); the bucket's lifecycle rule deletes every `uploads/` object a day after it was written.
- **Every object is recorded before it is written**, as today's loose objects: the Workspace DO records an upload as `pending` (with its key and a byte reservation against the workspace's quota) before the `put`, and as complete after it; the Conversation DO records a checkpoint blob's key before the Sandbox DO writes it, and claims it when the checkpoint is recorded. Contents the conversation already stores get no key: the Sandbox DO only hashes the container's bytes (`crypto.DigestStream`), as proof the run has them, and the run is granted the stored blob, so nothing is written, recorded or counted against the quota (today's `store_blob` writes nothing for contents it has). Alarms delete pending and unclaimed objects older than an hour and release their reservations, so a crash between the record and the write leaves nothing that is not eventually removed, and counters stay right.
- **Downloads** are links signed with HMAC (`MINERVA_DOWNLOAD_KEY`) over the download origin, workspace, conversation, version, path, user and an expiry of five minutes, served by `minerva-cf-files` on its own origin, which also checks the request's host, with `Content-Disposition: attachment`, `nosniff` and `Content-Security-Policy: sandbox`. Neither Worker has preview URLs: every uploaded version would stay reachable at an origin of its own, with the bindings of its day, and versions cannot be deleted. A link is a bearer capability until it expires: signing out does not revoke one already issued.
- **Encryption.** Blobs use R2's own encryption at first. Per-workspace keys (SSE-C, proven in the spike) are a later step: both Workers then hold a derivation secret and derive the workspace's key; keys never appear in links.
- **Blob keys** keep a random part, so deleting an object never races a re-upload of the same contents.
- **Deletion** of a conversation (or an agent, which deletes its conversations) tombstones it in the Workspace DO and the Conversation DO first, after which both refuse new runs, uploads and object writes; cancels its active run through the revocation outbox and waits for the run to end (its container destroyed and its Scripts DO reset); then deletes the Conversation DO's storage and the R2 prefix, and deletes the prefix again an hour later to catch any write that was already in flight. An alarm finishes an interrupted deletion.

Secrets (`MINERVA_SECRET_KEY`, `MINERVA_ENCRYPTION_KEYS`, `MINERVA_DOWNLOAD_KEY`, `MINERVA_SETUP_KEY`, model keys, connector clients) live in `.env.cloudflare` at the repository root (gitignored, mode 600) and are uploaded with `cf deploy --secrets-file`; they are never printed. Connector clients (`MINERVA_<APP>_CLIENT_ID` and `_SECRET`) are declared only for the apps whose pair is set in that file (half a pair fails the build); an unset app hides its connectors, except Todoist, which registers a client of its own. Removing a pair from the file stops declaring it but does not delete the uploaded secret. `MINERVA_ENCRYPTION_KEYS` is an ordered, comma-separated list of `id:secret` entries: an id of 1 to 32 letters, digits, `-` or `_`, used once, and a secret of at least 32 random bytes in URL-safe base64, padded or not (`pnpm secrets` writes `v1:` and 43 characters; keys written for Fernet are still valid secrets). The first entry encrypts and every entry decrypts, so a key is rotated by putting a new entry first and dropping the old one once no row's key version names it. A malformed entry, a duplicate id or the JSON list Fernet's key ring read is refused with a message saying what to write, by `scripts/secrets.ts check` before a deploy and wherever the Worker first reads the keys. Plain settings (`MINERVA_SITE_URL`, `MINERVA_MODEL_*`, limits, `MINERVA_SIGNUP_OPEN`, `MINERVA_DEBUG`, `MINERVA_EMAIL_FROM`, the sender behind the `EMAIL` binding, which accepts that address only) are text bindings in `cloudflare.config.ts`, checked by the Worker's own parser at build time. Development and tests read them from the environment; a production build reads `.env.cloudflare.vars` alone (gitignored: it names the deployed origins), which must exist, with https origins and debug off, so a shell's `MINERVA_*` (the Django app's names) never reach a deploy. `pnpm run deploy` checks that D1, both buckets (with their jurisdiction and lifecycle rule) and the AI Gateway exist, since `cf deploy` would create a missing one with default settings, and applies D1's migrations before uploading code.

**Local development without an account** (`pnpm dev:offline` in `cloudflare/`, README "Local development"). It runs `vite --mode offline`: the test build's entry with the fake model, `MINERVA_DEBUG` on (emails go to the log), local D1 and R2 under `cloudflare/.cloudflare/state`, no Workers AI or AI Gateway binding and no remote bindings, and the sandbox container only when Docker runs (otherwise the Sandbox class has none and a tool that needs it says so). Its secrets are `cloudflare/.dev.vars` (`pnpm secrets:offline`, gitignored). The mode exists only for the dev server: `cloudflare.config.ts` refuses it unless `vite.config.ts` has marked a serve (`MINERVA_DEV_OFFLINE`), its names are `minerva-cf-dev…` and its D1 id is a placeholder, so it cannot be built or deployed by accident (a source rule in `sources.test.ts` checks).

**First-run setup.** `pnpm secrets` generates `MINERVA_SETUP_KEY` (32 random bytes) with the other secrets; the operator reads it from `.env.cloudflare`. Signed in, `POST /api/setup {"key": …}` makes the caller the instance's first admin (Better Auth's `admin` role, reported as `is_staff`; apart from organization and workspace roles). The claim is one row of D1's `instance_setup`, written with the role in one batch, so it succeeds once; later claims answer 409. On an instance whose sign-up is closed, the same key sent as `X-Minerva-Setup-Key` to `POST /api/auth/sign-up/email` admits the operator's own sign-up until setup is done; the address is verified as usual before sign-in. Instance admins then manage `GET`/`PATCH /api/instance/settings` (`signup_open` overrides `MINERVA_SIGNUP_OPEN`; null follows it) and `GET`/`POST /api/instance/admins`, `DELETE /api/instance/admins/{id}` (the last admin cannot be removed), and remove another user's two-factor with their sessions, `POST /api/instance/users/remove-two-factor`. Rotating the key after setup changes nothing; an instance whose admins are all gone is repaired by setting a user's `role` to `admin` in D1.

### Step 2

Three parts were built in parallel (the executor, the Workspace DO, the Conversation DO with the model wrapper) and then wired together:

- **Wiring.** The Conversation's tools call gateway/'s executor, one per run with the snapshot's deadline and the call's abort (pi's, or the run's end, whichever comes first); a call's `tool_call` event comes from the executor's `settled` callback, so a write sent before pi aborted its call is still recorded with its real outcome. Its write ledger and page tokens live in the Conversation's SQLite (schema step 2) through `lib/sql.ts`, the one SQL interface the Workspace's core, the ledger and every object's schema steps share; the restart gate marks the dead instance's dispatched writes uncertain in its own transaction, and `writes_uncertain` mirrors the ledger's uncertain rows in the same transaction. Every change someone acts on once it is made (a write's claim and settlement, a cancel and its revoked flag, a start, a run's end, the gate's decision, a call's `tool_call` event, the replay cap's count) waits until no asynchronous transaction of pi's is open and is then made with no await after that check (`conversation/store.ts` `outside`); progress (deltas, phases, usage counts) may still join one of pi's, and is dropped with it unannounced. The CredentialPort leases from the Workspace over RPC with the attempt checked before and after, and decrypts for the one call. Both objects reach each other only through `addressing.ts` (an EU workspace's pair stays in its jurisdiction; a platform test checks the local seam). One connector registry (`src/connectors/`) serves the Workspace's snapshots and the executor. ### Step 3

The sandbox (`src/sandbox/`, `container/`) and the files (`src/files/`) were built in parallel and wired into the Conversation DO together with code mode (Step 4):

- **The sandbox.** The image is today's worker image without Node (Debian bookworm-slim pinned by digest; worker/python's requirements installed from hashed wheels; `minerva-fs` and the probe under `/opt/minerva`). `minerva-fs` runs as uid 1000 behind the wrapper: a long-lived `serve` process answers single file operations (a fresh interpreter took about 105 ms each), `pull-many` and the hydration stream carry whole folders, and the scan follows today's manifest policy over directory descriptors with `O_NOFOLLOW`. Blobs move directly between R2 and the container, each put with its length and the SHA-256 R2 checks, within the six connections an invocation keeps. `env.ts` is the `ExecutionEnv` (pi's path resolution and argument checks, output through an RpcTarget sink, `watch` by polling every 250 ms over at most 10,000 entries) and passes pi's conformance suite, 24 cases, locally and on the account.
- **The files.** `manifest.ts` and `store.ts` (`FolderStore`) keep versions in the Conversation DO's SQLite as canonical text in parts under 2 MB, with today's validation order, messages, kinds and lineage, warnings, codes (`stale`, `conflict`, `invalid_manifest`, `unknown_blob`, `quota`) and `folder_changes`. Attachments are copied into numbered names at the folder's root with the limits checked first. `uploads.ts` streams the body into R2 hashed; `links.ts` and `download.ts` sign and serve the download links from `minerva-cf-files`. The sweep deletes loose keys an hour old and repeats every deletion a day later. - **Wiring.** `read`, `write`, `edit` and `bash` come after `run_script` (`local.ts`, `local-run.ts`). Each attempt starts, hardens, verifies and hydrates its container when it begins; every result of a call that may change the folder is held until the checkpoint barrier of Checkpoints (all seven steps) has saved it (a batch of reads alone saves nothing: the folder is as it was saved); a watchdog ends a call that does not settle (and the attempt, when the Sandbox's kill for it does not answer within 30 s); a failed step calls `ctx.abort()` before any result is released, so the attempt ends and the next one starts from the last checkpoint; a container that failed its hardening or checks fails the turn as `worker_failed`, and a folder over its limits as `folder_limit`. The turn's last checkpoint, when a call that may change the folder ran, rehashes every file; the folder version is published in the run's end transaction, and the container is destroyed after it (a failed destroy is a `sandbox` job, and the next start finishes an ended run's). A folder over its limits ends the run as `folder_limit` with that limit's message: the end and its clean-up jobs are one transaction, made durable (`storage.sync()`) before the object resets, or the restarted object continues the run (a platform test fails without it).
- **Tests.** Local: the platform tests of the local tools and of every checkpoint fault point (`test/platform/local-tools.test.ts`, `sandbox.test.ts`, `files.test.ts`), the Docker-backed tests (`pnpm test:docker`, after `pnpm sandbox:image`). Deviations from the protocols above, and why:

- **No final checkpoint after a restart past pi's last commit.** An instance that has no `LocalRun` for the attempt (the object restarted after pi settled the turn, while the final checkpoint ran or after it failed) saves nothing: its container is replaced, and since every result pi recorded was released only after a checkpoint saved it, the run's last checkpoint is the folder as the turn left it, except for a change only the rehash would find (same size and mtime). Today's worker did the same: the next worker's `LocalCalls` had admitted no call, so `finish` saved nothing.
- **A preparation still running when the model answers is not awaited.** A container that fails its hardening or checks fails the turn at once as `worker_failed` when it is known before the answer or when a local call meets it. A turn without local calls whose container fails after the model has answered completes: no agent code ran in that container, and waiting would add the container's start to every such turn. The container is destroyed with the run's end.
- Output after a command exits is read for at most 10 s (time spent waiting for the caller does not count), so a detached writer cannot hold its call; its later output is dropped, where pi would wait for it.
- Reads are bounded: `readTextFile` at 8 MiB, `readBinaryFile` and a single read at 16 MiB, `listDir` at 100,000 entries; today only Node's 2 GiB applied. `watch` polls every 250 ms.
- The agent (uid 1000) can kill or stop its own helper processes (readers, the file server, the spill); calls then fail or time out, which is not treated as losing the sandbox. The folder steps of a checkpoint run after `cgroup.kill` and are not exposed to it. Argv execs check existence and the execute bit as root, so a file only root may run exits 126 instead of failing at spawn.
- Scan names are checked for NFC with Python 3.11's tables (Unicode 14) and validated by the Conversation with V8's ICU: a character assigned after Unicode 14 could pass the scan and be refused as `invalid_manifest`.
- Uploads: the Workspace's refusals (3 arriving, 30 waiting, the quota) come before the body is received, where today the last two came after it; the per-process caps (32 uploads in flight, 4 downloads per user) have no counterpart; the 15-minute deadline's abort is best effort, which the edge's buffering makes moot. On the download origin a non-GET request is 404 (today 405) and single ranges are served as 206.
- A checkpoint charges the run its planned upload bytes in full before uploading, even if fewer arrive, since the attempt ends in that case anyway. There is no counterpart of today's `files_reconcile --storage`, a sweep that lists a conversation's prefix for objects no row names (only deleting a conversation lists it); the counters are absolute totals and need no reconcile.

Found on the way:

- R2 response bodies opened more than six ahead lose bytes: the platform cancels responses beyond the six connections an invocation keeps, so transfers stay within six. One at a time a put takes 221 ms and a get 146 ms (100 KB, EEUR bucket); six at once 36 and 18 ms; there is no gain at 8 or 16.
- A deploy builds and pushes the image (17 to 75 s). Idle containers were gone well before their hour-long lease after redeploys that changed the image; whether such a deploy stops a running one was not isolated.
- A write that lands more than an hour after its key was recorded, past the sweep's first deletion, is uncounted and stays until the second deletion a day later, so every writer must give up well within the hour. `setConversationBytes` had no order fence (a report sent by an instance that reset could land after the next instance's and stay wrong until the conversation's next change): each report now names a revision, one above the last, written before it is sent, and the Workspace ignores one no newer than a report it has seen (closed after the steps 3/4 review).
- Where an EU workspace's container runs was not measured (Open questions, 8).

Open performance item: **checkpoints and hydration of many small files.** A folder of 50 MB in 500 files takes 16.5 to 18 s to checkpoint when every file changed, and 14 to 15.5 s to hydrate (the Worker's own puts of the 500 objects, six at a time, take 20 to 22 s), while its first scan takes 110 to 125 ms. Per-file R2 round trips dominate (about 30 to 40 ms a file, bounded by the six connections), so the cost grows with the number of changed files, up to the limit of 10,000 entries, and every turn hydrates the whole folder again. The likely remedy is to pack the changed small files of a checkpoint (and the hydration stream's reads) into a few objects, one per checkpoint, with each blob addressed by key, offset and length that R2's range reads serve; a checkpoint then costs a handful of puts instead of one per file. Warm containers (Open questions, 2) would avoid hydrating every turn but not the checkpoint, and fanning out over several invocations is bounded by the same connections. A decision is due before folders of thousands of files are expected.

### Step 5

Done 2026-10-12 on `cf-5`, units 5a2 to 5f, and deployed to `minerva-cf-test` only (production waits for step 7). A first design, an allauth-compatible port (5a) with a hand-written two-factor flow (5b), was replaced by Better Auth before it shipped. What was built (`src/accounts/`, `src/api/`, migrations 0003 to 0006):

- **Better Auth 1.7.7**, exact, MIT, telemetry off, with its CLI `auth` 1.7.7 (`@better-auth/cli` stopped at 1.4.21). It is the newest stable of 2026-09-30: it fixes a critical Magic Link takeover (not enabled here), 1.7.6 fixed D1 schema validation, and the SSO and SCIM advisories were fixed in 1.7.3, so those packages are pinned at the same version when they come (advisories read through 2026-09-30). It brings its own zod 4.5; ours stays 4.3.6. D1 runs through the adapter's own dialect, with transactions off.
- **Migrations.** 0003: Better Auth's tables as its CLI generates them (plus a unique (organization, user) on `member`); `workspaces` rebuilt with a required organization and `personal_owner`, both RESTRICT (deleting a user or organization that has workspaces fails until a deletion protocol cleans the objects and R2); `memberships`; `oauth_flows` keyed by session. It also carries a database of the replaced 5a over (users, hashes, organizations, workspaces; tested with seeded rows). 0004: `session.credentialStamp`. 0005: `totp_steps`. 0006: `instance_setup` and `instance_settings`. A test checks D1's columns against the CLI's schema.
- **Credential stamps.** A session stores an HMAC of its user's id, email and password hash from when it was made. `handleAuth` and `currentSession` delete any session a request names whose stamp no longer matches, so a password or email write ends older sessions in the same statement, whoever wrote it (a reset, an admin, the seed) and whatever crashes after it. A rehash moves the stamps in its batch, and a password change is `UPDATE … WHERE password = <checked hash>`, so a reset in between is never undone.
- **Two-factor on every first factor.** Better Auth's two-factor hook is re-matched to password, email-code and verify-email sign-in (the wrapper throws if 1.7.7's single hook changes). For a two-factor user the first factor makes only an expired placeholder that the hook deletes before answering, so no usable session exists until the second factor (a TOTP or recovery code, with the `minerva.two_factor` cookie for 10 minutes). Trusted devices are off.
- **The browser allowlist.** Only routes in `BROWSER_ROUTES` reach Better Auth; the rest is our 404 (no admin endpoints, invitations, email change, delete-user, update-user), and a new route needs an entry. Users come only from sign-up while it is open, our server code and the setup key; sessions only from first factors with a verified address, second factors with a matching challenge, or a holder's replacement. Bodies are read capped (413) and refused with keys outside `[A-Za-z0-9_.:-]` (the runtime's JSON key bug); our CSRF token exempts only the auth route, which checks `Origin` against the one trusted origin.
- **TOTP steps are used once** (`totp.ts`): the latest step of the code in Better Auth's ±1 window is claimed by a conditional upsert before the code is checked, a used or older step is 401 `INVALID_CODE`, and a session from a code that claimed nothing is refused.

- **Rate limits per IP** (done; `src/accounts/ip-limits.ts`, tested in `accounts-ip-limits.test.ts`). Better Auth's defaults (3 per 10 s on sign-in, sign-up, change-password and every two-factor route, 3 per minute on the code routes) stopped people: four wrong codes in 10 s, or a few colleagues signing in at once behind one address, got a 429. Every route in `BROWSER_ROUTES` now has a rule of its own, and a test fails when a route has none. A rule is `max` requests in a row, each less than `window` seconds after the one before (Better Auth's database storage, keyed by `CF-Connecting-IP`, IPv6 by its /64, and the path); a refused request counts for nothing, so a client that hammers is refused until `window` seconds after its last allowed request, then gets `max` more (`X-Retry-After` says how long).

  | Routes | Window | Max |
  |---|---|---|
  | `GET /get-session` | 10 s | 300 |
  | `POST /sign-out`, `GET /organization/list`, `GET /organization/get-full-organization` | 10 s | 100 (Better Auth's default) |
  | `POST /sign-in/email`, `/sign-in/email-otp`, `/email-otp/verify-email`, `/email-otp/reset-password`, `/change-password`, and the six `/two-factor/…` routes | 10 s | 10 |
  | `POST /sign-up/email`, `/email-otp/send-verification-otp`, `/email-otp/request-password-reset` (they send mail) | 60 s | 10 |

  The IP rules are a brake on volume (and on the Email Sending quota), not the guard against guessing, which does not depend on them: 5 failed sign-ins per address in 300 s (ours), 3 attempts per email code and 3 codes per address per minute (ours), Better Auth's lockout of a user for 15 minutes after 10 failed second-factor codes, 5 attempts per second-factor challenge, a TOTP step used once, and 5 password changes and 10 password re-checks per user per minute (ours). Tests: a person's pace passes (eight wrong passwords, six wrong codes, 150 session reads, ten code requests and ten sign-ups), a burst is refused (the 11th password, the 301st session read, the 11th code request, the 11th code or second-factor check), another address and another path are unaffected, and the per-code and per-challenge budgets hold from many addresses. A wide NAT is the cost of any per-IP rule: ten sign-ins in a row from one address, then a wait of up to 10 s. The count is not a rolling window: Better Auth restarts it only when a request comes `window` seconds after the last one it allowed (a refused request does not move that time), so a steady trickle fills it too: a code request every 30 s is refused at the 11th, five minutes in, until a minute after the 10th; a busy office behind one address gets a 429 for up to `window` seconds after every `max` requests in a chain. Accepted: the frontend does not poll the session (it reads it where it needs it, `frontend/src/lib/auth.ts`), and the real brake on volume is Cloudflare's own rate limiting at the edge, which this does not replace.

- **Durable Objects.** The script deploys `reset-worker/` as the instance's Worker: 503 to everything, no binding, and every class of the app's build as an `exports` tombstone (`state: "deleted"`), the supported way to delete classes declared through `exports`. Cloudflare deletes each namespace with its objects' storage and alarms, EU included; the script waits until none is left, then deletes the container application, which stays linked to the retired Sandbox namespace and would fail the next deploy.
- **R2.** Each bucket is emptied by paged deletion (`static/` included), deleted and created again with the same jurisdiction, location and storage class and exactly the rules of `r2-lifecycle.json`.
- **D1.** Deleted and created again empty (`weur`, no replication): every table, `d1_migrations` included.
- The next deploy applies the migrations from empty and creates every class afresh. Earlier Worker versions point at namespaces that no longer exist, so no rollback crosses a reset. More generally, a class created, renamed or retired changes the namespaces, and an earlier version cannot bring back a retired namespace or its storage: code and settings can be rolled back, a change of the classes cannot.
- Deleted: the test instance held 787 Durable Objects, 70 R2 objects (all under `blobs/`) and the rows of 32 test users; production held 8 Durable Objects (2 in each of four classes), no R2 objects and 14 empty tables from before 6b.

**The deploy scripts** (`scripts/deploy.ts`: `pnpm run deploy`, `deploy:test`, `deploy:files`; README "Deploy"). One run at a time, and one account for every `cf` command. Everything that can fail locally fails before the account changes:

- **Locks and account.** An atomic lock with the process id, shared with reset (both build into `.cloudflare/output/`); a lock left by a run killed outright is never taken over. The account is `CLOUDFLARE_ACCOUNT_ID` or the only one `cf` reaches; a `.env` that sets a `CLOUDFLARE_` variable stops the run, and a build that names another account stops the deploy. Ids and the account's subdomain are hidden from everything printed.
- **Before anything changes.** The secrets check (`scripts/secrets.ts check`: present, encryption keys in a format the Worker reads, a setup key of at least 32 characters, since a shorter one cannot claim setup); the app's build; the bundle check (the test build's code is absent from production and present in the test build); the download origin's build checked against the app's (its name, exactly the app's buckets, each the instance's own, the same download origin, `MINERVA_DOWNLOAD_KEY` as its only secret), so a test build that would reach production's Worker or buckets, or the other way round, stops here. Digests of both outputs are taken right after each build and checked again before each upload; symlinks in an output are refused.
- **Then, in order.** The resources check, which stops while either bucket lacks either lifecycle rule (`uploads/` after a day, `static/` after 30 days; `resources.ts --check` checks without changing); D1's additive migrations, the first change on the account; the schema check (exit 1 on drift, 2 when the database cannot be read); the app's upload with the secrets file only if unchanged since its check; the download origin's upload, with the link key written to an owner-only file in a fresh directory that is removed on success, failure and interrupt.
- **A partial deploy** (the app uploaded, the download origin not) is finished by `deploy:files`, which refuses unless the live app is the version this checkout recorded (`.cloudflare/deployed.json`, a digest of the link key) and has the local build's buckets and download origin. A failed app upload leaves the previous version serving with the new migrations applied, which it tolerates. Residual: a `cf build` run by hand between the final digest check and `cf` reading the output.

### Dates, text and numbers

Steps 6b5 and 6b6 settled these by keeping Python's rules: one port of CPython's `fromisoformat`, Python's zone list, its casefolding, whitespace and digits over the runtime's Unicode tables, and Pydantic's strict and lax readers. The cleanup (units 1 to 5) replaced them: `lib/dates.ts` reads RFC 3339 by a strict pattern, checks the calendar fields, reads an offsetless time as UTC (never in the runtime's zone) and checks IANA zone names with `Intl.DateTimeFormat`; Slack's `ts` stays an exact decimal string, converted through BigInt; text uses the runtime's string methods; tool inputs are strict zod objects and provider answers zod schemas, with no coercion (`z.coerce` is refused by a source rule). Two rules from then stand: identifiers are never normalized with NFKC or NFKD, which join text that should stay apart (NFKC only to refuse or redact, NFC only for file names and manifest paths; `sources.test.ts` checks), and decimal amounts stay their text (`xero/decimal.ts`, `stripe/money.ts`), never floats.

Measured on the account (Workers Paid, Frankfurt), with `cf` 1.0.0-beta.13, its `cloudflare.config.ts` format and Vite. All spike resources were deleted (one container snapshot expires by itself). Full reports are kept outside the repository.

| Spike | Result |
|---|---|
| PiHarness | Worked with pi-durable 1.1.0 and 1.0.3. Two reads in parallel then a write, from one prompt; idempotent submit; steer and follow-up; recovery after `ctx.abort()`, memory-limit resets (7 in a row, no cap) and an interrupted model stream, each about 30 s later; a redeploy mid-turn interrupted nothing; a 17-minute tool call completed. After an interrupted write, the model retried it under a new call id. First text delta 2–4 s after submit. pi-mcp works; pi-codemode does not (no `worker_threads`). `contextRetentionMs` must be 0, or every object stays active 10 minutes after each turn. |
| Sandbox | A Firecracker microVM (KVM, kernel 6.18). | Storage and realtime | Request bodies up to exactly 100 MiB, buffered by the edge before the Worker runs. Upload hashing with `tee()` and `DigestStream`: 550 ms CPU per 50 MiB. Static assets with an SPA fallback and the Worker first for `/api/*`. |

Consequences for the design:

- The Web connector keeps its URL and host policy and its same-host redirect rule; the DNS-pinning guard against private networks becomes the platform's refusal, which the connector must recognise (a 403 from `server: cloudflare`) and report as today. That refusal is measured, not documented, so step 6 adds adversarial tests (rebinding names, `nip.io`, IPv6 encodings, redirects to private addresses) against the deployed Worker. It comes in two forms. A request with an empty Accept header gets the text `error code: NNNN` (1003 for a private, loopback, link-local or non-Cloudflare IP literal, 1002 for a name that resolves to a private address, 1102 for loopback names such as `localtest.me`). A request with any Accept header, which the Web connector always sends, gets Cloudflare's HTML error page instead (text/html, about 6.5 KB, headed `Error` and the code; measured: 1002 for a name that resolves to a private address, 1102 for `localtest.me`), found in step 7 on the account: the connector read only the text form and a 1 KB prefix, so private sites were reported as "HTTP 403" until `platformRefusal` read both forms (Step 7).
- **Versions.** Busy objects keep their old code for minutes after a deploy and new objects may start on the previous version, so two versions run side by side: Durable Object storage changes are additive only, code accepts rows written by the previous and the next version, and a changed tool still fails through its fingerprint (`OPERATION_CHANGED`).
- `/assets/<missing>` would get the SPA shell, cached as immutable by the `/assets/*` header rule; the Worker therefore runs first for `/assets/*` and answers a miss with today's 404 (`no-store`).
- The sandbox checks are reworked for this platform (no loopback-only check; network checks over HTTP and TLS, not TCP connect) and run against the deployed Worker.
- A deploy usually reaches a busy object only once it is idle (and may reset it, which counts as a restart), so revocation, policy and security fixes can never rely on a deploy reaching running turns.
- **JSON keys** (found in step 1, in Node 24's V8, in workerd 1.20261006.1 and on the deployed Worker): after any JSON text with the key `"\\"` was parsed in an isolate, a later key written with an escape in the same place (`"\n"`, `"\u00e9"`) comes back as `"\\"`. `JSON.parse`, `Response.json()` and Hono's `c.req.json()` are affected, values are not. The state is per isolate, so one tenant's input could change another's parsed keys and the hashes over them; every port parses JSON with `lib/json.ts`'s `parseJson`, a unit test refuses `JSON.parse` elsewhere in `src/`, and a platform test and the deployed probe keep the bug visible until the runtime is fixed. Still to be reported upstream.

## Open questions

1. Move the executor and the decryption key to a separate Worker script with its own secrets, so the loop's isolate never holds a credential?
2. Warm containers: keep a conversation's container between turns for its idle timeout, or start one per turn as today?
3. pi's state grows with every run (a new session each), and PiHarness cannot delete conversations yet. How large does it get, and does `reset()` or a periodic compaction bound it?
4. A team's Workspace DO serializes its control plane (grants, refresh, run registry). What throughput and revocation fan-out does one object sustain?
5. Retention: run events, the write ledger and page tokens grow with every turn (today without a retention period too). Pick limits per conversation, and measure whether a very long turn approaches the 10,000 subrequests of one invocation (not tested in the spike).
6. Email Sending is in beta and limited to 1,000 messages a day; a provider API may be needed for production.
7. Compliance scope: Containers, Dynamic Workers and Secrets Store are missing from Cloudflare's published SOC 2 and HIPAA lists.
8. Residency of an EU workspace beyond its Durable Objects and bucket: where its container's VM runs (no placement constraint for `durable_object` scheduling), where Workers AI and AI Gateway process its prompts, and its users' accounts, which live in the one D1 database (location hint `weur`, not the EU jurisdiction D1 also offers).
9. **Later, not in the current steps (to be designed in the coming weeks): queries across objects.** Durable Objects cannot be queried together, so operator dashboards, admin search and analytics across conversations and workspaces need their own path. The direction: indexes kept in the objects where the product needs them (the conversation list already lives in the Workspace DO), and an append-only export of events to R2 through Cloudflare Pipelines (Iceberg, queryable with SQL), which would also feed the audit log.
10. **Later, not in the current steps (to be designed in the coming weeks): search.** SQLite's FTS5 works within one object only. Full-text search across a workspace needs an index in the Workspace DO, or Cloudflare's Vectorize or AI Search, which also covers semantic (vector) search; pgvector, which ARCHITECTURE.md planned for later, is not available.
11. **Carried over from the agent files plan** (removed 2026-10-13; ARCHITECTURE.md section 7 describes what it built). Open: whether a per-agent switch for commands (`bash`) is needed at launch, and whether file names with format characters (bidi overrides, zero-width) are refused or only escaped where the app shows them. Its later phases, still intended:
    - images to the model as blob references the model wrapper inlines, re-encoded on upload without metadata, never stored as bytes in pi's state or the run's events;
    - connectors that upload files by path (Drive and OneDrive first, then mail attachments in Gmail and Outlook, and Slack files), each with its own permission checks;
    - warm sandboxes (open question 2), lazy hydration of large files, zip downloads, previews of raster images, project folders that several conversations start from, and branches when a user edits an earlier message.

    Its questions about Django's store (the blob sweep's cost at scale, a whole manifest written per checkpoint) do not carry over: the instance keeps folder versions in the Conversation object and cleans up with alarms.
