# Plan: self-hosting and Minerva Cloud

Superseded 2026-10-14 by [product-and-engine.md](product-and-engine.md): Laravel holds all durable state and the Cloudflare code only executes runs; self-hosting, the hybrid and cells are dropped for now. Kept as the record of the reasoning, and for the parts the new plan names.

Status: research, 2026-10-13; revised 2026-10-14, when accounts and administration moved to Laravel (Decisions). Of Part 1, unit 2 is built; nothing else is. This plan takes over step 8 of [cloudflare.md](cloudflare.md) (self-hosting) and adds what Minerva Cloud needs. Its Decisions replace cloudflare.md's "Instance and control plane" section, which still describes the earlier line (everything a company needs in the instance, accounts through Better Auth). opencode reviewed the first draft, the 2026-10-14 revision in five rounds and once more in a fresh session; its findings are folded in, except that production, which holds only the operator's test data, is still reset. After the fresh review the order became hosted-first (2026-10-14): self-hosting's units wait until after the hosted beta.

## Goals

- **Minerva Cloud first.** A hosted product: a Laravel application for accounts, organizations, billing, policies and administration, and Cloudflare as the runtime that runs the agents.
- **Enterprise in its own infrastructure, later.** First the hybrid: our Laravel, the runtime in the customer's Cloudflare account, so their credentials, conversations and files are stored there and nowhere else. Models and providers still process what a turn sends them, and our Laravel still decides who may sign in (Decisions 9). A fully separate deployment, Laravel included, only when a contract requires it.
- **Self-hosting, lesser.** A company deploys the runtime alone into its own Cloudflare account, behind Cloudflare Access, with one setup command. It gets agents, connections, grants and files, but not organizations, invitations, billing or the administration pages, which are Laravel's. Accepted 2026-10-14, and built after the hosted beta; until then the runtime keeps its seams (one directory interface, named instances).

## Decisions

Decided 2026-10-14, replacing the earlier Decisions 1 to 3 (one identity in the instance, entitlements as quotas with the control plane as one more writer, the instance working without the control plane) and Better Auth in the runtime.

1. **Laravel owns identity and administration; the runtime runs agents.** Accounts and administration interfaces are solved problems in Laravel and are not rebuilt in Workers.

   | Laravel (private repository, Laravel Cloud) | The runtime (`cloudflare/`, this repository) |
   |---|---|
   | Users, sign-in, two-factor, passkeys, verification, password reset | Checking access tokens from one issuer: Laravel or Cloudflare Access |
   | Organizations, members, invitations, roles, team workspaces and who belongs to them | Workspaces as the runtime needs them: id, jurisdiction, kind, members and roles, as Laravel pushes them |
   | SSO and directory sync | Connections: OAuth flows, encrypted tokens, refresh, the tenant of each connected account |
   | Plans, billing, entitlements | Grants and ceilings, agents, conversations, runs, files, the sandbox, scripts, search |
   | Connection policies: connectors offered, allowed tenants, action caps for the organization | Enforcing the policies, quotas and entitlements pushed to it |
   | The operator admin; search across organizations; usage | Usage records and connection metadata, reported to Laravel |
   | All email | No email |

2. **Laravel never stores provider tokens or conversation content.** Tokens are used on every tool call and refreshed in the Workspace object; the grant editor needs them to list a user's calendars or folders. Content includes conversation titles. Laravel receives ids, counts, usage and connection metadata, by a field list the management API fixes (provider, tenant id, status, and a label only where the label is the account's own address or name), never resource names, recipients or anything a user typed. The same holds for its logs, queues and Nightwatch. This means a leak of Laravel's database or logs exposes no customer's accounts or content, and it makes the hybrid possible. It does not contain a compromise of the running application: Laravel decides who is who, so a compromised Laravel can sign in as any user and change memberships and policies. Laravel's security is the product's.

3. **Standard OAuth between the two, from established libraries.**
   - Laravel is an OAuth 2 authorization server through Passport (first-party, built on The PHP League's `oauth2-server`). Access tokens are RS256 JWTs living about 10 minutes (`Passport::tokensExpireIn`); refresh tokens rotate.
   - The runtime's Worker is a confidential client of it (a backend for frontend, as the IETF's "OAuth 2.0 for Browser-Based Applications" recommends), with `oauth4webapi`, already a dependency, and checks access tokens with `jose` against Passport's public keys. Passport publishes no discovery document or JWKS and puts no `iss` or `kid` in its tokens, so the authorization server's metadata and the keys are configuration. Since tokens carry no `kid`, a rotation tries each configured key, newest first: a new key is configured in every cell before Laravel signs with it, and an old one is removed once its tokens have expired. The Worker requires, not merely checks when present: RS256, its own client id as the audience, `exp` and `nbf`, the generation claim (below), and a subject that names a user in the runtime's directory. Stock tokens of a grant without a user carry the client id as their subject, so Laravel's client allows only the authorization-code and refresh-token grants, and a test proves the others are refused. `oauth4webapi`'s own validator for JWT access tokens expects RFC 9068's profile, which Passport's tokens are not, so `jose` checks them.
   - A browser session's tokens live in a Session object, one Durable Object per session, encrypted like connections' tokens; the browser holds only an HttpOnly cookie with the session's id, which `EventSource` sends (it cannot send headers). **Every authenticated runtime request, streams and downloads' link signing included, goes through a live Session object; nothing accepts a bare access token.** That is what makes signing out effective, since Passport's revocation lives in its database, which an offline check never sees.
   - Refresh follows the connections' refresh states (`refreshing`, `refresh_uncertain`; cloudflare.md, Credentials and refresh): one refresh at a time, its result fenced against a session generation, so a sign-out during a refresh is not undone by the refresh's late answer. A refresh whose answer was lost means signing in again, since Passport has already invalidated the old refresh token. A session ends at an absolute lifetime however often it refreshes.
   - The access token says who the user is and how they signed in (password, social, passkey, or SSO with the organization it was for), nothing else. Membership and roles are pushed by Laravel to the Workspace objects. A workspace of an organization that requires SSO refuses a session whose sign-in was not that organization's SSO, so a password session cannot reach it. A removal follows cloudflare.md's strict revocation: the Workspace object's transaction is the commit point, it stops the user's running turns through its outbox, and Laravel shows the removal as pending until every affected workspace has acknowledged. A provider request already sent may still complete.
   - While the management channel is down, a removal is not enforced: Laravel retries without pause and alerts an operator after five minutes, and the operator can suspend the organization in the cell directly, by the emergency command. Until the removal arrives, the removed member's existing session keeps its old memberships, open streams included. This weaker guarantee is stated to customers; a membership lease that fails closed is open question 14.
   - Revoking a user (password reset, suspension, deprovisioning, signing out everywhere) starts in Laravel: in one transaction it deletes the user's Laravel sessions, revokes their Passport tokens, refresh tokens and unused authorization codes, raises the user's generation, and writes the outbox row that tells the runtime. A request to Passport's authorization or token endpoint that began before that transaction may still finish after it, and a credential it creates may be exchanged again later; no timing rule closes such a chain. So every credential carries the generation of the sign-in it descends from, never the generation current when it is issued: a Laravel session records the user's generation when the user authenticates, an authorization code takes it from that session, refresh tokens and access tokens take it from the code or refresh token they were exchanged for, and the access token carries it as a claim. Passport refuses a code or refresh token whose generation is not the user's current one, and the runtime, which receives the current generation through the management API, refuses an access token whose generation is lower, at admission and at every refresh. Anything descending from a sign-in before the revocation is refused however late it arrives; a new sign-in starts a new lineage, and a suspended user cannot start one: every way into Laravel (password, Socialite, passkey, SSO, a remembered session, account recovery) checks the account's status. Carrying the generation through an exchange extends Passport beyond configuring it: custom models for codes and refresh tokens are supported, but its token factory sees the user, scopes and client, not the credential being exchanged, so the lineage has to be threaded through its grant handling and serialized into the access token. That is security-sensitive integration code with an upgrade burden on every Passport release; open question 13, settled by the spike that starts unit 3b.
   - A Session object serves only once it is registered in the user's index in the runtime's D1, by a conditional write that succeeds only while the token's generation is the user's current one. A revocation raises the generation in the same database, then ends every registered session. D1 orders the two writes, so a session racing a revocation is either registered first and ended, or refused. A Session object without a registration, or a user without a generation, is refused.
   - Signing out in the app ends the Session object, then Laravel's session; ending only the runtime's would sign the browser straight back in through Laravel's. Laravel's sign-out route is one the Worker handles first: it ends the Session object, then forwards the request. Signing out everywhere is a user revocation. The interleavings (an exchange, a refresh and an authorization each racing a revocation, and chains of them) are acceptance tests of unit 3b and Part 3's unit 1.
   - Self-hosted, the same check runs against Cloudflare Access's published keys and its `Cf-Access-Jwt-Assertion` header, without a Session object (unit 3a).
   - The existing CSRF check (`http/csrf.ts`: an unsafe request must carry the site's `Origin`) stays for the runtime; Laravel keeps its own CSRF protection for its routes; the OAuth callback is a GET checked by its state.
4. **One origin, with the Worker in front.** `app.minervacomputing.com` routes to the runtime's Worker, which serves the SPA and `/api` as today and forwards Laravel's paths (sign-in, `/oauth`, the account, organization, billing and policy pages) to Laravel Cloud unchanged. There is no CORS, both cookies are first-party, and run streams never pass through PHP. When Laravel is down, its pages and new sign-ins fail; running conversations go on, and a signed-in browser keeps working until its access token needs refreshing.
   - One origin is one browser trust boundary: script on a Laravel page can call `/api` with the runtime's cookie, as the SPA can. This is accepted, and Laravel's pages are held to the SPA's standard (no third-party script, a strict Content Security Policy on both).
   - The forwarding is an allowlist of paths and methods, never "everything else". It forwards Laravel's own cookies and drops the runtime's session cookie and any `Authorization` header; it replaces the forwarding headers rather than passing the client's; it follows no redirect itself (`redirect: "manual"`), so a redirect cannot carry headers to another host; it keeps every `Set-Cookie`; and nothing it forwards is cached. Laravel trusts only the Worker as a proxy, and the Worker authenticates itself to Laravel (a shared secret header), so the application's own Laravel Cloud hostname refuses direct traffic, except Stripe's and WorkOS's webhooks: those have routes of their own on that hostname, which take no browser session, check the provider's signature over the raw body, and record each event's id so a repeat is processed once.
   - Only Workers we control forward to Laravel. A hybrid cell's Worker does not (Decisions 9).
   - A prototype of this forwarding, with Laravel Cloud, comes early in unit 3b, before anything depends on it (open question 2). It exercises more than sign-in: Laravel Cloud's own edge, cache and firewall (nothing cached at either edge), canonical URLs and signed verification links, Socialite's and WorkOS's callbacks, passkeys' origin, several `Set-Cookie` headers, assets, Inertia's navigation and the webhooks. The two applications' cookies and asset paths have namespaces of their own, and the Worker's authentication to Laravel is checked before any route that can issue a browser credential.
5. **Laravel's pages are Laravel's.** The account, organization, member, billing and policy pages are rendered by Laravel with Inertia and React, styled with the Ledger components (open question 6). The SPA links to them and keeps only what self-hosting has too, so the public repository has no pages for features only the cloud offers. Considered and not chosen: SPA pages calling Laravel's API through Sanctum, which puts the cloud's pages in the public repository and two backends behind one SPA.
6. **Laravel's packages.** Fortify (sign-in, two-factor, passkeys, reset, verification), Passport, Socialite (signing in with Google and GitHub; Microsoft needs the community SocialiteProviders adapter), WorkOS for enterprise SSO and directory sync (the integration Laravel's starter kits ship), Cashier (Stripe), Pennant (entitlements that are on or off; numeric quotas go through the management API, not Pennant), Filament or Nova for the operator admin (open question 7), Nightwatch, and Laravel's queues and scheduler, with a worker that is always awake for the outboxes. The database is Laravel MySQL in Frankfurt (decided 2026-10-13). These packages are the parts; the integration between them (Decisions 3, Part 3) is work of its own, and versions are pinned.
7. **The management API.** Laravel calls the runtime to create and delete workspaces, set members and roles, set policies, entitlements and quotas, revoke a user's sessions, suspend an organization and stop everything in an emergency. The runtime reports usage records, connection metadata and audit events to Laravel. Its protocol, designed with unit 3b:
   - A signature covers the direction, the destination cell, the method, the path, a timestamp, a nonce and the body's hash. Keys are per cell and per direction and rotate (several valid, the first used). A nonce is admitted once, durably, within the timestamp's window.
   - Every write has a stable operation id and a version per resource. The receiver records the operation id together with the write's effect, in one transaction, and keeps a status for it that only moves forward (accepted, then done, or failed); a retry with the same id is not applied again and gets the current status, so a removal that waits for cancellations reports `accepted` until they are acknowledged and `done` after. Laravel shows a change as pending until `done`. An older version is refused, and the same version with a different body is a conflict. A write is a whole snapshot of its resource (a workspace's members, an organization's policy), not a patch, so a lost write is repaired by the next one. A deletion leaves a tombstone, so a late write cannot recreate what was deleted. An operation overtaken by a newer version of its resource ends as `superseded`, so Laravel never waits on it.
   - Each resource has one owner: Laravel for membership, roles, policies, entitlements, quotas and suspension; the cell for usage, connection metadata and audit events. Versions are a pair of the writer's recovery epoch and a counter, and a restored writer raises its epoch, so a restore never reuses a version for a different body and the restored writer's next write wins. Reconciliation repairs the receiver from the owner, never the reverse; what a restore of the owner would bring back is limited by the recovery log (Part 3, Recovery).
   - An organization's security state (members and roles, policy, entitlements, suspension) has one revision. Each Workspace object receives its part of a revision as one snapshot and applies it whole or not at all, so it never holds a mix of two revisions (a removal from one and a newly enabled connector from the next). Workspaces of one organization may briefly be at different revisions, each one a state Laravel intended. A new workspace serves nothing until its first snapshot has arrived, and an organization's suspension gates every workspace under it.
   - A cell's reports are accepted only for the organizations Laravel assigned to it; its signature proves which cell sent them, not that the organization is its.
   - Neither side calls the other inside its own transaction. Each writes an outbox row in the transaction that makes the change (Laravel in MySQL, the runtime in the object, as the Workspace object's outbox already does) and delivers it afterwards with retries; the receiver keeps an inbox of operation ids, so a repeat is applied once. Usage records carry immutable ids, and billing counts each id once before anything reaches Stripe. A daily reconciliation compares the directory and usage on both sides and alerts on a difference or a delivery that keeps failing.
   - The standalone mode has no management API: its routes do not exist there.
   - The API is declared in the runtime's oRPC contract (`contract/`); Laravel follows its OpenAPI document. Shared test vectors (signed requests with their verdicts, valid and each kind of invalid) keep the two implementations agreeing.
8. **Cells.** One runtime deployment (an instance: two Workers, one D1, its objects and buckets) is a cell. Minerva Cloud starts with one shared cell in the EU, and Laravel records which cell each organization lives on. More cells, for load or for a region, and a dedicated cell for a large customer, are the same deployment. Routing between cells is open question 1.
9. **Enterprise.** The hybrid comes first: a cell in the customer's Cloudflare account, provisioned by Laravel through Cloudflare's API with a token the customer grants, and the customer's SSO reaching our Laravel through WorkOS. What it promises: credentials, conversations, files and search indexes are stored in the customer's account; Laravel receives only the metadata of Decisions 2; models and providers process what turns send them. Before it is sold, every service that carries content is listed with its owner and configured in the customer's account: the AI Gateway and its logs, Workers' logs and traces, the Queues and their consumers, the container image's registry, and the tools our support uses. The browser reaches the customer's cell on a hostname of its own, never through a Worker of ours, so content never passes through our account (open question 1). The reverse holds too: the cell's Worker, which the customer can replace, never forwards Laravel. Sign-in, account and organization pages stay on our origin, and the cell is an OAuth client of its own (a Passport client per cell, whose tokens no other cell accepts), so it receives only its own sessions, never a password or a Laravel session cookie. Signing out works across the two origins: the cell ends its session and sends the browser to Laravel's sign-out on our origin, and a sign-out that starts in Laravel ends the cell's sessions through the management API. This is designed and tested before the hybrid is sold. Laravel decides who signs in, and a token that can deploy the cell can replace its code; the customer chooses the token's scope and can revoke it, which stops our upgrades too. A fully separate deployment ships Laravel as a container image the customer runs, built when a contract asks, since Laravel Cloud is not known to deploy into customers' accounts (to check before selling it).

## Part 1: the runtime

The base every cloud cell runs, and what self-hosting needs on top. For the hosted beta: units 1, 2, 3b, 6's deploy checks, 9 and 10. After it: units 3a, 4, 5, 7 and 8, and 6's public releases (decided 2026-10-14; see Order). One unit per fresh agent. Each ends like the earlier steps: its tests pass, opencode reviews the diff, and it is committed on `cloudflare`.

1. **Freeze the stored formats.** Before an instance outside ours holds data (see Order): an inventory of everything stored:
   - D1's tables, which unit 3 shrinks to the runtime's directory, OAuth clients and flows, and the instance's own rows;
   - each Durable Object's tables, including pi's `pi_*` and the Agents SDK's `cf_agents_*` in the Conversation object, which their packages own, and the Session object's;
   - stored hashes and tokens: write keys, fingerprints, page tokens, folder digests;
   - alarms and fencing state, R2 keys, the encryption envelope;
   - the Durable Object class names: a retired class loses its storage, while a rename or transfer keeps it only through Cloudflare's migration for it;
   - the growth of each object against SQLite-backed objects' 10 GB and 2 MB per row: the Workspace object's registries, the Search objects, pi's state.

   Each entry says who owns it and how it may change. Additive migrations are not enough on their own: two versions run side by side after a deploy, so each version must read what the other writes. Self-hosters may skip releases, so a release names the oldest it upgrades from, and the deploy refuses a larger jump and names the releases to pass through. Dependency updates (pi-durable, the Agents SDK) are checked against the inventory. After the first release, instances no longer start fresh. Freezing does not mean the formats never change; it means every later change follows these rules. Before it, the identifiers the two sides share are settled: organization, workspace and user ids, the issuer-bound subject, and the envelope of usage records and events.
2. **Instances by name** ([instance-names.md](instance-names.md)). Done 2026-10-14. Every resource name is derived from the instance's name, and operator state is in a directory per instance outside the checkout.
3. **Access tokens instead of accounts.** Replaces "email through the operator's zone" ([email-zone.md](email-zone.md)), dropped 2026-10-14: the runtime sends no email (Laravel sends the cloud's; self-hosted sign-in is Access's).
   - Better Auth, its tables, sign-up, two-factor, the claim, the auth emails, the `EMAIL` binding and their pages leave the runtime and the SPA in 3b, once its spike passes. Production holds nothing but the operator's own test data and is reset. Local development and the test instance sign in through a fake authorization server, so they run without Laravel.
   - **3a, standalone mode** (after the hosted beta). The runtime checks Cloudflare Access's token (Decisions 3): the exact issuer (the team's domain) and the application's audience tag from configuration, not merely a valid signature. The user's routes require a person's token, with a non-empty subject and an address; a service token's has neither (it names the token instead), so automation cannot pass as a user. (Both kinds carry `type: app`, so that field tells them apart from nothing.) A user is the pair of issuer and Access's subject. Access's subject is per address within the Cloudflare account and changes when a user is removed and added again; it is not a person's lasting identity, so it does not by itself stop a recycled address from passing as its former owner. Removing someone therefore leaves a tombstone in the directory, and an identity with a tombstoned address is not provisioned again until an admin allows it. Admins are listed by address in configuration; the first sign-in of each pins its subject, and a different subject with that address is not an admin until an admin confirms it with a command. The runtime keeps a small directory itself: every user Access lets in gets a personal workspace on their first visit. Whether they also join the instance's team workspace is configuration (default: no; admins add them), so widening the Access policy does not widen who sees the team's connections. Access's own policy decides who gets in, for example only the company's Google Workspace; an offline check does not see Access revoking one user's session, so removing someone is done in Access and in the directory (below). Every hostname that reaches the Worker, workers.dev and previews included, and the download Worker, is behind Access or refuses requests without its token.
   - **Standalone operations** (with 3a). What the cloud does in Laravel's pages, the standalone mode does with `pnpm` commands against the instance: list and remove users (stopping their runs and sessions, and deciding what happens to their connections and conversations), manage the team workspace's members and roles, set budgets for the whole instance (personal workspaces cannot be used to escape them), the emergency stop, retention and deletion. Open question 3's answer for the standalone mode (what removal, suspension and the emergency stop each stop, and what happens when a delivery fails) is part of this unit's acceptance.
   - **3b, managed mode** (first). In this order:
     1. A spike with real Passport, not a fake: `oauth4webapi` to a Session object, the generation lineage through code exchange and refresh, concurrent exchanges, a revocation racing each, and a key rotation. It answers open question 13. Nothing of Better Auth is removed before it passes.
     2. The forwarding prototype with Laravel Cloud (Decisions 4).
     3. The runtime as Passport's OAuth client, with the Session object, the token check, refresh, sign-out and the per-user session index (Decisions 3). The authorization request uses PKCE with S256 and a single-use `state` bound to the browser by a short-lived cookie, held in a transaction that expires in 10 minutes and is consumed by the callback; the redirect URI is registered exactly; a new session id is issued after sign-in, so a session id set before it is useless; and the address to return to is a path on the site, never a full URL. Tests cover a replayed callback, sign-in CSRF, two tabs signing in at once, session fixation and a hostile return address.
     4. The minimal management API (Decisions 7): creating workspaces, setting members and roles, revoking a user's sessions, suspension, with signatures, versions, outboxes and reconciliation. The directory is written only through it. Organizations' pages, billing and policies come later (Part 3), but nothing in managed mode works without this. Open question 3's answer for the managed mode is part of this step's acceptance, since it promises suspension and revocation.

     Until Laravel's Passport exists (Part 3, unit 1, built alongside), the platform tests run against a fake authorization server, as the faults build already fakes providers; then the browser walk signs in through Laravel's staging environment against the staging cell.
   - Configuration says which mode an instance runs in. Both share one directory interface, so nothing past the token check and the directory's writes knows the difference.
4. **`pnpm run setup`** (after the hosted beta; our own cells are created with unit 2's commands, `cloudflare/README.md`, First deploy).
   - It creates D1 (location hint asked at setup), both buckets with their jurisdiction and lifecycle rules, and the AI Gateway.
   - Standalone, it creates the Access application in front of the Worker with a policy the operator chooses, or prints the steps where the API cannot (open question 8).
   - It writes the instance's directory (unit 2). The workers.dev subdomain is read from the account, or registered when a fresh account has none yet.
   - It applies the migrations, deploys, and prints the URL.
   - A second run creates only what is missing. It refuses an existing resource whose settings differ from what it would create, and never resets anything.

   `make setup` stays the local development setup; `pnpm run setup` is the one that changes an account. A cloud cell is set up the same way, in managed mode.
5. **Export and restore** (after the hosted beta; the beta's gate is the rehearsed recovery of Part 3, Recovery, from the platforms' backups). `pnpm run export` writes the runtime's data of a set of workspaces (an organization's, in the cloud; Laravel exports its own rows):
   - their directory rows, every Workspace and Conversation object's tables (walked from the indexes through a token-gated endpoint, since Durable Objects have no bulk export) and their R2 objects;
   - as a versioned directory of JSON lines and blobs, with checksums, resumable after an interruption.

   A consistent snapshot needs a boundary, and the export pauses the workspaces: new runs and changes are refused, running runs finish or are stopped, and token refreshes, alarms and outbox deliveries are held, before any object is read. The pause is state in each Workspace object, with an owner and an expiry, so it survives the command dying, a restart or a deploy, and ends by itself if the export is abandoned. Shared Queues are not drained, since other organizations keep using them; each workspace records a watermark of what it has sent, and the export waits until its consumers have passed it. This is a portable export, which pauses an organization; backups against disaster are the platform's point-in-time recovery, which pauses nothing. Search indexes are not exported but rebuilt from the conversations, and Session objects are not exported at all. Credentials are exported as ciphertext, which is bound to its row and decrypts only with the same instance's keys. Moving an organization to another cell therefore means reconnecting its connections, unless import re-encrypts them (open question 10). `pnpm run restore` into a fresh instance is tested on every release, because a backup that was never restored is not one. D1's Time Travel and the Durable Objects' point-in-time recovery cover mistakes within 30 days in each store, but not a coordinated restore across them.
6. **Releases and upgrades.** The deploy's checks below come before the beta, since our cells need them too; tagged public releases with notes come after it. An upgrade is checking out a newer tag and running `pnpm run deploy`.
   - The instance records in D1 the release it runs and the schema steps it has applied. The deploy refuses to downgrade across a schema step or a change of Durable Object classes.
   - A deploy refuses an instance whose reset stopped partway. Today a reset that stops after quiescing leaves the identity row and the old D1, so the next deploy serves the old tables with fresh, empty objects. A reset-in-progress marker in D1, written before quiescing and gone with the recreated database, tells this apart from a first deploy whose migrations failed (found in instance-names 2c's review).
   - Each release's CI deploys the previous release to the test instance, starts runs, deploys the new one while those runs are busy (so busy objects keep the old code), and checks that they finish, and that an object restarted on the new code reads what the old one wrote.
   - In the cloud, a release of the runtime and one of Laravel can be deployed in either order: the management API is versioned, and each side accepts the other's previous version.
7. **Off pre-release tooling** (before the first public release). `cf` 1.0.0-beta.13 and a commit build of `@cloudflare/vite-plugin` move to released versions before the first public release, or the guide pins them and says why.
8. **A self-hosting guide and a rehearsal** (after the hosted beta). `docs/self-hosting.md` covers:

## Part 2: what the runtime needs for Minerva Cloud

A cloud cell is the runtime in managed mode, holding many organizations' workspaces.

| Feature | Why the cloud needs it | Self-hosted |
|---|---|---|
| The management API and the managed directory (Decisions 7) | Laravel drives the cell | Not used |
| The tenant of every connection: each connector declares how to read it at connect time (Google's `hd`, Microsoft's `tid`, Slack's team, Notion's workspace, Linear's organization, HubSpot's portal, Stripe's account), or, where one token reaches several companies, which parent resource is the tenant (Atlassian's site, Xero's organisation, GitHub's organization). Recorded before the stored formats freeze, since adding it later means reconnecting | Connection policies | Recorded the same |
| Enforcing connection policies: connectors offered; allowed tenants checked after the token exchange (a refused account's token is revoked and nothing stored), with the provider's hint sent beforehand (`hd`, a tenant authority, `team`). For a token that belongs to one company (Google, Microsoft, Slack), an allowed tenant means only the company's accounts may connect, not that agents see only the company's data: what others shared into the account stays reachable, and grants govern it. For tokens that reach several companies, a policy layer intersected with every other layer (like the ceiling), allowing only the allowed tenants' resources, so no other grant can reach another tenant. The tenant is established before the call, never from its answer: from the address where the provider scopes the endpoint to one tenant (Atlassian's cloud id in the path, Xero's tenant header), or from a lookup of the resource made before the call (a GitHub repository's owner). An operation whose tenant cannot be established before the call is refused, and results of list and search calls that span tenants are filtered by each item's tenant. A repository transferred between the lookup and the call is a race this cannot close, and the connector's documentation says so; action caps in the same layer; a tightened policy goes through strict revocation (cloudflare.md), stopping affected runs, and connections it excludes become `blocked`, not deleted | Companies limit members to company accounts and approved integrations | Open question 4 |
| Usage records: one durable record per model call, container session and stored byte change, with an id, the organization, and the price version it was charged at; reconciled after crashes (a call counted unmetered, a container that outlived its run) | Billing must not double-count or miss | Cost visibility |
| Quotas per organization, set by Laravel and enforced by the cell: model spend, container time, storage, runs, enforced across the organization's conversations at once. A reservation is taken before each chargeable step (a model call at its input plus its maximum output, a container session at its maximum lifetime, both of which the cell enforces; compaction and retries are steps too) and settled with the actual cost after, so concurrent turns cannot overshoot together. A step whose settlement is lost (a crash) keeps its full reservation until reconciliation. Storage is charged over time (byte-hours), not per change. What the reservations cannot bound (a stream lost after the provider charged it, a container that outlived its lifetime because cleanup failed) is Minerva's cost, not the customer's, and is measured separately from what customers are billed | A shared cell pays for every tenant's Workers AI and containers | Budgets an admin sets in configuration |
| Deleting an organization's workspaces across D1, their objects and R2, verified | Offboarding, and the law | Wanted |
| Audit events for what agents and members did, and the support-access switch an organization controls (cloudflare.md's table); where entries that name content are kept is open question 5 | Operator access must be visible and consented | Wanted |
| Retention: run events, the write ledger, page tokens and pi's state (cloudflare.md's open questions 3 and 5) | Storage grows with every turn | Wanted |
| Search over a user's conversations: SQLite FTS5 in a Search object per user and workspace; semantic search later with Workers AI embeddings in Vectorize. Never in Laravel (Decisions 2). Queues deliver at least once and keep messages for a limited time, so the index is a projection with a protocol: the Conversation object writes an outbox entry carrying the conversation's id and revision (not its text), the consumer fetches the text and applies only a newer revision, a deletion leaves a tombstone a late message cannot undo, failures go to a dead-letter queue, and an index can be rebuilt from the conversations. Every result is checked against the reader's current access before it is shown | Users find past conversations | Wanted |
| Rate limits per organization and suspension (sign-up and its limits are Laravel's) | Free compute invites abuse | No |
| The executor and the decryption key in a Worker of their own (cloudflare.md's open question 1). | Compliance and residency answers (cloudflare.md's open questions 7 and 8) | Selling to companies | Enterprise self-hosters ask too |

Today the model wrapper counts calls and token totals per run (`src/model/provider.ts`), with costs at zero and some calls counted unmetered. That is a start for usage records, not billing. Quotas across workspaces need a home that sees the whole organization: an Organization object, or D1 with conditional updates. The unit that builds quotas decides which.

Queries across organizations (cloudflare.md's open question 9) are mostly Laravel's now: its MySQL holds the directory, connection metadata and usage. Questions about content stay in the cell.

**Gates before any customer's data:** an invited beta still holds real credentials and spends real money, so before the first outside organization: budgets enforced, the emergency stop tested, tests that one organization cannot reach another's workspaces, connections or files, a rehearsed restore, retention and deletion, and a decision on the executor's own Worker. **Gates before open sign-up**, on top: the rate limits and a measured cost per turn (open question 12).

## Part 3: the Laravel application

Decided 2026-10-13: a Laravel application on Laravel Cloud, with a Laravel MySQL database, in its own private repository. Decided 2026-10-14: it owns identity and administration (Decisions 1 to 6).

**Hosting.** Laravel Cloud runs the web app, its queue workers and its scheduler, in Frankfurt (EU Central), near the first cell's D1. The database is a Laravel MySQL cluster in the same region, which Laravel Cloud requires. Laravel Cloud's environments: production against the production cell, staging against the staging cell; the test instance, which the fault tests break on purpose, gets a Passport client of its own in staging and nothing else. Queued jobs are idempotent (they carry the management API's operation ids), and scheduled jobs that must run once take a lock.

**Recovery.** Laravel and each cell are restored separately, so a restore of either can bring back state the other has moved past (a removed member, a deleted workspace, usage already billed). One rule: a restored side first applies the recovery log below to its own state, then reconciles (Decisions 7: the owner's state wins, and a restored owner publishes under a new epoch), and only then serves again. So a stale owner snapshot never overrides a restriction the log holds. Since both sides can be restored past the same change, every change that reduces access is also written to a log in R2 that no restore rewinds, and is applied again from it: deletions, removals, role downgrades, a tightened policy, grants reduced in the cell, support access withdrawn, suspensions, user revocations. The entry is written before the change is applied, and the change is not `done` (Decisions 7) until its entry is stored, so a crash between the two cannot lose it. An entry whose change then failed is still applied on replay; that is safe, since every entry only reduces access. Entries are signed and numbered, a later grant that restores access is ordered after them by number, and the bucket has a lock rule against overwriting and deleting. The log protects against restores and mistakes, not against someone holding the operator's Cloudflare account, who can remove the lock. Files are covered too, since R2 has no point-in-time recovery: objects are never overwritten (their keys hold a hash and a random part), and a deleted file's object is removed only after the window the databases can be restored by (30 days), so a restored manifest finds its files. Deletions for offboarding state that delay. Money is covered separately: usage records are immutable and also written to a log in R2 that no restore rewinds; Laravel sends each to Stripe with its id as the meter event's identifier, and records each submission in a log of its own outside its database. Stripe deduplicates identifiers only within a rolling window of at least 24 hours, and its summaries are totals, not a list of accepted events. So after a restore of either side, billing pauses; events younger than that window may be resent under their identifiers, older ones never are; and per customer and period, the usage log's total is compared with Stripe's summary and its invoices, a difference being corrected by an operator (a correcting event, or a credit). Nothing is billed twice, and what is missing is found. Restored connections are not trusted as current: a provider may already have rotated a refresh token the backup holds, so a restored connection starts as `refresh_uncertain` and asks for reconnection if its refresh fails, and a connection the log deleted stays deleted. A restored cell ends every session: it raises an epoch for the whole cell, which every Session object records when it is made and checks on every request, so a restored Session object cannot undo a sign-out. Users' generations are taken again from Laravel, whose own are authoritative, and from the log. When the log or the other side cannot be reached, the restored side stays closed rather than serve stale permissions. The Passport keys, the management API's keys and Laravel's encryption key are backed up outside Laravel Cloud, since a restored database is useless without them. Recovery objectives (how much data may be lost, how long an outage may last) are set before the beta.

Units, each needing the runtime's side named with it:

1. **Identity.** Fortify, Socialite and Passport, with the runtime registered as Passport's client (one client per cell and environment); the sign-in pages; the Laravel side of the minimal management API. Built alongside the runtime's unit 3b and verified with it. Social sign-in's rules are settled here, not later: an account links to a provider by the provider's stable id, never by address; linking happens only while signed in, and unlinking cannot leave an account without a way in; a Socialite sign-in passes the same two-factor requirement as a password; recovery is defined.
2. **Organizations.** Members, invitations, roles and team workspaces, pushed to the runtime through the management API.
3. **Billing.** Plans and prices in Stripe through Cashier, Checkout, the Customer Portal and Stripe's webhooks; entitlements as Pennant features and quotas as numbers, both pushed to the cells; usage from the cells into Stripe's billing meters. The billable model is the organization. Cashier does not decide the states between: a failed payment and its grace period, cancellation, credits, plan changes within a period, usage that arrives after the period closed, and corrections to meters. Stripe's and WorkOS's events can arrive out of order, so each is stored on receipt and processed in a transaction, and before an entitlement is removed the provider's current state is read, not inferred from the event.
4. **Connection policies.** The page per connector: offered or not, allowed tenants, action caps. An admin pins a tenant from their own connection ("only accounts from Acme"), using the connection metadata the cell reports, without typing an id.
5. **The operator admin.** Customers, organizations, cells, usage, suspension; only operators sign in, with two-factor.
6. **SSO and directory sync** through WorkOS. Laravel's starter kits offer WorkOS AuthKit as an alternative to Fortify, not an addition, so combining them needs rules of its own: how an SSO identity links to an existing account with a password or a Socialite sign-in, and that an organization requiring SSO refuses every other way in for its members, existing sessions and refresh tokens included (Decisions 3). Directory sync removes a person from that organization and ends their sessions' access to it; it does not suspend the account, which may belong to other organizations too. Suspending whole accounts needs accounts the organization manages (made by its SSO, belonging to it, with rules for any other memberships they hold), which is designed when an enterprise asks. Directory events are reconciled against the directory's state, since deleting a whole directory does not emit an event per user.
7. **Cells by API.** Provisioning a dedicated or hybrid cell through Cloudflare's API (Decisions 8 and 9).

Considered and not chosen for the application: TypeScript on Workers with PlanetScale Postgres through Hyperdrive (one language and types shared across the contract, but no admin framework, and accounts rebuilt by hand); Django (known from `main`, but no first-party managed host); Rails (nothing Laravel lacks for this job).

## Open questions

1. Routing between cells: a hostname per cell (`eu.app…`) chosen after a lookup in Laravel at sign-in, or one front Worker that routes by organization. One cell needs neither. A hybrid cell is always reached on its own hostname, and its Worker forwards nothing to Laravel (Decisions 9).
2. Laravel Cloud behind the runtime's Worker: forwarding to the application's own Laravel Cloud hostname, which proxy headers Laravel trusts, and whether Laravel Cloud's own edge accepts it.
3. Suspension and the emergency stop: which of sign-in, new turns, running turns, uploads, reads, downloads and token refresh each one stops, how it reaches every workspace of an organization or the whole cell when deliveries fail, and how it survives a restore. Today a stream rechecks its authorization periodically and a signed download link works until it expires; those windows are kept and stated, or closed. Answered in units 3a and 3b, as part of their acceptance, not later.
4. Connection policies when self-hosted: none, or allowed tenants from configuration.
5. Where audit entries that name content (recipients, resource names) are kept: in the cell (R2 through Cloudflare Pipelines), with Laravel holding administrative actions only.
6. The Ledger components for Laravel's Inertia pages: a package published from this repository, or a copy styled to match.
7. The operator admin: Filament (larger and more active) or Nova (first-party, paid).
8. Access in front of the Worker. The review reports that Cloudflare's documentation now supports Access on workers.dev, created through the API, and that protecting the Worker itself covers its previews but refuses WebSocket upgrades, while protecting a hostname does not. To confirm in unit 4: the browser uses SSE, but the stream's relay from the Conversation object is a WebSocket, so the chosen protection is rehearsed with a turn. If it holds, a self-hoster needs no domain.
9. Residency of a cell's accounts and content: one EU cell with D1 in the EU jurisdiction, or one cell per region; and the container's and the model's placement (cloudflare.md, open question 8). Laravel's own data is in Frankfurt.
10. Import into another cell: whether credentials are re-encrypted under the new cell's keys or reconnected.
11. The free tier: its quotas, and whether its model is the default Workers AI model.
12. The cost of a typical turn (container time, Durable Objects, model), measured, to set quotas and prices.
13. The generation in Passport's credentials (Decisions 3): how much of Passport it takes to thread the lineage through its grants and into the access token, through its extension points or by replacing its bridge classes, and what that costs on each upgrade. The spike that starts unit 3b answers it with real Passport. If the cost is too high, compare alternatives, which must pass the same racing and chained-credential tests: a plain check of Passport's revocation status does not, since a token minted by an exchange that raced the revocation has an unrevoked row. Any alternative keeps the lineage (or serializes issuance against revocation) in Laravel. If none is acceptable, the split's identity design is reconsidered before Better Auth is removed.
14. A membership lease: Workspace objects that stop serving a team workspace when its membership has not been confirmed by Laravel for some minutes. It bounds a removal during a broken management channel (Decisions 3), at the price of team workspaces failing when Laravel or the channel is down.
