## The rule in brief

A run's work in pi is its operation, which is the `run:<id>` submission it sent to its session and the tasks pi made for that submission. A task belongs to the operation when it is in the same session, is not a background task, and has an id above the submission's. The active run's operation owns its work. Everything else pi holds is orphaned.

Four things follow from that one rule. A tool or model call is admitted only for the active run, only while its submission is placed, and a tool call only from a task that belongs to it. The restart gate reads the run's submission first and counts only tasks that belong to it. A stop marks orphaned tasks one by one and never aborts a whole pi conversation. Before a run's start configures pi or submits, it waits until no orphaned non-background task is live. pi settles an orphaned submission in the commit that ends the task holding its run. A reset ends a wait that does not finish in 30 s.

Chunk 19a still creates one pi session per run, so in 19a every orphan is in another session than the active run's. The rules are written for one session shared by many runs, which chunk 19b brings. Unit tests run them, and the code that applies them, on such a session with pi itself.

## Decisions

### The data shape

`PiWork` and `classifyWork` stay in `gate.ts`. A new file, `cloudflare/src/conversation/pi-work.ts`, holds the operation and the code that reads pi for it.

```ts
/** A run's operation in pi: the session it claimed, and its `run:<id>` submission once pi has it. */
type Operation = { session: number; submission: { id: number; status: SubmissionStatus } | null };

/** What pi holds for a run: no input yet, work in progress, or a settled submission with nothing of its own left (gate.ts). */
type PiWork = "not_submitted" | "in_progress" | "settled";
```

`Operation` is the run's identity in pi, keyed by what Minerva already sends (`operationId: run:<id>`). A run with no session has no operation (`null`). Only the active, acting run's operation owns work. Ended runs need no operation, since their work is orphaned by definition.

`pi-work.ts` holds:

- `Operation`;
- `belongs(op, task)`, true when `op` has a submission, `task.session === op.session`, the task is not background, and `task.id > op.submission.id`. It holds whatever the submission's status, so a settled run's last live task still counts as its own;
- `piWork(storage, run)`, moved from `conversation.ts:1556` and exported, so U1 runs it in Node (The gate);
- `admitTool(deps, call)` and `admitModel(deps, fence)`, each with its rule inline (Admission);
- `PI_SETTINGS`, moved from `conversation.ts:151` and imported there, so U3 can assert `backgroundTokens`.

`classifyWork(submission, ownLive)` checks the submission first. No submission is `not_submitted`. `queued` or `placed` is `in_progress`. `done` or `unanswered` is `in_progress` when `ownLive > 0`, else `settled`. Tasks without a submission of this run never make work in progress. In `test/unit/conversation-gate.test.ts`, the row `[undefined, 2, "in_progress"]` becomes `not_submitted`, and its comment says that the count is the run's own live tasks.

The id rule rests on three facts in the table. Ids ascend in commit order. Every task of an operation is made in or after the commit that places its submission. And no other operation's task can be made after that commit, because a run submits only once no orphaned non-background task is live (The start's wait), and Minerva makes no background tasks. So the rule is not a guarantee of pi's alone. It holds because the start's wait holds, and unit test U5 runs that wait on a shared session. U3 asserts that `backgroundTokens` stays 0.

### The gate

The gate keeps its place and its decisions (`decideGate` is unchanged). Only its reader changes.

`piWork(storage, run)` reads the operation first. No session or no `run:<id>` submission is `not_submitted`, whatever else the session holds. A queued or placed submission is `in_progress` without another read. Only for a settled submission does it look for the run's own live tasks, one filtered scan per live status: `scanTasks({conversationId: session, status, background: false, order: "descending"}, 1)` (pi-durable `types.d.ts:592`, `storage/sqlite/storage.js:288`, over the index `tasks_by_conversation`). The newest live non-background task of that status is the only one to check. If its id is not above the submission's, none is, so the read is exact without paging. It passes `classifyWork` the submission's status and the count of the run's own live tasks. `onStart` and the start's watch use the same reader, so they agree with the gate.

Two answers change, and both matter for 19b. A run with no submission no longer counts live tasks of an earlier run in its session as its own, so a run that never reached pi gets no attempt for another run's leftovers. A leftover background task no longer counts either. It is orphaned, and the cleanup at open marks it.

### Admission

Admission is by the active run and its operation, never by a session lookup.

**Tool calls.** `ToolHost.current` takes `{ session, task }` from `api.conversationId` and `api.taskId`, and answers a promise. It counts the entry for the test build (`#entered`), reads `store.activeRun()` (indexed by `runs_status`, `schema.ts:78`), refuses unless that run's session is the call's, reads the run's submission from pi's storage, refuses unless the submission is `placed` and the call's task id is above it, and then checks the fence synchronously after the last await, as today. The connector tool, the script tool (through `scriptToolHost`) and the local tools await it. A refusal answers `RUN_ENDED_MESSAGE` as today.

**Model calls.** `begin` stays synchronous. It refuses unless the active run's `provider_session` is the call's `sessionId` and its fence is current. The pi check is in `record`, which is already awaited before the upstream is called and before `recordModelCall`. It reads the run's submission and returns `null` (the existing "not recorded, not counted" refusal, `provider.ts:314`) unless the submission is `placed`. `model/provider.ts` does not change. pi gives a model call no task id, so the rule for model calls is the operation's state, not the task. It is enough because a session's model calls come only from the generation that holds its live run and the compactions that generation owns, and the start's wait and the cleanup at open leave a session no live generation but the placed operation's.

**The hosts' bodies.** The two checks are functions in `pi-work.ts`, `admitTool(deps, call)` and `admitModel(deps, fence)`. Their `deps` are the store's `activeRun` and `isCurrent`, pi's `submissionByRequest` and an entry counter.

- `#toolHost.current` is `(call) => admitTool(deps, call)`. `admitTool` counts the entry through `deps.entered`, then reads the active run, compares sessions, reads the submission, applies the rule and checks the fence. It answers exactly what `current` answers.
- `#modelHost.record` first awaits `admitModel(deps, fence)` and returns `null` when it refuses, before `pricesOf` and `recordModelCall`.
- Nothing else in either body admits or refuses a call. opencode's review of unit 3's diff checks these two bodies.

So unit tests run the production checks over a real `RunStore` and pi on node:sqlite, with `deps` built as the Conversation builds them (U4). Each check adds one indexed read (`submissions_by_request`, pi-durable `storage/sqlite/migrations.js:51`) per call, through the store's queue (What the code does today).

`store.runBySession` and `store.runByProviderSession` are deleted. The test build keeps its own attribution. `#entered` passes the port the session the call names (the pi session for a tool, the provider session for a model call), and `faults/ports.ts` maps it to the newest run that names it, in its own SQL, for both its counts and the fake model's marks. In 19a that is the call's own run, so the tests that assert pi ran nothing for an ended run keep their meaning.

**Logs.** A late result logs one line per call, `run <A>'s call <tool> answered after the run ended; its result is refused (run <B> acts now)`, or `(no run acts now)`. In `#invoke`, `record` always enters `store.outside`, and the line is decided inside that callback, where `appendToolCall` runs. It logs when the run is no longer active there, whether the outcome has no event or `appendToolCall` answers `null`. A per-call flag, kept outside the promise that is retried, limits it to one line. `#localTool.execute` logs the same line, with the tool name, after `runGated` and `local:released` when its run is no longer active. A `run_script` result is not logged. Its scripted calls are, through `#invoke`. No line carries arguments or results. The late-result line and the bound's reset use `#log` at warn level (Decisions on the owner questions, 4). The late-result line is the "You see" box.

### Stopping and settling

A new class, `PiStops` in `cloudflare/src/conversation/pi-stops.ts`, applies the rule to pi. The Conversation gives it a reader of the acting run's operation, the bound and its log, and passes `pi` to `mark` and `settle` on each call. It takes no other part of the object, so unit tests run the production code on pi over node:sqlite (U5). It replaces `#stopPi` and `#abortSession`. It never calls `conversation.abort`, never withdraws a submission and never uses PiHarness's `withdraw`.

It keeps marking and settling apart, since pi's calls do, and runs starts one at a time.

**Mark** (`mark(pi, session?)`) is one pass.

- It reads `pi.inspect()` (on pi's line, pi-durable `harness/harness.js:159`), then the acting run's operation, in that order. A submission committed between the two reads has no task in the inspection, so its tasks cannot be taken for orphans.
- In one synchronous stretch, it starts `pi.abortTask` for every live task that does not belong to the operation, whether or not it is already marked. With `session`, only that session's tasks. pi commits no second mark for a task already marked by request, and it upgrades a `restart` mark (`scheduler.js:200` to `:201`).
- These calls are not awaited, since an `abortTask` can wait on a running invocation that ignores its signal. Their failures are logged.
- There is no second pass. Suppose a generation hands its run to a successor between the read and the marks (`generation.js:562`). The successor's first model call is refused, because no run is active, or the call names another run's provider session, or the operation is not placed. pi's retries are off (`conversation.ts:152`), so the successor ends by itself. A caller that waits marks it on its next pass.

**Settle** (`settle(pi, signal)`) repeats these steps:

1. Run a mark. Every pass reads `pi.inspect()` and the operation again and never reuses an earlier pass's reads.
2. From that pass's reads, take the live non-background tasks that do not belong to the operation.
3. If there are none, return. Otherwise await `pi.waitForTask(first, context)`, with `signal` in its context. `signal` ends the wait early, and pi cancels only the wait (pi-durable `harness/types.d.ts:667`).

Settle waits on tasks only. pi settles a placed orphaned submission `unanswered` in the commit that ends the generation holding its run (A run's inputs settle with its generation, in What the code does today). That generation is a live, conversation-owned, non-background task, so it is always in settle's wait set. Settle has no `which` parameter. Every caller waits for non-background orphans only, and mark marks background ones too. Settle waits for tasks marked by any caller, not only its own marks.

`pi.waitForTask` resumes pi's scheduler (`harness.js:177`), so `settle` must never run before PiHarness's `pi.resume()`. Every caller reaches pi through `harness.pi()`, which returns only after the resume (PiHarness `_doOpen`, `:529` to `:536`), and the cleanup at open only marks. A doc comment on `settle` says the same.

**Lane** (`section(fn)`). It runs a start's section after the previous one ends (The start's wait). A section that throws does not stop the next.

The callers:

| Caller | Steps | At the bound |
|---|---|---|
| A run's end (`#afterFinish`, deferred) | mark | none; the next start settles what is left |
| A reconcile (`#reconcile`) | mark | none |
| Deletion (`deleteInternal`) | settle (no run acts after the end, so every live task is orphaned) | none. A settle that does not end holds the deletion, as today's `conversation.abort` does. |
| Retention's abort of a session (`retention.ts:173`) | mark, that session only, as today without waiting | none |
| A start (`#startLoop`) | lane, settle | The start's wait |
| The cleanup at open (`#stopEnded`) | mark, awaiting the marks' commits | none (Cleanup at open) |

Deletion keeps today's order. It ends the run, settles pi's work, then destroys scripts and the sandbox. P5 checks that no task is live at its answer, but passes with the settle replaced by a mark, since its connector tool returns at once on pi's abort. The test that fails then deletes during a `bash` call held past `runGated` (`local-tools.test.ts`, As built, Unit 4). `deleteInternal` drops its `latest` guard and the comment above it, and settles on every try. Deletion takes no turn in the lane. A start can still be inside `harness.submit`, past its fence check, when deletion reads. Its submission and generation can then land after deletion answers, as today. That generation's first model call is refused at `begin`, because no run is active (`provider.ts:249` to `:250`). pi's retries are off, so it ends `unanswered/model_error` by itself, and `#settle` ignores it (`conversation.ts:872`).

Retention passes only while no run is active, so its session's work is all orphaned and the marks are what the whole-session abort made, without the code that could abort an active run's work.

A stop marks every orphaned task, not only the ending run's. In 19a the two sets are the same, since the only live work outside the active run's session is the run that just ended and sessions retention has not deleted. One rule for every caller is simpler than a rule per run, and it never touches the active run's work.

### The start's wait

`#startLoop`'s section, from the attempt's start to the submit, runs in `PiStops`'s lane, one run at a time:

1. Inside the lane, run today's checks that the run is acting and its fence is current. Then, in the same synchronous stretch and before any await, take the run's end signal from `#controller(runId)`. A run that ended while its section was queued returns here, marking and waiting for nothing. Since the check and the signal come in one synchronous stretch, `#controller` never creates a controller for a run that has ended (`#afterFinish` aborts and deletes it, `conversation.ts:936` to `:937`). Then start the attempt and its phase, as today.
2. **Wait.** Settle. Its marks reach background orphans too, and its wait is for non-background ones only, as the plan says. The wait's signal is the run's end signal joined to the section's deadline. A cancel, a deletion and the run's deadline abort the end signal, so a run that ends while it waits ends its section at once, without configuring anything.
3. Check the fence again, then install the run's tools, create or reuse its session, claim it, prepare its container and submit, as today.

`#watch` and `#recover` start the section with `#defer` and do not await it, as `onStart` does (`conversation.ts:728`). A section can wait up to `piSettleMs`, and Lifecycle drives due jobs one after another (`conversation.ts:169` to `:173`). For a `not_submitted` run, `#watch` then answers `{rescheduleAt: now + WATCH_MS}`. A section that is already running is found in `#loops`.

The lane is what keeps one run's input from queuing behind another's. Without it, run A's section can pass its fence check, then await `harness.submit` while A is cancelled and B starts. B's wait would find nothing of A's, and A's input could land after B's. In 19a that leaves a stray generation in A's session that admission refuses. In 19b there are two outcomes, and the lane rules out both. If B's input commits first, A's input queues behind B's run and becomes a stray pi run after B answers, with task ids above `run:B`. If A's commits first, B's input queues behind A's generation. Admission refuses that generation's call, and pi ends it with no final boundary, so B's input stays queued and B never starts. With the lane, B's section starts only after A's section has ended, A's submit included. B's mark then sees what A's submit made, and B's wait settles it.

**The bound.** A section's deadline is set when it is queued, so it covers the time in the lane and the wait. The bound applies to starts only. It is `piSettleMs`, 30 s in production (Decisions on the owner questions, 1). It is a port, so the test build reads a shorter one from the fault plan's config (`pi_settle_ms`), as `runTimeoutMs` does (`faults/ports.ts:229`). Each section has its own timer, cleared in a `finally`, so a section that ended can never fire it. When the deadline passes while the section still waits, in the lane or in settle, and its run is still current, the object logs `run <B> could not start: pi's earlier work did not end within 30 s`. The section first awaits `lifecycle.jobs.push` of `watch:<run>` due now, which rearms the alarm, then `ctx.storage.sync()`, and then resets (`#reset`), as the folder-limit path pushes, syncs and resets (`conversation.ts:1143` to `:1162`). The next instance then opens at once rather than at the next due job, which can be up to `WATCH_MS` later. A timeout alone would leave the work running, as `within` does (`conversation.ts:1604`), so the reset is what ends it. A reset ends every invocation in memory. The next instance's gate finds B with no submission (`not_submitted`, no attempt counted), its cleanup marks the orphans before pi resumes, their abort handlers run with no invocation to join, and `onStart` starts B's section again. pi's own abort handlers for generations and tool tasks are single commits, so one reset ends the work that held the wait.

**Cost when nothing is left.** The wait costs one `pi.inspect()` read, on pi's line in the same isolate. A start claims its session after the wait, so the wait also reads the run's submission only when an earlier start of the run claimed a session and did not submit (As built). The cost is part of what the perf box measures (Perf probe and rule).

### Cleanup at open

`#stopEnded` keeps its place, after `Harness.open` and before the factory returns, so before PiHarness's `pi.resume()`. The plan says "before `Harness.open` resumes the scheduler", but `Harness.open` resumes nothing; this is the last point before anything runs. It now uses `PiStops`'s mark, given the Harness the factory just opened (since `harness.pi()` waits for the open) and the acting run's operation read from the factory's storage, instead of `store.sessions()`. It marks in one synchronous stretch, as today, and withdraws nothing. It awaits the marks with `Promise.allSettled` and logs each rejection, as mark does. A rejected mark must not fail the factory, which every later event would run again. Before resume no invocation exists, so each mark resolves once its commit is made. It waits for nothing else, since the factory runs under `blockConcurrencyWhile`'s 30 s limit (ARCHITECTURE.md, Attempts and recovery), and it fires no fault point, so a test's hold cannot block the factory.

Against today it also marks orphaned work in the acting run's own session, such as a background task or tasks with ids at or below its submission's. In 19a neither exists.

### After a restart

| Where the object died | What the next instance does |
|---|---|
| A run in progress (submission placed, tasks live) | The gate answers `in_progress` and restarts the run. The cleanup marks nothing of its own. pi resumes its tasks, and admission takes them under the new attempt's fence (placed submission, ids above it). As today. |
| A run cancelled, its stop lost | The gate finds no acting run, or the next run with no submission. The cleanup marks the cancelled run's tasks before pi resumes, and their abort handlers settle its placed submission `unanswered`. The next run's start settles them, then submits. This is F1. |
| Between a run's claim and its submit | The run has a session and no submission, so the gate answers `not_submitted` and counts no attempt. `onStart` starts its section, which reuses the claimed session, waits, and submits `run:<id>` once (pi deduplicates by request id, `submissions.js:130`). |
| The submission settled while the object was away | `settled` when no live task of its own is left; `onStart` reconciles it, the run ends, and its end marks what is orphaned. |
| A leftover background task | Not counted by the gate; orphaned, so the cleanup marks it. |
| The gate ends the run (inert conversation, deadline, attempt cap) | No acting run, so all of pi's live work is orphaned and marked, as today. |
| During the start's wait, or its reset at the bound | `not_submitted`, no attempt counted; the cleanup marks the orphans; the section runs again. |
| During a mark or a settle, whoever called it | The marks already committed stay, and their abort handlers run after resume. The cleanup marks the rest before pi resumes. Laravel sends a deletion again, and its settle finds less. |
| During the cleanup at open | The gate already committed its decision and synced. The next instance runs the gate again, as today when the factory dies after the gate. |

## Perf probe and rule

**Metric.** S, per turn, is the first model call's `answered` mark minus the run's `created_at`, both on the object's clock. `answered` is the existing mark taken when the fake-remote request's answer is read (`faults/ports.ts:178`). A request's departure cannot be timed inside the object: its clock moves only when I/O completes, and the output gate holds the request until the writes before it are durable. So S ends at the first answer, as M1 and M2 do, and includes one round trip to a sibling object that is the same on both sides. `created_at` is written by the start's final transaction. So S covers the activation, the attempt's start, the lane and the wait, the session's creation, the submit, pi's first step, the first call's admission (where 19a's model check reads pi), the output gate's wait for every write before the request, and the round trip. It leaves out Laravel's round trip and what the start does before its final transaction (the compile, the attachments' copy), which 19a does not change. The coordinator accepted S as the measure (Decisions on the owner questions, 2).

**How it is measured.** The probe's existing run (20 turns of six calls, `perf.test.ts`) adds S for each turn, 20 samples. Every turn starts after the previous one completed, so each S includes a wait that finds nothing, which is the case the rule is about. S ends at the `answered` mark that chunk 14a's calibration moved. The ballast is written before every call's request, the first included (`faults/ports.ts:170` to `:178`), so S needs no calibration of its own. The baseline is unit 1's commit, `main`'s engine with the probe. The coordinator runs baseline, head, baseline, head on `minerva-cf-test-19`, each after a fresh `pnpm run deploy:test`, and reports S's median and p95 beside M1 and M2.

**Rule.** Head's median S minus the baseline's median S is at most 200 ms in both pairs. More fails. If the two baselines' medians differ by more than 200 ms, the probe cannot judge the rule, and the coordinator asks the owner instead of calling it a pass.

## Risks

- **A wait delays the next turn.** A run started right after a cancel waits for the cancelled run's pi work to end, up to 30 s, then resets once. A tool that ignores pi's abort (a local tool past `runGated`, a script finishing its guest) is the usual cause.
- **A reset at the bound ends what else the instance holds.** It cuts a facts delivery, a sweep and the previous run's container destroy. Each is a Lifecycle job or is redone by `#recover`, as after any reset. It also turns the earlier run's in-flight write settlements into `uncertain` (the lost-write sweep) and its open model-call and script records into `lost` (`settleLost`, `store.ts:864`), as any reset does.
- **The id rule rests on pi's id sequence, its follow-up behaviour and the start's wait.** The first two are pi-durable 1.2.0's. A pi-durable upgrade must be checked against `belongs` as it is against `pi-tables.ts`'s statements (ARCHITECTURE.md, Open questions 3). U2 and U5 run on pi itself, so an upgrade that breaks the order fails them.
- **Model admission is by the operation's state, not the call's task.** If pi ever made model calls outside the live run's generation tree, such as a background compaction, admission could not tell whose they are. U3 fails if `backgroundTokens` changes.
- **Deletion waits for non-background orphans only.** Minerva makes no background task (U3). A chunk that turns background compaction on makes deletion wait for background tasks too.
- **A start inside `harness.submit` at a cancel or a deletion can leave one refused generation**, which ends by itself (Stopping and settling). Today's code has the same gap. In 19b its unanswered input and refused-call entry sit in the shared session, and 19b decides how they show (its note after a stopped turn).
- **The test build's attribution is per session.** Correct in 19a; 19b changes it (What 19b and 20 inherit).
