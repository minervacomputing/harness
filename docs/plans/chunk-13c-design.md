## Decisions

**A tombstone is a deleted-class export.** In Cloudflare's Durable Object migrations a deleted class (`deleted_classes` in Wrangler's migrations, an `exports` entry with `state: "deleted"` in `cf`'s config) deletes the class's namespace and every object's storage and alarms, wherever they are located, EU included. It cannot be undone. The code must not export the class and no binding may name it. `reset-worker/cloudflare.config.ts:56` does this for every class an app exports, and the code-mode lab keeps one (`test/account/scripts-worker/cloudflare.config.ts:31`). The unit that adds the tombstone (unit 3) deletes `src/retired.ts`, its exports from `src/index.ts:31` and `src/faults/index.ts:135`, and turns `cloudflare.config.ts:209` into `Workspace: exports.durableObject({ state: "deleted" })` and, on the faults builds, `FaultMailbox` likewise (`:213`). Tombstones go only into builds for an instance (`target.instance !== null`). The offline and test modes drop both classes outright, since local state holds nothing to retire and `cf`'s local simulation refuses to delete a class it does not have. The second deploy (unit 4) removes both entries. Then the build exports `Conversation`, `Scripts`, `Sandbox` and, on the faults builds, `FaultProvider`.

**A deploy refuses to strand a namespace.** Today only the reset checks that the Worker has no namespace of a class the build does not export (`scripts/reset.ts:270`). Unit 2 moves `ownNamespaces` (`reset.ts:173`) to `scripts/account.ts` and a pure `strayClasses(namespaces, build)` to `scripts/builds.ts` (classes with a namespace that the build exports neither live nor deleted). `deploy.ts` runs it in its read-only phase, before the identity is recorded, and stops on a stray. The reset uses the same function. So a deploy that drops the tombstone before its namespace is gone stops before anything changes, on every instance, CI's included.

**Secrets follow the build.** `cf deploy --secrets-file` keeps secrets the file lacks: staging still has the three retired ones after 13b's deploy. Unit 2 makes the deploy delete, right after its upload, every secret on the app Worker that the build does not declare (pure `undeclaredSecrets(onWorker, build)` in `builds.ts`; names printed, never values). This stays: secrets.env and the build become the only source of the Worker's secrets. `cf workers secrets delete` makes a new version per secret, so the unit uses `cf workers secrets bulk` instead if it can delete, and records which it used.

**The download Workers go in the deploy.** Unit 2 also makes the deploy delete `<name>-files` when it exists (`cf workers delete <name> --force`, then `workerExists` must be false, since an aborted delete exits 0). Every instance gets a deploy with this step during 13c, so unit 5 removes it with `names.download` (`scripts/instance.ts:55`, `:75`). The `-files` suffix stays reserved (`nameProblem`), since the buckets use it. No separate script and no `cf` by hand: the deploy already pins the account, takes the locks and checks the identity (`deploy.ts:114`, `:169`), and CI's deploy then cleans `minerva-cf-ci` with no owner step.

**Order, because CI deploys main.** Every push to `main` that changes `cloudflare/` deploys it to `minerva-cf-ci` (`.github/workflows/main.yml`), and a queued run skips when `main` has moved past it with account-path changes (ci-account-suites.md, Freshness). The `ci-instance` environment allows only `main`, so an older commit cannot be deployed to CI by hand. Unit 3 is therefore pushed alone, and nothing that touches the account paths is pushed until its account job is green. If unit 4 reaches CI first anyway, the new guard turns it red before any upload. The recovery is a revert of unit 4 on `main` (CI deploys the tombstone), then unit 4 again. Each tombstone and drop is deployed by hand to `minerva-cf-test` before its push, then reaches CI, then staging.

**Production is reset early and deployed once.** The reset needs a build that exports `Workspace` live: with the tombstone, `reset-worker` refuses the build (`reset-worker/cloudflare.config.ts:46`), and with the drop, the stray check refuses the namespace. So production is reset at `main` before unit 3 lands, with `node scripts/reset.ts --instance minerva-cf --production --yes`, and stays quiesced (503) until the last deploy. The reset keeps the Worker's secrets (every version inherits them) and the container image in the registry, and deletes every object, both buckets' keys and D1, which it recreates empty. Production is then deployed once, at unit 4's head or later, after the drop has passed on test, CI and staging. That deploy applies 0001 to 0013 to the empty D1, provisions the live classes afresh, never creates `Workspace`, deletes `minerva-cf-files` and the retired secrets, and writes the identity row. Between the reset and that deploy, nobody deploys production.

**Migration 0013 drops 15 tables.** The chunk's list misses five that 0003 made: `twoFactor`, `organization`, `member`, `invitation` and `rateLimit`. Applying 0001 to 0012 in SQLite leaves 18 tables, and the code reads only `recovery_conversations`, `recovery_runs` (`src/internal/conversations.ts`, `runs.ts`, `src/stream/route.ts`, `src/conversation/delivery.ts`), `instance_identity` (`scripts/identity.ts`) and `d1_migrations` (`src/http/probe.ts:41`). `migrations/0013_retire_accounts.sql` starts with `PRAGMA defer_foreign_keys = on;` as 0003 does, then drops children before parents: `oauth_flows`, `memberships`, `invitation`, `member`, `instance_setup`, `instance_settings`, `account`, `session`, `twoFactor`, `workspaces`, `organization`, `user`, `verification`, `rateLimit`, `oauth_clients`. A trial in Node's SQLite with foreign keys on and a row in every table passed, left `instance_identity`'s row and three tables, and `foreign_key_check` was empty. Dropping `user` first failed with `FOREIGN KEY constraint failed` (`organization` and `workspaces` restrict it). No squash: staging and CI keep their applied list. After 0013 no UNIQUE constraint is left, so `test/unit/schema-check.test.ts` changes (unit 1).

**Production's catalog answers 404 by design.** Production has no internal settings and no Access application, so the box "`GET /internal/v1/catalog` on production answers" becomes: it answers 404 `NOT_FOUND` with the security headers, and `pnpm test:deployed --instance minerva-cf` passes (its probe calls every class, in the EU too, and compares D1's migrations with `migrations/`). A 200 needs an Access application on production's hostname, a service token and the four settings, which is open question 1.

**CI's secrets lose the retired values.** `MINERVA_CI_VARS_ENV` becomes two lines, `MINERVA_MODEL_PROVIDER=fake` and `MINERVA_MODEL_NAME=@cf/zai-org/glm-5.3-flash`. GitHub cannot read a secret back, so `MINERVA_CI_SECRETS_ENV` is replaced with a fresh file from `pnpm secrets --instance minerva-cf-ci` in a temporary `MINERVA_INSTANCES_DIR`, which now holds `MINERVA_SECRET_KEY` alone. A new key on a test instance is safe: the suites derive the fault and probe tokens from the file, and a write id's stored hash matches across a rotation (`src/gateway/executor.ts:527`). The masks then lose the origins: `ciMaskValues` drops its `vars` input and the origin loop (`scripts/masks.ts:30` to `:36`), and `ci-masks.test.ts` loses the origin assertions. The workers.dev subdomain stays masked, since `accountSubdomain` prints `::add-mask::` in every step that derives an origin (`scripts/account.ts:75`, `scripts/suite.ts`, `deploy.ts:169`). The owner changes both GitHub secrets.

**The local instance files are pruned last.** The retired lines in each `secrets.env` keep the old values re-uploadable until production and staging are verified. Unit 5 adds `node scripts/instances.ts prune <name>`: it rewrites `secrets.env` keeping the names `scripts/secrets.ts` requires or lists as placeholders, `vars.env` keeping the names `scripts/build-settings.ts` knows, and removes `deployed.json`. It takes the instance's lock, writes atomically (`writeInstanceFile`), and prints the names it dropped. It runs on the local `minerva-cf`, `minerva-cf-staging` and `minerva-cf-test`. It touches no account.

## Risks

- Dropping a tombstone (a deleted class that then disappears from the exports) has not run on this account. It runs first on `minerva-cf-test` (A10). If the platform refuses it, the tombstone stays, which is harmless, and the drop waits for a decision.
- A reset is impossible between A6 and A10 on the test instances, since `reset-worker` refuses a tombstoned build. CI's monthly reset waits.
- After 0013, a deploy from a checkout older than 13c stops at the schema check (applied 0013 is not in its `migrations/`). A rollback goes through `cf`'s version rollback, which is safe: code from 13b on reads none of the dropped tables.
- The prune deletes any secret the build does not declare, including one set by hand. The values stay in each local `secrets.env` until unit 5.
- CI's token may lack a permission the guard or the prune needs (listing namespaces, deleting secrets or Workers). Its first run after A3 shows it, and the owner adds the permission (ci-account-suites.md, The owner's setup, step 2).
- Laravel's staging must not reach `minerva-cf-staging-files`. The engine stopped issuing download links in 13b, and staging downloaded a file after 13b's deploy, so none is expected (inferred).

## Amendments after opencode's review

opencode (`plan` agent) reviewed this design at `4673851` with seven findings. Each was checked against the code and against Cloudflare's pages on [Durable Object migrations](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/) and [rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/). Six hold in full or in part and are folded in below; they win over the body.

1. **No rollback across the tombstone.** Cloudflare refuses a rollback when a Durable Object class lifecycle change lies between the two versions. The risk "a rollback goes through `cf`'s version rollback" is wrong. Recovery after A6, A7 or A8 is a forward deploy from a checkout at unit 3 or later, whose exports keep `Workspace` deleted. Restoring a live `Workspace` export would only create a new, empty namespace.
2. **A read-only check before each migration that drops tables.** `deploy.ts` applies the migrations (`scripts/resources.ts`) before its schema check, so a surprise would surface only after 0013 has run. Before A2, A8 and every deploy that first applies 0013 to an instance with data, `node scripts/schema-check.ts --instance <name>` must pass at 0012 (staging and test did on 2026-10-16), and the agent records D1 Time Travel's current bookmark for that database (read-only, kept outside the repository) so that the owner could restore it. Unit 1's new case also puts rows in `recovery_conversations` (with `deleted_at` and `fact_seq` set) and `recovery_runs`, and asserts they are unchanged after 0013. The schema shows no foreign key from a kept table to a dropped one, so the drops cannot cascade into kept rows.
3. **Preservation, not reachability.** `test:deployed`'s probe uses fresh objects and a new namespace would pass it. Before and after A8 and A12, the agent records a digest of each kept namespace's id (`Conversation`, `Scripts`, `Sandbox`), the row counts of `recovery_conversations` and `recovery_runs`, and the identity row, and they must be equal. The owner's check in A9 also opens one older conversation per jurisdiction staging uses.
4. **External bindings block a deletion.** A deploy that deletes a class is rejected with `tombstone_delete_blocked_by_external_bindings` while any other Worker binds its namespace. The download Workers bind only R2, and no Worker in the repository binds `Workspace` or `FaultMailbox`. A rejection changes no Durable Object, but 0013 has run by then, which code from 13b on tolerates. A6 shows it first on the test instance; the unit then reads the referencing Workers from the deploy's output, and the owner decides.
5. **Dropping a stale tombstone is documented.** Once the namespace is gone, the tombstone is stale, every deploy prints a `stale_tombstone` notice, and Cloudflare lists it in `removable_entries`. Before A10, A11 and A12, that notice (or the namespace listing) is the evidence for each instance. The first risk is therefore smaller than stated. While a tombstone stays, resets stay blocked, so a stuck drop is not harmless and is raised with the owner at once.
6. **Only the retired secrets are deleted.** `laravelSecrets` declares `MINERVA_LARAVEL_TOKEN` and `MINERVA_STREAM_KEYS` only when the local `secrets.env` sets them (`cloudflare.config.ts:89`), so pruning every undeclared secret could delete staging's live token after one missing line. The deploy deletes only `MINERVA_ENCRYPTION_KEYS`, `MINERVA_DOWNLOAD_KEY`, `MINERVA_SETUP_KEY` and any `MINERVA_<APP>_CLIENT_ID` or `_CLIENT_SECRET`, when the build does not declare them. Any other undeclared secret is printed by name and left. After the deletion the deploy lists the names again and stops if a retired one remains. This step is temporary like the download Worker's, and unit 5 removes both. Whether `cf workers secrets bulk` deletes with a `null` value is not settled here: `cf`'s schema shows only a PATCH to `secrets-bulk`. Unit 2 tries it on `minerva-cf-test` in A2 and otherwise deletes one secret at a time.
7. **Production is reset after the tombstone is proven, from a pinned checkout.** A5 moves after A7. It runs from a worktree detached at unit 2's commit, which still exports `Workspace` live, kept until A13 passes. The agent records the reset's full output and its final line before going on. If unit 4 stalls, the fallback is `pnpm run deploy --instance minerva-cf` from that same worktree, which serves production again with an empty `Workspace` namespace that a later tombstone deploy retires.

Not taken: opencode's call for a pinned "retirement release" for instances that miss the tombstone. The four instances are all the instances there are, and each must show the evidence of amendment 5 before unit 4 lands. A new instance never had the classes.
