# Minerva architecture

Updated 2026-10-18. This repository is **Minerva's open harness**: the engine that runs an agent's turns on Cloudflare (Workers, Durable Objects, D1, R2, Containers), with its permission pipeline, its 20 connectors and its sandbox. Minerva the product is hosted; **self-hosting is not supported**. How to develop and deploy the engine is in [cloudflare/README.md](cloudflare/README.md); what each connector lets agents do is in [docs/connectors.md](docs/connectors.md); work in progress is planned in [docs/plans/](docs/plans/).

## Summary

The agent **never holds a credential and never decides its own permissions**. Each turn's commands run in a microVM with no network at all; the scripts it writes run in isolates with no network; every call to a connected app goes through a permission check that the user's grants decide, in trusted code that borrows the credential for that one call.

| Area | Choice |
|---|---|
| Runtime | One Worker (`minerva-cf`); a Durable Object per conversation, and per conversation's sandbox and scripts |
| Agent loop | pi-durable through PiHarness in the Conversation object: durable across crashes, with Minerva's tools, history and code mode |
| Sandbox | A Firecracker microVM per conversation (Cloudflare Containers), kept a few minutes between turns, no route out, hardened before any command runs |
| Code mode | Each script a Dynamic Worker with no network, no `env` and a CPU limit |
| Permissions | Layers that only narrow: provider account ∩ ceiling ∩ user ∩ agent, deny wins; checked on every call |
| Models | Workers AI, or OpenAI and Anthropic through the instance's AI Gateway (prompt logging off), behind our own request policy |
| Files | A folder per conversation: versions in the Conversation object, blobs in R2 (an EU-jurisdiction bucket for EU conversations) |
| Budgets | Every model call, script and container priced in micro-dollars; a run Laravel gives an allowance ends at its next model call once it has spent it |
| Interface | An internal API Laravel calls under `/internal/v1/` (behind Cloudflare Access), credentials leased from Laravel per call, facts delivered back to it, and a run stream browsers read with a token Laravel signs; one oRPC contract (`contract/`) |

## The engine and the product

Minerva is two systems ([docs/plans/product-and-engine.md](docs/plans/product-and-engine.md), decided 2026-10-14): **a private Laravel application decides what may happen; this engine does it and records what it did.** Laravel holds users, organizations, connections and their credentials, grants and agents as users set them, the run registry, the product transcript, billing and administration. The engine keeps execution: pi's loop, the sandbox, code mode, the connectors and the permission pipeline, each conversation's folder, and each run's attempts, write ledger and events, with an outbox of facts for Laravel and a recovery index in D1. It holds no users, sessions or stored credentials, and no transcript of its own.

Commands go one way, each idempotent: Laravel reads the connectors' catalog, starts and cancels runs, asks the engine to describe an account, list a connection's resources or check a grant edit, reads a conversation's folder and resolves downloads, and deletes conversations. The engine asks Laravel for a run's credentials one call at a time, reports a provider's refusal, and delivers its facts in order. There is one engine deployment per environment (production, Laravel's staging, and the test instances with fault points); a dedicated copy for an enterprise would be a second deployment, not a self-hosted one.

## Trust model

| Zone | Trusted? | Holds |
|---|---|---|
| Laravel | Yes: it decides what a run may do | Users, stored credentials, grants, the transcript; its Access service token and the engine's Sanctum token |
| Browser | Only for the run its stream token names, for at most five minutes (plus 30 s of clock skew) | A stream token |
| Worker and Durable Objects | Yes: our code and its dependencies | Secrets, all execution state, a leased credential for one provider call at a time |
| Sandbox container | **No**, hostile | The turn's files; no token, no route out |
| Script guests | **No**, hostile | One RpcTarget that queues tool calls |
| Model output, provider content, files | **No** | — |

**The agent loop is trusted code.** In Minerva's first version (Django, with the loop inside the container), a compromised loop reached nothing but a gateway. Here the loop runs in the Conversation object, in the same Worker script as the secrets and the executor, so the trusted code base includes pi-durable, pi-ai, the Agents SDK and their dependencies. A bug or supply-chain compromise in any of them runs with the Worker's bindings and secrets: it could address any conversation's objects, use the credentials Laravel lends for the runs it is asked to run until the provider expires or revokes them (API keys and some tokens never expire), and ask for more while runs keep starting. It never sees a refresh token, a client secret or Laravel's key, nor the credentials of connections that no run leases and no settings call carries. Model output cannot execute as host code: it reaches the loop only as tool names, arguments and text, which go through the permission pipeline. Code the model writes runs only in the container and in script guests, which hold nothing and reach nothing.

Mitigations: dependencies pinned with exact versions and lockfile hashes; a credential leased for one provider call and held in memory only, never stored in pi's state, events or logs; the model request built by our own provider wrapper, which refuses anything but text and image input and function tools (a defence in depth, since the request is not hostile). Moving the executor into a Worker of its own is open question 1.

## Data placement

Each piece of state has one authoritative home; everything else is an index that can be rebuilt from it.

- **D1** (one database per instance, primary near Frankfurt): the recovery index, `recovery_conversations` (a conversation's organization, workspace and jurisdiction, the highest fact sequence sent to Laravel, raised before each send, and when it was deleted and purged) and `recovery_runs` (a run's conversation and its start's input digest), written in one batch of conditional statements before any object is reached, and listed whole, a page at a time in order of id, by `listConversations` for Laravel's recovery after a restore; and `instance_identity` (the instance's name and kind, which deploys and resets check). The index's rows outlive the conversations they name. D1 has no interactive transactions; reads go to the primary (no read replicas). Migration 0013 dropped the engine's former account tables.
- **Conversation DO**: authoritative for the organization and workspace it is bound to (fixed by the first command that names it), `runs` and `attempts`, `run_events`, the write ledger (`run_writes`), each model call's and script's record (`call_records`, `script_records`), `page_tokens`, each start's preparation and answer (`internal_starts`, `internal_answers`), cancel `tombstones`, the `facts` and their delivery state (`fact_delivery`), `folder_versions` (manifests split into rows under 2 MB), the run's checkpoint, the script store, and pi's `pi_*` tables. Tables earlier versions wrote (`messages`, `starts`, `releases`, `start_keys`) stay, unused.
- **Sandbox DO**: authoritative for the container's lifecycle: incarnation id, owning run and attempt, hardening state, cleanup pending; and for container time: a span per incarnation and the runs it sealed (`container_spans`, `sealed_runs`; The sandbox lifecycle, Container time).
- **Scripts DO**: only its fence (`script_fence`): the newest run, attempt and script it has run, and whether that script ended, so a stale script or reset from a replaced attempt is refused after a restart too (Attempts and recovery, Fencing).
- **R2 `minerva-cf-files`**, and **`minerva-cf-files-eu`** (created in R2's EU jurisdiction) for EU conversations, which Laravel's all are: `blobs/<ws>/<conv>/<sha256>/<random>`, and `uploads/<ws>/…`, where the browser puts an attachment with a URL Laravel signed. Content is deduplicated within a conversation, not across conversations. A lifecycle rule deletes `uploads/` objects a day after they were written, used or not, so a folder never names one (Starting a run).

A conversation's data is therefore in databases of its own rather than in rows filtered by a key, and a command reaches an object only by typed calls after the recovery index has bound it to the command's organization and workspace; the Worker that makes those calls is trusted with all of them, and D1 and R2 are shared. The price is queries across tenants: objects cannot be queried together, so admin search, analytics and an audit log need a path of their own (open question 9), which the product plan gives Laravel.

**Addressing.** One module (`src/addressing.ts`) maps a conversation's workspace id and jurisdiction (from the recovery index, never from the command) to its objects (`jurisdiction('eu')` when set) and to its bucket, since the same name with and without a jurisdiction is a different, empty object. Laravel's conversations are created in the EU jurisdiction. The Worker never routes a request to a Durable Object by a client-chosen name without checking it; there are no generic Agent routes (`routeAgentRequest` is not used); objects are reached only through typed RPC from our own code. Local workerd has no jurisdictions (`jurisdiction()` throws), so with `MINERVA_DEBUG` on, and only then, an EU object is named `eu:<name>` in the plain namespace; a deployed build refuses `MINERVA_DEBUG`. Where an EU conversation's container runs is unmeasured: `durable_object` scheduling has no placement constraint, so the VM may sit outside the EU even when its Sandbox DO does not (open question 8). The deployed Worker's `/api/probe` (token-gated) reports each class's jurisdiction as the account tests see it.

## Permissions

A grant is **connection + resource kind + resource + actions**, allow or deny. A resource may be `*`, every resource of that kind including new ones. Allows on kinds or wildcards a connector no longer declares are ignored when a run starts; denies always apply. Laravel stores the layers and grants as users set them and never interprets them; it asks the engine to check a new concrete grant against what the account can see (`checkGrantEdit`), and removals never need the provider. Each connector's kinds and actions are listed in [docs/connectors.md](docs/connectors.md#permissions).

```text
effective = provider account ∩ workspace ceiling ∩ user layer ∩ agent layer   (deny wins)
```

The effective permissions are compiled once when a run starts, from the layers and the agent's connections `startRun` carries, and stored with the run (`gateway/policy.ts`, `gateway/grants.ts`, `gateway/tools.ts`).

An organization may also have a **connection policy** (`gateway/tenancy.ts`): the connectors it offers, each with the tenants it allows or any. Laravel stores it and sends it raw in `startRun`, `listResources` and `checkGrantEdit`, with each connection's tenant as `describeAccount` answered it. The compile offers tools only on the connections it admits: a connector it does not list is refused, and under a list a connection whose account is in no listed tenant is refused, as is a connector whose tenancy is unknown. For a connector with a tenant per resource the run snapshots the allowed tenants, and every resource a call touches or returns is checked against them. Without a policy nothing changes. A missing layer passes everything for the ceiling, allows nothing for a user until they choose, and inherits for an agent. Changing access, removing a connection or member, or changing an agent's connections makes Laravel cancel the affected active runs (Strict revocation).

Every tool call goes through one pipeline (`gateway/executor.ts`):

```text
strict argument validation
  → lease the connection's credential from Laravel for this call
  → provider consent (the connection's OAuth scopes)
  → connector resolves the real resources the call touches, checked against its declaration
  → permission check, then the connection policy's tenants
  → (writes) dispatch the write, one at a time per run
  → call the provider
  → (writes) settle: succeeded, not applied (forgotten, so it can be tried again), or uncertain
  → drop returned records the run may not see
  → return, with an opaque run-bound page token
```

- **Writes.** Identical writes within a run are deduplicated. A write the provider refused outright, or that never reached it, is forgotten. One whose outcome is unknown (a timeout) is uncertain and pauses the run's further writes (Writes, below).
- **Tokens.** If a provider rejects a connection's token, the engine reports it to Laravel (`reportUnauthorized`) with the generation of the credential it was lent, so a late report cannot mark credentials that replaced it; Laravel marks the connection **Needs reconnecting**.
- **Changed tools.** A run snapshots a fingerprint of each tool's declaration, its connector's tenancy included. If a deploy changes what a tool means, active runs lose it (`OPERATION_CHANGED`) rather than use it under old grants.
- **Tenants.** A call the grants allow on a resource of a tenant the policy does not allow fails with `POLICY_DENIED`, "Your organization does not allow this {label}."; a call the grants refuse gets their generic refusal, so the tenant is named only for what the run may otherwise use. Records of other tenants are dropped as records the grants hide are.
- **No caps on work.** A turn has no limit on writes, model calls or tool calls, so an agent can work on one prompt as long as it needs; a deadline per turn is optional (`MINERVA_RUN_TIMEOUT_SECONDS`).

## Connectors

A **connector** (`src/connectors/<name>/`, the contract in `gateway/connector.ts`) declares resource kinds, actions (with dependencies such as "create requires read") and operations. Each operation has a strict zod input schema and a `prepare()` step that resolves the real resources a call touches: `{ need }` for a concrete resource, or `{ enumerate }` for a listing filtered afterwards. The executor rejects a call whose requirements do not match the operation's declared needs, and a write that enumerates or names no concrete resource, so a connector mistake fails closed. Design notes for each provider are in its module's comments.

- **Canonical ids.** Grants and records use the id the provider lists. Aliases (`primary`, a differently cased address, a name) are resolved before authorization, so a deny cannot be bypassed under a wildcard allow.
- **Hierarchies.** A nesting kind (Drive folders, Notion pages, Linear sub-teams) carries each resource's ancestors. An allow on the resource, an ancestor or `*` allows it; a deny on any of them blocks it. Unknown ancestors never help an allow, and an incomplete chain is blocked by any exact deny for that action. The executor rejects malformed ancestry (wildcards, duplicates, a resource inside itself, more than 64 ancestors, ancestry on a flat kind). Connectors resolve ancestry again just before they read, list or create, refusing what moved in between (`FILE_MOVED`, `PAGE_MOVED`, …).
- **Several kinds.** An operation may need actions on more than one kind (an Outlook reply needs Read on a folder and Send on its recipients); records scoped to a kind without the operation's output action are dropped.
- **One write per operation.** A mutating operation sends one mutating request, only from `execute()` and only with time left. The executor judges the write by what the provider client recorded, not by what the connector returned.
- **Provider consent.** A connection starts with the connector's base scopes only. The catalog gives Laravel each operation's scopes, and Laravel's flow asks for the scopes of every allowed action (incremental where the provider supports it). Tools whose scopes are missing are not offered; a call made after scopes shrank fails with `CONSENT_REQUIRED`.
- **Tenancy.** Each connector declares how its resources belong to organizations, which connection policies limit: one tenant per account (Google's Workspace domain, Microsoft's Entra tenant, Slack's workspace, HubSpot's, Intercom's, Notion's, Linear's, Stripe's and Sentry's account or organization), which `account()` names; a tenant per resource (Jira's and Confluence's site, Xero's organisation, a GitHub repository's current owner by numeric id), which every resource, record and discovery item names from what the provider answered for that call; or unknown (Todoist, the Web). The executor refuses a need, and drops a record, of a connector with a tenant per resource that names none. A tenant per account limits which accounts are used, not what is shared into them.
- **Connections** belong to a workspace in Laravel and are personal (the user's own OAuth, so the provider's permissions also apply) or shared (an admin shares one they own, and each member uses it under their own layer; built in the app's chunk 11). Tools are namespaced per connection, and the executor routes each call to a connection it chose, never one named in model arguments.
- **OAuth apps.** The catalog gives each connector's OAuth descriptor (its client's name, endpoints, scopes, PKCE). Laravel registers the clients, runs the flows and refreshes tokens through the client that issued them; the engine holds no client. Todoist's client is registered dynamically. API-key connectors (Stripe) and built-in services (the Web) use the same contract.

Content from providers and web pages is untrusted input to the model. Filtering what agents see does not neutralize prompt injection; it bounds what an injected agent can reach.

## Protocols

These are the parts most likely to be subtly wrong. Each has fault-injection tests (Testing).

### Starting a run

Laravel registers a run under the conversation's lock and sends `startRun` with the same run id until it is answered. The command carries the user's message, its attachments (staged uploads), the conversation's recent messages, the agent's instructions and connections, the raw layers and grants, and the run's allowance when Laravel gives one (Budgets). A start is answered with an acceptance or a refusal, and either answer is stored, so a repeat gets it again; an error stores nothing and is answered 500 or 503, and Laravel sends the start again.

1. **The recovery index first** (`internal/recovery.ts`): the conversation's row is inserted on first use with the command's organization and workspace, and the run's row with its conversation and the digest of the command's input, in one D1 batch read back before any object is reached. A command naming another scope is `SCOPE_MISMATCH`, another input for the same run `IDEMPOTENCY_CONFLICT`; every write after the conversation's insert is conditional on the scope, so a refused command binds nothing. No run executes without its row.
2. **The binding.** The Conversation DO, addressed through the index's jurisdiction, binds itself to the organization and workspace on first use and refuses a command that names others. A stored answer for the run id is answered again as it is.
3. **Refusals before any attachment is measured or copied,** each stored as the run's answer: a tombstone for the run (`CANCELLED`), the conversation deleted (`CONVERSATION_DELETED`), another run active or prepared (`CONVERSATION_BUSY`), more than 10,000 facts not yet acknowledged (`FACTS_BACKLOG`), no text and no attachment (`EMPTY_MESSAGE`), and the attachments' own checks (too many, one twice, a key outside the workspace's staging prefix).
4. **The preparation**, written once: the run's snapshot compiled from the command's authority (`gateway/tools.ts`, `startSnapshot`), the catalog's and the compiler's versions, the snapshot's digest, and the history selected and clipped by `conversation/history.ts`, which only the conversation's first run reads (The harness). A start sent again after a reset or a failure finds it and uses it, so a run compiles once. A preparation also makes the conversation busy for any other run until the start is answered or cancelled.
5. **The attachments**, measured and never trusted: each staged object's size is read first (missing, different from the declared size, or over the file limit is `ATTACHMENT_UNAVAILABLE`), then its bytes are counted, hashed and sniffed for their media type, then copied by the folder: for each contents the conversation does not hold yet, it records a loose blob key `blobs/<ws>/<conv>/<sha256>/<random>`, then puts the bytes there with their SHA-256, which R2 checks, so an object replaced since it was measured fails the copy. The folder then names only the conversation's own blobs, never an `uploads/` key, which the lifecycle rule deletes a day after it was written. Loose keys a crash left unclaimed are deleted by an alarm.
6. **One transaction:** a tombstone that arrived meanwhile makes the start `CANCELLED`, a deletion `CONVERSATION_DELETED`, another active run `CONVERSATION_BUSY`, each stored. Otherwise it commits the attachments into a base version, stores the run with its snapshot, its allowance and its turn (the history and the prompt: the message, a note naming the attachments as the folder now holds them, and a note with the run's start time in UTC, `[The user sent this message on Monday, 2026-10-19 14:03 UTC.]`), appends the `queued` event and makes the run `provisioning` (Laravel registered it before it sent the start), pushes the run's watch and deadline jobs, stores the acceptance and deletes the preparation.
7. **Then** the run's loop starts, and the staging objects are deleted.

The acceptance names the catalog's and the compiler's versions, the snapshot's digest and the run's authorized set (the connections the snapshot's tools reach), which Laravel keeps with the run. The snapshot holds the policy layers, tool refs and fingerprints, instructions, model alias, base folder version, attachments, start time and deadline. The instructions hold no time, so they are the same from run to run and a conversation's requests keep their cached prefix; models do not know the date, so the start time rides in the turn's prompt instead. Laravel's bound on an unanswered start is a `cancelRun` with `start_expired`, which the object orders against the start: if the start committed first the run is stopped, and if the cancel did the start is refused.

### Strict revocation

Laravel commits a change of authority (a grant or layer edit, a removed connection or member, an agent's connections) under the same lock as its starts, with a cancel for each affected run that is starting or running, and sends `cancelRun` until it is acknowledged. The engine's acknowledgement is the enforcement point.

1. `cancelRun` goes through the recovery index as a start does, binding the run to its conversation if no command named it yet, so a cancel can never fence a run in one conversation while it runs in another.
2. For a stored run that is active, the Conversation DO sets the run's local `revoked` flag and ends it in one transaction, with "Stopped because permissions changed." for a revocation or a removed member, and "Stopped." for a plain cancel or a deletion; it answers `cancelled`. For a run that has ended it answers `cancelled` if a cancel ended it, else `ended`.
3. For a run it has not received, it writes a tombstone with the reason, deletes the run's preparation if any, and answers `tombstoned`: a start in flight finds the tombstone in its final transaction and a later one in step 3, and both are refused `CANCELLED`.
4. Every answer is returned only after its change has committed, outside pi's transactions, so a rollback of pi's cannot undo an acknowledged cancel.

The executor checks the local `revoked` flag and the run's state synchronously, with no await in between, immediately before it dispatches any provider request, and again before it returns a result. Once Laravel is told the cancel is done, no new provider request starts under the old permissions; a request already sent may complete ("no further effects", not rollback), and a write in flight settles and is recorded. Laravel refusing the run's next lease is a second guard, not the enforcement.

A container parked for the conversation's next run (The sandbox lifecycle, Parking) is left parked by a revocation: it holds no credentials, and the next run's grants are compiled anew at its start. Deleting the conversation destroys it.

**Emergency stop.** Busy objects keep running their old code for minutes after a deploy, so a security fix cannot rely on a deploy reaching running turns. The stop is Laravel's alone (chunk 14c): an instance admin's Emergency stop page in Laravel's admin, or `minerva:stop`, closes a one-row admission flag that every start reads before any other lock and every lease reads too, then requests a cancel with `emergency_stop` for every run starting or running and sends them through the cancel path above; reopening sends the engine nothing. The engine is unchanged: it ends each run as it ends any cancelled one. `admission` stays declared in the contract, answered 501 and unused, and `ADMISSION_CLOSED` is never sent.

### The harness

PiHarness (`agents/harness/pi`, agents 0.28.0) runs pi-durable 1.3.0 in the Conversation DO, which extends the Agents SDK's `Agent` and attaches it with `this.lifecycle.use(...)`; pi's tables live in the object's SQLite. Requirements, each from the spike:

- `settings.contextRetentionMs: 0`, since pi otherwise keeps every object active, and billed, for 10 minutes after each turn;
- one extension, `minerva`, registers the tools; one pi conversation per Minerva conversation, which every run continues, so the model sees the whole conversation, tool results included. Its id and provider session are on the conversation's row (`conversation.pi_session`, `pi_provider_session`), and each run copies them onto its own (`runs.session`, `runs.provider_session`) when it claims the conversation's pi conversation, in the same write that names a new one (`store.claimSession`), so admission, the gate and the stops keep reading the run's row. The conversation's first run creates it (`pi.createConversation`) seeded with the history Laravel sent with the start (`conversation/history.ts`: the latest 20 messages, each clipped to 30,000 characters, newest first within 120,000); a conversation from before has none on its row, so its next run creates one the same way. Each run then sets its instructions with `configure()`, which records nothing when they are unchanged and otherwise patches the instructions' section at pi's next request, and submits its prompt once with `operationId: run:<id>` (idempotent). Steers and follow-ups (`whenBusy`) work and come later;
- the model through our provider wrapper (below), never `createAI`'s default AI Gateway, which logs prompts;
- tools honour `context.abortSignal`.

**Model.** pi-ai, with Workers AI by default (`@cf/zai-org/glm-5.3-flash`: all 10 models tried made the right calls; this one was the cheapest, about $0.00015 for a two-read, one-write turn) or an OpenAI or Anthropic upstream, both through the instance's own AI Gateway with prompt logging off, so no model key is in the Worker. Model settings come from configuration (`MINERVA_MODEL_*`), and the model's prices from models.dev at deploy; each call is admitted against its run's budget at its record and charged at its settlement (Budgets). The wrapper forces the model, the output cap and `store: false`, sends only text, images and function tools, refuses hosted tools, stored-item references and file inputs, and taps the stream for deltas. It refuses a tool call whose finished arguments are not a JSON object even after pi-ai's repair, such as one cut off mid-value, as pi-ai's own stream parsers do since 1.3.0: createAI's chat path (Workers AI, OpenAI's chat API) and the fake model still keep partial-json's reading of the text's prefix, a plausible but wrong value the tool would run with. Images reach the model through pi's `read` (a file the user attached is in the conversation's folder): the model pi sees takes images when its upstream does (Workers AI and OpenAI models as pi-ai's catalog says, an OpenAI model it does not know and every Anthropic model always), at most 2000 pixels a side and 1.5 MB of base64, since pi keeps a tool's result in one SQLite row and a row holds at most 2 MB. A larger image is shrunk by the Images binding (`src/conversation/images.ts`), outside the isolate: pi-durable's own processor, Photon, decodes in WebAssembly memory, 241 MB for a 12-megapixel photo. A model that takes text only gets pi-ai's placeholder instead of each image. No provider text reaches pi's state, its events or the logs: a failure's text is replaced (a context overflow by our own words that pi-ai still classifies as one, so pi compacts and asks again), createAI's diagnostics, which copy it, are dropped from every message, and the log gets the failure's kind, status, class and createAI's code.

**The prompt cache.** createAI sends pi's provider session as `prompt_cache_key` on the Responses API (clamped to 64 characters) and as `x-session-affinity` on Workers AI, summary calls included, so the key is one per conversation. A request renders the tools, then the instructions, then the conversation's turns, and the first two stay the same from run to run while the user's connections, grants and agent do (the instructions hold no time, Starting a run), so a later turn can read the earlier turns' prefix from OpenAI's cache, which keeps an entry at least 30 minutes after its last use. A revocation, a new connection, an edited agent or a compaction changes the prefix once. The key is not one per agent: OpenAI's guide says it is not needed for caching on GPT-5.6 and later and that separate keys guard against cache-hit probing across users, and the tools, which differ by user, come first, so a shared key would gain at most a new conversation's first call. On a test instance with `gpt-6.1-sol` (2026-10-19), a 10-turn conversation with no pause read the cached prefix on every first call from its second turn on, and cost 72% less than with a pi session per run, whose calls read no cache across runs. On staging the same day, twelve short turns of one conversation each read about 99% of their 7,200 or so input tokens from the cache from the second turn on. A turn after the entry lapsed writes the whole retained context to the cache again, up to about 108,800 tokens (about $0.27 on `gpt-6.1-sol`), where a session per run wrote only its seed of 20 messages. Users often return hours later, so on a long conversation such a turn can cost more than before. It is not measured.

**Compaction** is pi's own, inside the run that needs it, with no instruction of ours to its summarizer (`PI_SETTINGS` in `conversation/pi-work.ts`). Before each model request pi estimates the context: the newest call's reported usage, plus 3.5 characters a token for what came after it. Above the context window less `reserveTokens` (19,200, 15% of `CONTEXT_WINDOW`'s 128,000) it first summarizes all but about the newest `keepRecentTokens` (38,400, 30%). These are the ratios Cloudflare OS uses: room for the answer (8,192 tokens by default) and the estimate's error, and more of the newest work kept word for word than pi's defaults (16,384 and 20,000). The cut walks back that far, then forward to the next user or assistant message that does not separate a tool call from its result, so it can fall inside the run, before or after its own message, and a large tool round followed by a message is summarized whole, its result clipped to 2,000 characters for the summarizer. The summary is one model call through the wrapper, admitted and charged as the run's and recorded as a summary (Attempts and recovery). pi puts it back as a user message and keeps every entry in storage. A request that overflows anyway is compacted and sent again only when its generation has not compacted yet and a cut exists. pi's retries are off, so a failed summary fails the run, which then ends `failed` with the code `compaction_failed` and "This conversation has grown too long, and its earlier turns could not be summarized. Try again, or start a new conversation." A request that still overflows when pi will not compact again (no cut, or a compaction already in its generation) ends it with `context_overflow` and "This turn needed more than the model can read at once. Try a smaller request, or start a new conversation." `unansweredEnd` (`conversation/events.ts`) reads both from pi's detail, `Compaction failed: …` or the wrapper's overflow text, and every other unanswered turn ends `worker_failed`; the log gets pi's reason and detail, which hold only the wrapper's texts. The next run continues the compacted pi conversation, estimates again and compacts again if it must. On `gpt-6.1-sol` a compaction near the threshold cost about $0.13, the summary call and the next call's cache write together, and its summary used under 300 output tokens with no reasoning (measured on a test instance, 2026-10-19).

**The note after a stopped turn.** A turn that did not complete stays in the pi conversation as far as pi had it, so the next run tells the model how it ended, or the model may carry on with what the user stopped. Its section, after the settle, walks back over the runs before it, at most 20, to the newest whose `run:<id>` submission pi holds, or to the first run that names the pi conversation, whose seed already has the messages before it. The run's input then starts with bracketed paragraphs (`turnNote` in `conversation/history.ts`): that turn's end (stopped by the user, stopped because permissions changed, out of time, or failed, each with "Do not carry on with it unless the user asks you to."; or an answer that never reached the user), then each later message pi never received because its run ended before it submitted, oldest first, quoted while its run's snapshot is kept, clipped as history is and closed by "[End of that message. Do not act on it unless the user asks you to.]". Nothing follows a completed turn. The note rides in the run's own input rather than a second submission, so each run still submits once to an idle session (A run's work in pi, below), and a section that runs again computes the same note. Laravel's transcript never holds it.

**A run's work in pi** is its operation: its `run:<id>` submission and the tasks pi made for it, which are the tasks in its session that are not background ones and have ids above the submission's (`belongs` in `conversation/pi-work.ts`). The acting run's operation owns its work. Every other live task pi holds is orphaned. The rule rests on three facts: pi's ids ascend in commit order, a run's first generation is made in the commit that places its submission, and no run submits while another run's non-background work is live (the start's wait, below). Minerva makes no background work (`compaction.backgroundTokens: 0`), and a unit test fails if that changes.

**Admission by run.** A tool call is admitted only for the active run, from that run's pi session, while its submission is `placed`, and from a task whose id is above the submission's (`admitTool`). The fence is checked after pi's read, so a run that ended during it is refused. The connector tools, `run_script` and the local tools ask through one `ToolHost.current`, and a refused call answers "This run is no longer active." without running. A model call is admitted in two steps. The wrapper's synchronous `begin` refuses it unless the active run's provider session is the call's and the run's fence is current. Then `record`, awaited before the call's record and its request, refuses it unless the run's submission is `placed` (`admitModel`), and a refused call is neither recorded nor counted. pi gives a model call no task, so the operation's state is the rule. That is enough because a session's model calls come only from the generation that holds its live run and the compactions that generation owns, and the start's wait and the cleanup at open (Attempts and recovery) leave no other generation live. pi's retries are off, so a generation whose call is refused ends at once, its submission `unanswered`.

A call that answers after its run ended is refused, and logged once at warn level without its arguments or result: `run <A>'s call <tool> answered after the run ended; its result is refused (run <B> acts now)`, or `(no run acts now)`. A connector call or a script's call logs it in `#invoke`, inside `store.outside`, where its `tool_call` event is not appended. A local tool logs it once its checkpoint has released the result (`local:released`). A write such a call sent still settles in the ledger.

**The start's wait.** A run's start runs as a section in `PiStops`'s lane (`conversation/pi-stops.ts`). A section runs once every section queued before it has ended, whether it threw or not, so no start configures pi or submits while an earlier one is between its checks and its submit. The section checks that the run acts, checks its fence and takes the run's end signal in one synchronous stretch, so a run that ended while its section was queued stops there. It then starts the attempt and its phase, and settles. The settle marks every orphan, background ones included, and waits until no non-background orphan is live (Attempts and recovery, Stopping pi). The run's end cuts the wait short, and the section then configures nothing. After the wait it checks the fence again, installs the run's tools, claims the conversation's pi conversation (the conversation's first run creates it), configures the run's instructions on it, reads the note after a stopped turn, checks the fence once more, prepares its container and submits. A start, `onStart`, the `watch` job and `#recover` start the section without awaiting it, since it can wait until the bound and Lifecycle drives due jobs one after another. When nothing is left, the wait costs one `pi.inspect()`. A start claims its session after the wait, so the wait also reads the run's submission only when an earlier start of the run claimed a session and did not submit.

The bound is 30 s (`PI_SETTLE_MS`; the test build reads `pi_settle_ms` from its fault plan), counted from when the section is queued, so it covers the lane and the wait. A section whose bound passed in the lane never runs. When the bound passes while the section still waits and its run still acts, the object logs at warn level `run <B> could not start: pi's earlier work did not end within 30 s`. It pushes `watch:<run>` due now through `store.outside`, which keeps the job out of pi's transactions, and then syncs. It resets only if the run still acts after those awaits. A push or a sync that fails is logged and the reset still happens, and the run's earlier watch then opens the next instance within 20 s. The reset ends every invocation that held the wait. The next instance's gate finds the run with no submission and counts no attempt, its cleanup at open marks the orphans before pi resumes, and the start runs again. pi's abort handlers for generations and tool tasks are single commits, so one reset ends the work that held the wait.

### Attempts and recovery

pi has no restart limit and no notion of Minerva's attempts, so the Conversation DO keeps them. The first execution is attempt 1; there are at most 3.

Measured with 112 injected deaths across tool, model-stream, factory and submit crashes, memory-limit resets and caps, plus controls; reviewed adversarially:

- **Where the gate runs: first in PiHarness's harness factory**, before `Harness.open`. pi exists only once the factory returns, and every event that opens pi (alarms, requests, RPCs) goes through it, so nothing of pi runs before the gate. The constructor is not usable: the platform sometimes builds an instance, never delivers it an event and discards it (6 times in about 115 restarts), and a constructor counter counted each of those as an attempt.
- **What counts as a restart:** the factory running in a new instance while an *activated* `provisioning` or `running` run has unsettled pi work, read by the run's operation (The harness; `piWork` in `conversation/pi-work.ts`). The run's own submission (`storage.submissionByRequest(conversationId, "run:<id>")` on the factory's `storage`) is read first. With none, the run is `not_submitted` whatever its session holds, so a run that never reached pi gets no attempt for work another run left. A queued or placed submission is work in progress. A done or unanswered one is in progress only while a task of the run's own is live. One scan per live status (`storage.scanTasks`, filtered to non-background tasks, newest first) reads the newest such task, which counts only when its id is above the submission's. A leftover background task never counts. It is orphaned, and the cleanup at open marks it. Queued runs belong to the start protocol: they get no attempt and no marker, and are never submitted to pi before activation. A settled submission with no live task of its own is no restart; the run is reconciled from pi's record. PiHarness's own `pending()`, `busy()` and `sessions.list()` cannot be used here: they wait for the open in progress. Controls that must not count, and did not: a turn, idle hibernation and a second turn; an 11-minute tool across 24 alarms; a 150 s model retry handed to the alarm; a redeploy during a turn.
- **The gate's decision**, in one `transactionSync`, then `await ctx.storage.sync()` before `Harness.open`, so a crash right after the gate cannot lose the count: if the deadline has passed, the run ends as `timed_out` ("The run took too long."); if this would be attempt 4, or under 30 s remain, it ends as `worker_exited` ("The worker stopped unexpectedly."); otherwise the attempt is incremented and the restart marker `{status: "provisioning", attempt: N}` appended (then `running` when the loop resumes), before pi does anything. The once-per-instance flag is set only after the decision is committed, so a factory that throws retries the gate on the next event.
- **Stopping pi** (`PiStops`, `conversation/pi-stops.ts`). A stop marks each orphan, a live task the acting run's operation does not own (The harness), with `pi.abortTask`, so the active run's work is never touched. It never aborts a whole pi conversation and never withdraws a submission. A mark reads `pi.inspect()` first and the acting run's operation second, so a submission committed between the two reads has no task the mark could take for an orphan. It starts every mark in one synchronous stretch, background tasks included, and does not await them, since an `abortTask` waits for the run invocation it saw, which may ignore its signal. A run's end (deferred), the reconciliation of a run pi settled while the object was away, and retention's abort of a session (that session's tasks only) mark. Deletion settles. A settle marks, waits with `pi.waitForTask` until one non-background orphan has ended, and repeats until a mark finds none. Deletion's settle has no bound, as pi's whole-conversation abort waited before chunk 19a. A start settles in its section (The harness). pi settles an orphaned placed submission `unanswered` in the commit that ends the generation holding its run, so no submission needs a wait of its own. `waitForTask` resumes pi's scheduler, so nothing settles before PiHarness has resumed pi.
- **The cleanup at open.** After `Harness.open` and before the factory returns, so before PiHarness's `pi.resume()` (`Harness.open` itself resumes nothing), the factory marks every orphan: the work of runs the gate ended, of cancels and revocations while the object was away, of sessions no run names, and background tasks. It marks in one synchronous stretch, so the paused scheduler reserves nothing meanwhile, and withdraws nothing. With no invocation to join yet, each mark resolves once committed. The factory awaits them with `Promise.allSettled` and logs a failed one, which never fails the factory, since every later event would run it again. It fires no fault point and waits for nothing else. The abort handlers run after `pi.resume()`. A platform test resets the object at a cancelled run's stop, before its mark. The next instance marks both of the run's tasks, and pi starts no tool or model call of the run afterwards (`protocols.test.ts`). Measured before chunk 19a, when the cleanup also withdrew queued inputs, the tool result read "was aborted", the submission ended unanswered, and PiHarness's wake job and alarm were cleared. Deleting the wake job is not a stop (pi resumed on the next request), and `session.reset()` is not either. As a backstop, admission refuses calls of any run but the active one, and the model wrapper and the executor refuse calls for attempts that are not current.
- **A start that crashed before pi had its input** has no wake-up of its own: a Lifecycle job (`watch:<run>`, 20 s) wakes the object. `this.schedule()` did not fire in the spike.
- **Timing.** The gate costs nothing measurable; recovery waits for PiHarness's 30 s heartbeat (p50 29 s, at most 60 s), so a crash in a run's last minute usually ends it. pi's retry delays stay at or under 60 s, so a long wait is never mistaken for a restart.
- **Deploys** usually leave a busy object on its old code until it is idle, but the platform can reset a busy object on a code update; that counts as a restart, whatever the cause.
- **Not covered:** a deterministic crash before the factory (in the Agent's own start-up or `openPiSessionStore`) would repeat without being counted; pi does not run in such an instance.
- Writes the dead instance left `dispatched` are marked uncertain by the gate, in the same transaction as its decision (Writes); nothing waits in the gate, which runs under `blockConcurrencyWhile`'s 30 s limit.
- **Replay cap:** safe tools are wrapped with a per-call execution counter in SQLite; a call replayed more than twice is answered with an error instead of running again.
- **Fencing:** every asynchronous operation (a model call, a tool call, a credential lease, a script and its reset, a sandbox command, a checkpoint, an event append) carries the run id and the attempt it started under, and is refused when either is not current. The exceptions are settling a write that an older attempt already dispatched, settling a model call's record and ending a script's record, which happen whichever attempt is current; the records themselves are made only under a current fence. Laravel knows runs, not attempts, so the Conversation DO checks a lease's attempt before and after asking for it; the Scripts DO keeps the newest run and attempt it has run a script under and refuses a reset from an older one, since a reset aborts every guest it loaded.
- **Model calls and scripts are recorded before they start.** The model wrapper records a call (`call_records`: its 8-hex id, drawn again on a collision within the run, the attempt, the instance that sends it, the route, its reservation, the route's rates and the price table's version it was admitted at, and whether it writes a compaction's summary) in one change with the fence check, the budget's check (Budgets) and `runs.model_calls`, before the request; a fence no longer current refuses the call with "This run has ended." and counts nothing. It holds the upstream's terminal event until the record is settled, once: `reported` with its usage, `refused` at zero for a 4xx with no answer, or `unmetered` at its reservation, cause `no_usage` (an answer without a usage report), `stopped` (no answer, stopped by the run or pi) or `failed` (no answer otherwise, or a status other than a 4xx). The reservation is the context window pi is told (128,000) and the call's output cap (`model/policy.ts`, `reservation`): what an unmetered call is counted and charged at, by rule, not a bound on what a call can cost (Budgets). `run_script` records a script the same way before it runs, refused with "This run has ended." when the fence is not current, and ends the record at the time the script answered, before the result is rendered. The run's sums move with a call's record and its settlement. A settlement or an end that throws resets the object before pi hears the answer, so a record open in a live instance always belongs to a call or a script still under way.
- **The restart rule.** Each instance has an id (`RunStore.instance`, which also tags the stream's sockets). A Durable Object has one live instance and a reset ends the old one's work, so a record another instance left open belongs to one that is gone. `settleLost()` settles each such call `unmetered`, cause `lost`, at its reservation, and ends each such script at `min(now, started_at + timeout_ms)`, estimated; it never touches this instance's own records. It runs first in `#recover`, outside pi's transactions, and first in every settlement job.
- **A run's retention** (`conversation/retention.ts`). 30 days after a run ended, once it is settled and no write of it is still dispatched, the `retain` job deletes its own records: its events, its snapshot (`runs.snapshot` emptied, `run_snapshots`), its attempts, the replay cap's counts, its saved arguments, its call and script records, its write ledger and page tokens; then, when it has a pi session of its own, that session's rows, through pi's own indexes (`conversation/pi-tables.ts`), since pi-durable has no delete call. The conversation's own pi conversation (`conversation.pi_session`) goes only with the conversation's purge: a run that names it ends with its records, and the orphan drain never takes it. `runs.prune` records how far it got (`records`, `pi`, `done`), in the transaction of each step of at most 500 rows. Its row, its stored answer and its tombstone stay until the conversation is destroyed, so a start sent again gets its acceptance and a cancel `ended`. From the first step `RunStore.snapshot()` throws (only an acting run reads it). A stop never reads a pruned run, since it reads only the acting run's operation (Stopping pi). A session with live work has its live tasks marked through pi, without waiting, and is skipped for the rest of the pass; an unknown pi schema (not version 1) stops only the pi stage, so runs wait in `pi` while the others' records still go. A run's end makes the job due 30 days later. A pass also drains the pi sessions no run names, which a reset between `createConversation` and `claimSession` leaves: only while no run is active or prepared, since only an acting run's loop creates sessions, re-checked in the step's own synchronous stretch.
- **A run's settlement job.** `finish` pushes the Lifecycle job `settle:<run>` in its transaction for a run with `metered` set (every run this code inserts; a run an older version inserted is never settled), and `#recover` pushes it again, after `settleLost()`, for every metered run that ended and is not settled, so a job a reset lost is made again. The job settles what a gone instance left open; asks again in 5 s while a call or script record of the run is open (one the end cut, which its own stream or script settles); seals the run in its Sandbox within 10 s (`RPC_WAIT_MS`), asking again 30 s after a seal that failed or timed out, as it does while a Sandbox still runs code without `seal`; asks again at the earlier of 30 s and the cutoff of a span still open short of it (The sandbox lifecycle, Container time); then, in one change outside pi's transactions, writes `run.settled` from the run's records and the seal's spans and sets `runs.settled_at`, unless that is already set or a record is open again. A crash at any step leaves the job, which starts again from the first step, so the run gets one `run.settled`. Every ended run seals its conversation's Sandbox, chat-only runs included, which creates that object.

What the user sees: if a turn's instance dies mid-answer, the next attempt picks the answer up from pi's last commit, the chat drops the earlier attempt's streamed text, a read that was cut off runs again, and a write that was cut off does not (the model is told and can check; asking for the same write again gets the first one's outcome). The folder goes back to its last checkpoint.

### Budgets

A run that Laravel starts with an `allowance`, in integer micro-dollars (µ$), stops once it has spent it. Laravel's side, an organization's monthly limit and the allowance it gives each start, is the Budgets section of `docs/architecture/turn.md` in the app.

- **The price table** (`budget/prices.ts`). The route's token rates come from models.dev: the deploy, and a reset's build, read the configured model under its provider in models.dev's `api.json` (`scripts/model-prices.ts`: dollars per million tokens as whole µ$, rounded; a `context` tier as `above`, the rates for a call whose input passes its size; a missing cache rate at the input rate), print them and give the build `MINERVA_MODEL_PRICES`, which `config.ts` parses. It is not a setting, and a `vars.env` cannot set it. A deploy stops when models.dev cannot be read or has no cost for the model, and a deployed build refuses a route without prices, so every call it makes is charged; the test build adds the fake model's in code (`faults/prices.ts`: 1 µ$ a token). Container time (`standard-1`, 74,016 µ$ an hour) and scripts (2,000 µ$ each and 72,000 µ$ an hour of wall time) are in code, from Cloudflare's pricing pages, since no catalog lists them. All are list prices without included allowances. The table's version is 16 hex of SHA-256 over its canonical JSON. The catalog publishes the table and its version as `prices`; the catalog's own version stays its connectors'.
- **Charges.** A call is charged when its record settles, at the rates its record kept when it was admitted, so a deploy that changes prices mid-run never leaves a call without a price: a reported call its uncached input, cache reads, cache writes and output (reasoning inside it) at their rates; a refused call (a 4xx) nothing; an unmetered one (`no_usage`, `stopped`, `failed`, `lost`) its reservation at its rates, by rule (337,920 µ$ on production's and staging's route, OpenAI's `gpt-6.1-sol`: 128,000 input and 8,192 output tokens at models.dev's $2 and $10 a million; 23,296 µ$ on the build's default, Workers AI's GLM, at $0.15 and $0.50). A script is charged as it ends, `perScript` plus its wall time, and a run's container time once, at `run.settled`, from the Sandbox's spans; both at the table the build has then. Each charge is rounded up once, when it is made, and totals are sums of charges. A call's charge and a script's are added to the run's `spent` (`runs`, Conversation migration 12) in the change that settles or ends them, the restart rule's included. These are Minerva's charging rules, not the providers' invoices.
- **Admission.** For a run with an allowance, the call's record (Attempts and recovery) checks the budget in its change, after the fence check. It first settles what a gone instance left open (the restart rule), since an attempt pi resumes can reach its first call before the object's recovery has charged the previous instance's lost call. It then compares the run's spend so far with the allowance: `spent`, each open script at `perScript` plus its time so far, and container time since `runs.container_since`. That is set once, through `outside`, before `LocalRun` asks the Sandbox for a container, so it overcounts a little (a container that died unnoticed included), which only stops a run sooner; `run.settled` charges the spans instead. An open call is not counted, since pi makes one model call at a time. A run without an allowance is never refused. Nothing else checks the allowance: scripts, local calls and connector calls are not refused for it, and the next model call after them is. The check adds about 10 µs a call.
- **The budget's end.** At or over the allowance, the run ends in that same change, `failed` with the code `budget_reached` and "This conversation reached its budget.", and nothing is recorded or counted; the wrapper answers the call with "This run has ended.", and the end marks pi's orphaned work for abort and destroys the container as every end does. `run.finished` carries the code (Facts).
- **Not a hard limit.** A run can pass its allowance by what is in flight when it crosses it: the model call that crossed it, the tool calls that call asked for, and its container's time until the run's end destroys it. A run whose crossing call is its last completes over budget, since no check follows.

### Writes

The write ledger lives in the Conversation DO's SQLite (`gateway/ledger.ts`). The write key (SHA-256 of the label `minerva:write-key:` and the RFC 8785 canonical JSON of the tool and its normalized arguments; query hashes, operation fingerprints and folder-version digests hash the same way under labels of their own, `lib/canonical.ts`) is claimed before dispatch; one write is dispatched at a time per run, with its deadline fixed at dispatch; refused writes are forgotten, applied ones recorded (with `applied_without_result` when the response was unusable), unknown outcomes marked uncertain, which pauses every later write in the run; writes still dispatched 30 s past their deadline are marked uncertain by an alarm. A write is dispatched by the instance that may die, which can then never settle it, so the restart gate marks every write of the run still `dispatched` as uncertain in its own transaction, and the new attempt's later writes pause. Deduplication is by key within the run, so it also catches a model that retries an interrupted write under a new pi call id (measured in the spike). A write settles in the DO that dispatched it, under `ctx.waitUntil`, even if the tool call that asked for it was cancelled. A claim and a settlement are made only while no asynchronous transaction of pi's is open on the object's storage: one made inside it would roll back with it, and a claim the executor was told was dispatched would leave nothing for the restart gate to mark uncertain. The same holds for every change someone acts on once it is made: a revocation, a cancel, a start, a run's end, the attempt gate's decision, a call's `tool_call` event, the replay cap's count, a model call's record and its settlement, a script's record and its end, the restart rule's settlements and a run's `run.settled` all go through `outside` (`conversation/store.ts`), which waits until no such transaction is open and makes the change with no await in between. Only progress (deltas, phases) may run inside pi's transaction; rolled back with it, it was never announced either.

### Credentials and refresh

Laravel stores the credentials, refreshes them and runs the OAuth flows; the engine never holds a refresh token, a client secret or Laravel's key. A run's connector call leases its credential from Laravel (`leaseToken`, with the run, the attempt and the connection; `conversation/laravel-runs.ts`):

- The fence is checked before the lease is asked for and again once it arrives, as for every asynchronous operation (Attempts and recovery, Fencing). Laravel refuses a run that is no longer active and a connection outside the run's authorized set.
- The lease holds the secret (an access token or an API key; a built-in service gets none), its scopes, its generation and its expiry when known, in memory, for that one call. It is never written anywhere or logged. A lease whose token expires within 60 s is asked for once more, then refused, so a call never starts with a token about to lapse.
- A failure worth retrying (no answer, a timeout, a 5xx) is asked again twice, 250 ms and 1 s later, while the fence is current. Laravel's refusals reach the model as the engine's own messages, never Laravel's: `RUN_NOT_ACTIVE` as the run having ended, `RECONNECT_NEEDED` as "The connection expired. Reconnect it in Minerva.", anything else as "This connection is not available to the agent right now. Try again."
- A provider's rejection is reported with `reportUnauthorized` and the lease's generation (Permissions, Tokens).

The settings calls Laravel makes (`describeAccount`, `listResources`, `checkGrantEdit`) carry their credential in the command, used for that call only and never stored or logged (`internal/connections.ts`).

### Facts

The engine tells Laravel what a run did through an outbox of facts per conversation (`facts`, written by `conversation/store.ts`, delivered by `conversation/delivery.ts`): `run.status`, `run.tool_call` (the call as the chat shows it, with its arguments cut to 2,000 characters), `run.local_tool`, `run.write` (each settlement, those after a cancel included), `run.usage` or `run.unmetered` per counted model call, the terminal `run.finished` with the final message, the run's folder version and changes, its end's code and the conversation's stored bytes, and `run.settled` with the run's totals and its charge. Deltas are not facts: they are run events (Events and the stream).

- **Usage.** Every counted model call gets exactly one settlement fact, written with its record's settlement (Attempts and recovery). `run.usage` carries the provider's report (input with cache reads and writes, cache reads and cache writes apart, output, reasoning), the route (`provider`, `model`) and `requestBytes`, the UTF-8 length of the last request body it built, absent when it built none. `run.unmetered` carries its cause: `refused` at zero tokens, not estimated, or `no_usage`, `stopped`, `failed` or `lost` at the call's reservation, estimated. Both carry the call's charge, `costMicros` (0 for a refused call), with `prices`, the version of the price table that priced it (Budgets); a call on a route the table has no price for (only in the test build) carries neither.
- **`run.settled` ends a run's usage.** It is written once, after `run.finished` and every settlement fact of its run, so its sequence is above theirs: the calls (refused and unmetered counted apart), reported tokens apart from estimated ones, the containers and their time, and the scripts and their wall time, each with whether it is estimated. `run.finished` still lets the next turn start, so the transcript never waits on accounting, and a call the end cut may still settle after it; `run.settled` is the barrier. It usually follows `run.finished` within seconds (about 5 s after a cancel, while the cut call settles), but can trail it by more than a minute when the seal waits behind a sandbox start or destroy in flight (80 s on the test instance after memory resets). A run an older version started (`metered` unset) gets none.
- **Money on `run.settled`.** When every call and script of the run was charged, `run.settled` carries `modelMicros`, `scriptMicros` (the sums of their charges), `containerMicros` (its container time, charged once from the spans), `chargedMicros` (the three added) and `prices` (the version that priced the container time; a run's calls and scripts can name others); otherwise none of the five. Laravel adds a run's spend only from it.
- **The end's code.** `run.finished` carries `code`, why the run ended (`budget_reached`, `folder_limit`, …), empty when it completed.
- **Stored bytes.** `run.finished` carries `storedBytes`, what the conversation's folder keeps once the run has ended (Files), read in its transaction; absent when the sum threw, so a run always ends. Laravel keeps the latest per conversation and sums it per organization for its storage limit.
- **Written with what they describe.** Each fact is written in the transaction of the change it describes, outside pi's transactions, with a dense sequence per conversation. Its JSON is fixed when it is written, so a repeat is byte for byte the first delivery.
- **Delivered in order.** A Lifecycle job sends the facts after Laravel's last acknowledgement with `deliverFacts`, in batches of at most 500 facts and 4 MiB, each after raising the recovery index's `fact_seq` to the batch's last sequence. Laravel applies a batch whole and acknowledges it; the engine checks the acknowledgement against what it sent and wrote. A `FACT_GAP` sends again from Laravel's watermark (Laravel was restored); a `FACT_CONFLICT` stops delivery for the operator and retries hourly; any other failure backs off, doubling from two seconds to at most five minutes.
- **The backlog bound.** A start is refused `FACTS_BACKLOG` while more than 10,000 facts are written and not acknowledged.
- **Replay.** `replayFacts` pages through a conversation's facts after a sequence, up to 4 MiB a page, for Laravel's recovery, and raises the index before it answers, as a delivery does.
- **Retention** (`conversation/retention.ts`). A fact is deleted 7 days after Laravel acknowledged it, never before, however old: each acknowledgement the delivery stores is marked with its time (`fact_acknowledgements`), and the cut is the highest mark at least 7 days old, never above what Laravel holds. A restore of Laravel to a point under 7 days old therefore finds every fact it lacks still held. The lowest sequence still held is the floor (`fact_delivery.floor`), raised in the transaction that deletes the facts below it; it never falls. A `replayFacts` from below `floor − 1` is refused `FACTS_PRUNED` (410) with `data: {floor}`, rather than answered with a page that starts later. A `FACT_GAP` below `floor − 1` leaves the acknowledgement as it was, drops the marks above Laravel's watermark (so the facts it lacks that are still held stay), and stops the delivery for the operator, retried hourly as a conflict is, since sending from the floor would skip what Laravel lost in silence. The deletion is the Lifecycle job `retain`: due 7 days after an acknowledgement and 30 days after a run's end (moved only earlier, and made again from the data when the object starts), it runs passes of steps of at most 500 rows, each one transaction outside pi's, ends a pass after 250 ms and comes back at once (the object's clock stands still through SQL, and a timer moves it only by its own delay, so the pass syncs the storage after each step, which moves the clock to the time the steps took), does nothing while a run is active or a start is prepared (it comes back in an hour), and never throws: a failure is logged and retried after 30 s, doubling to an hour.

### Checkpoints

A turn's folder is saved at quiet moments, driven by the Conversation DO, so no result pi records describes files the store lacks:

1. close admission to new local calls; 2. wait for running ones; 3. `cgroup.kill` the agent cgroup and verify it is empty; 4. scan the folder as the dropped user; 5. stream changed files from the container into R2 (the Sandbox DO writes R2 itself, so file contents never cross an RPC, which is limited to 32 MiB) and verify each hash; 6. record the checkpoint for the current attempt on top of its previous one; 7. release the held tool results to pi.

A round of reads needs no checkpoint. If any step fails, the Conversation DO calls `ctx.abort()` before releasing results, so pi never commits them: the attempt ends, recovery starts the next one from pi's last commit, the held calls come back as interrupted, and the container is replaced from the last checkpoint. A failed checkpoint ends the attempt without recording the result.

The run keeps only its last checkpoint, which becomes the conversation's next version when the run ends, however it ends; the run records what the turn added, changed and deleted, and what the scan could not keep (symbolic links, special files, unreadable entries, names too long or deep). A folder over its size or entry limit is not saved in part: the turn fails and says which limit it hit.

The versions in R2 stay the folder's record. A cold start may restore the conversation's snapshot of the version it starts from instead of downloading it (The sandbox lifecycle, Retiring and snapshots), but the run uses that folder only once a scan that hashed every file found exactly the version's manifest; any other outcome replaces the container from the image and hydrates from R2 within the same attempt.

### The sandbox lifecycle

A Sandbox DO per conversation runs one container at a time, kept between the conversation's turns for a few minutes (Parking, below): `durable_object` scheduling policy, instance `standard-1` (1 vCPU, 4 GiB; `lite` takes about 100 ms per exec and moves 1–4 MB/s), `enableInternet: false`, and no outbound intercepts, so it has no route out (other ports time out; 80 and 443 accept and then reset). Nothing secret is passed to its environment, since a root process can read PID 1's.

Hardening is a state machine recorded with the container's incarnation id: `starting → hardening → verified → in_use → destroying`, between two runs `in_use → parked → verified`, and for a parked container no run took `parked → retiring → destroying`. Before `verified`, while `parked` or `retiring`, and in a container restored from a snapshot until its folder passed its check, no agent command or file operation is admitted. One root `exec` runs, with `set -eu`:

1. a tmpfs `/workspace` with `size` and `nr_inodes` set to the folder limits, owned by uid 1000, so a full folder fails with `ENOSPC` at the size the store counts;
2. a tmpfs `/tmp`, `noexec`, with `/tmp/home` and `/tmp/matplotlib` owned by uid 1000 (bash's `HOME` and `MPLCONFIGDIR`);
3. a cgroup `/sys/fs/cgroup/agent` with `pids.max` (256) and `memory.max` set to the base (1 GiB) plus both tmpfs sizes: pages the agent writes to a tmpfs are charged to its cgroup, so with the base alone a growing folder would OOM-kill commands instead of failing with `ENOSPC` at the folder's limit. Where `/sys/fs/cgroup` is not a root cgroup, as in a local container under Docker (read-only, holding the container's processes), the step first remounts it read-write and moves those processes to a leaf `init`, since cgroup v2 gives children the pids and memory controllers only from a parent with no processes of its own;
4. `mount -o remount,ro /`.

A second `exec` verifies each postcondition (mount options and sizes, `/tmp` not executable, the home directories and their owner, `/` read-only, the cgroup's limits equal to the spec's, that the dropped wrapper reports no capabilities and `NoNewPrivs: 1`). Any failure, or any doubt, destroys the container and fails the turn. A container that stops answering either `exec` (no answer within a minute) says nothing about its hardening: it is destroyed and treated as one that did not start, and a container that did not start is replaced once with a fresh start before the attempt gives up on it (in the minutes after a deploy pushes a new image, a start can wait unplaced or answer nothing). A Sandbox DO that restarts never reuses a running container it did not verify in its current incarnation: it destroys it first. If `destroy()` fails, the DO keeps `cleanup pending` and retries on an alarm. Every operation on the Sandbox DO, `destroy` and cleanup included, names the incarnation (and the run and attempt) it is for, and is refused for any other, so a late cleanup from one attempt can never destroy the next attempt's container.

**Parking.** After a run's last checkpoint the Conversation DO parks its container for the conversation's next run, naming the version that checkpoint made, else the one the run started from, which is what the conversation's folder becomes however the run ends. The Sandbox DO destroys the container instead while any work of the run is in flight, and when the last scan left out more than symbolic links and special files (an unreadable entry, a name too long or too deep, more warnings than it lists), since parking cannot make such a folder the version. Otherwise one root `exec` with `set -eu` kills the agent cgroup until it is empty; fails on a regular file with more than one link, which hydration never makes and the scan cannot see; deletes every entry of `/workspace` that is neither a regular file nor a directory, without following links; sets hydration's modes (directories 0755, files 0755 or 0644 by the owner's execute bit, changed only where they differ, so the scan's index still holds); empties `/tmp`, `/dev/shm` and `/dev/mqueue` (every place uid 1000 can write after the hardening, measured in the image under Docker) and removes System V IPC objects; and makes the home directories again. A failure or no answer destroys the container. Only then is the row written `parked`, with the version and a lease of 5 minutes (owner, 2026-10-19), after which the alarm retires it (below). A parked container belongs to the conversation, not a run: `seal` leaves it, and the Conversation destroys it only when the conversation is deleted or a start replaces it. The next run's preparation asks to `acquire` it first. A container holding another version, or started or hardened otherwise than the run's spec gives (the hardening records the SHA-256 of the class's image name and its argv, which covers the script and every limit), is destroyed; one that passes the verification again gets a new incarnation, the run's fence and lease, and the scan's index. Every fence of the run that parked it is then stale. A restarted object keeps a running parked container, to be verified when acquired. A container parked before a deploy that changed the image is destroyed rather than acquired.

**Retiring and snapshots.** A parked container that no run took retires at its lease. When its folder is slow to hydrate (300 files or 20 MB and up), the retire leaves a snapshot, which the next cold start of that version restores instead of downloading the folder. The folder stays on tmpfs while containers run, and is copied onto the root disk only at the retire, since a snapshot keeps the root disk alone. A folder on a loop-mounted ext4 image, which a snapshot would keep as it is, was rejected: the local dev server's Docker flags cannot loop-mount, every fresh container would change, and the image's free blocks would carry deleted files into the snapshot. The retire is written `retiring` only when the class names an image, the folder has a version, the row's digest is the one the current code would give, and the record does not already hold that version as it would be taken now; anything else is destroyed. Its root `exec` (`set -eu`) kills the agent cgroup until it is empty, stops when the folder is under both thresholds, refuses anything parking does not leave, and writes the folder as one pax archive at `/var/lib/minerva/folder.tar`, root's 0600 in root's 0700 directory, without extended attributes, ACLs, SELinux labels or links between files, then syncs and remounts `/` read-only again. The copy is an archive rather than a tree because the archive keeps each mtime to the nanosecond, whatever the snapshot keeps of a file's own (`docker commit` keeps whole seconds). The archive and the snapshot run outside the serial queue, so a start is never held behind them, and have 3 minutes together. The snapshot is called only after a synchronous check that the retiring generation is still the current one, since the container port is the object's and a call after a start would snapshot the next container; its outcome counts only through the queue while that generation is current, so a start, `forget`, the deletion or a restart that came first means no record and no destroy of a later container. The record (`sandbox_snapshot`, one row) keeps the snapshot's id, the version, the digest, the format (the SHA-256 of the retire's and the seed's scripts and hydration's extraction, so changing any of them makes older snapshots unusable with no version to bump), and when it was taken and last restored. There is no list call, so the record is the only way back to a snapshot. A snapshot nothing records (a crash between it and its record, or a start that replaced its container while it ran) expires on its own.

A start names the version its attempt will hydrate. When the record holds it, with the digest the spec and the current image give, the current format, and taken or last restored under 29 days ago (snapshots expire 30 days after their last restore; an older record is dropped), the container starts from the snapshot (`containerSnapshot`, without `image`), and the row notes it `restoring`. Its hydration runs as one root `exec` that feeds the archive to hydration's own wrapped `tar -x`, so the folder is the agent's with hydration's modes, then scans the folder with every file hashed and an empty index, and requires exactly the plan's files (size, mode, mtime, SHA-256) and directories with no warnings. Only then is `restoring` cleared and the restore time written; a cached folder is never patched. A restore that fails at any step (not ready, the hardening, the verification, the seed, the check, a container lost) destroys the container and drops the record, since one failure is enough to stop trusting a snapshot and costs only the next cold start's restore; a destroy someone asked for leaves the record. The Conversation then prepares from the image, with both of a start's usual tries, and hydrates from R2 in the same attempt, so a bad snapshot costs a turn the failed restore's seconds and never fails it. A restarted object destroys a container that was retiring or restoring and keeps the record. The conversation's deletion destroys its container first, a retiring one too, then `forget`s the record, so a Sandbox still on the previous version, which has no `forget`, never leaves the container running while Laravel retries the deletion.

**Container time.** The Sandbox DO keeps a span per incarnation (`container_spans`), changed only where its state row changes (`writeState`, in the same transaction, by the pure `spanChange`): a new incarnation opens a span at its start with its lease, a lease change moves the span's lease, and the incarnation going away closes the span with the reason its call site gives, `destroyed` when a destroy answered, `gone` when the object found the container stopped (a failed destroy, `recover`, an unusable container), and `parked` when the run parked it. A parked or retiring container has no open span, so the time it waits and retires is charged to no run, and acquiring it opens the next run's span. A destroy that fails keeps the span open until the alarm's destroy answers. `seal(runId)` runs in the lifecycle's serial queue, after any step in flight: it records the run as sealed (`sealed_runs`), after which a start for it is refused as stale ("This run has ended."), destroys the run's container if it is still the current one and no destroy is owed already (the alarm retries an owed one, so a destroy that keeps hanging cannot hold every seal past the settlement job's wait), and answers the run's spans and `spans_since`, since when the object keeps them. `containerCharge` (`sandbox/store.ts`) charges each span from its start to the earlier of its end and its lease plus `HARD_GRACE_MS` (10 minutes, also how long past its lease the alarm lets work still running keep a container), and an open span to that cutoff. The charge is exact for spans ended `destroyed` or `parked`, and estimated when a span is open, `gone` or ended past its cutoff, or when the run was created at or before `spans_since`, since an older version may have started a container that has no span. These are lifecycle durations the object observed, not the platform's billing records.

Every agent command runs through one wrapper: `echo $$ > /sys/fs/cgroup/agent/cgroup.procs || exit 125; exec setpriv --reuid=1000 --regid=1000 --clear-groups --inh-caps=-all --ambient-caps=-all --bounding-set=-all --no-new-privs timeout -k 5 <s> bash -c "$0"`, with the command as an argument, never interpolated. `cgroup.kill` ends leftover processes, `setsid` ones included. A kill first closes the gate to new wrapped processes and waits for those already starting to join the cgroup (or fail), so none joins after it was found empty. Commands run without network, with a timeout of 10 minutes unless the model asks for longer, never past the run's deadline, and with only the tools in the image (`container/`): Python with document, spreadsheet, plotting and data libraries, poppler, ripgrep, jq, sqlite3 and similar.

**File operations run as the dropped user too.** pi's `read`, `write` and `edit` go through `minerva-fs`, a Python helper on the read-only root, run as `python3 -I -S /opt/minerva/minerva-fs …` through the same wrapper: isolated mode, so nothing the agent writes can change it; paths as arguments, never interpolated; bounded reads. Where a path must stay inside `/workspace` (the scan, hydration, checkpoint reads), it is walked one component at a time with `openat`-style calls relative to directory descriptors, each with `O_NOFOLLOW`, so a symlinked parent cannot lead outside; files are opened with `O_NONBLOCK` and accepted only if `fstat` says regular file. pi's own tools keep pi's semantics for paths the agent names, but run without privileges, so a link out of `/workspace` reaches only what uid 1000 may read on a read-only root. Root is used only for hardening, verification, `cgroup.kill`, parking, the retire's archive and feeding that archive to a restore's extraction, which runs as the agent. The SDK's `Files` (which runs as root) is not used on agent-controlled paths.

**When a container starts.** An attempt prepares its container while the model starts (the parked one acquired, else one started, hardened, verified and hydrated from the run's last checkpoint, else its base version; the start restores the conversation's snapshot when it holds that version, and the hydration then seeds and checks the folder instead of downloading it) when a container is parked or the folder it hydrates has files, attachments included. Otherwise its first local call prepares it and waits behind "Preparing files", which on an empty folder is the start, hardening and verification alone, and a turn that makes no local call starts no container.

**The local tools** are pi's own, given an `ExecutionEnv` (`@earendil-works/pi-durable/env`, `FileSystem & Shell`) that forwards to the Sandbox DO; it passes pi's conformance suite (24 cases). `read` is wrapped to be replay-safe. If the Conversation DO restarts mid-turn it loses its `exec` handles: calls in flight come back as interrupted and the container is replaced from the last checkpoint.

### Code mode

When a run has tools, the agent also gets `run_script`: a script that can only call the same tools, for example to make independent reads at once or to filter long results before they reach the model. Each call is an ordinary checked call, recorded and shown as a card; only what the script prints or returns reaches the model. Its description states the runtime's limits: a guest may use about 256 MB (there is no lower setting), computation is cut by `cpuMs` (30 s, or the wall clock when shorter) a few seconds late, timers exist, and `eval` does not.

Each script is a Dynamic Worker loaded with `globalOutbound: null`, no `env` and `limits.cpuMs` by the per-conversation Scripts DO itself, so a CPU-bound script blocks that object, never the conversation. The Conversation DO enforces the wall clock (120 s, cut to the deadline); on timeout, pi's abort or the script's refusals it stops the RpcTarget (later calls get a promise that never settles, so a stopped guest that awaits one stops; past 100 of them more are answered at once, so they cannot fill its memory), lets dispatched writes settle, and the Scripts DO resets itself (`ctx.abort()`) as soon as it hears of the stop, or when its call to the conversation breaks (the conversation is gone). After every script, stopped or not, the conversation resets the Scripts DO with the script's fence, and its next script waits for that reset within its own wall clock, so timers and unawaited work a guest left end and the object's 10 Dynamic Worker slots stay free. The guest's only capability is that RpcTarget, which applies the caps (100 open calls, 256 KB of arguments, stop after 100 refusals, the output limits) and queues calls with the direct ones; a long output or value crosses as its head and the size of the rest, and the conversation cuts the result exactly as pi would (1 MiB, pi's own note). `@cloudflare/codemode` is not used: its replay re-ran an interrupted write (measured), and its executor's timeout can be switched off by the script. Of the two teardown recipes the spikes found, only the reset ends a guest that ignores its stop (measured on the account with the code mode lab, cloudflare/README.md).

### Events and the stream

Events are appended to the Conversation DO's `run_events` with dense per-run sequence numbers; a refused append takes no number. Their types and payloads are the contract's (`contract/`), with values such as `text_delta` and `timed_out`. Text and reasoning deltas come from a tap on the provider stream, flushed every 0.25 s per model call with the call's 8-hex id; the restart marker before a new attempt tells the reader to drop the earlier attempt's text. A conversation's pi conversation is seeded once, by its first run, from Laravel's transcript (final text and file notes only). Later runs continue pi's transcript, whose context leaves out a stopped turn's aborted and refused assistant messages and answers a tool call cut off by the stop as aborted, so partial text never reaches the next turn.

The browser reads a run from Laravel's pages at `GET /stream/v1` with `fetch`, a stream token in `Authorization` and the cursor in `Last-Event-ID`, so no id is in a URL or a log. Laravel signs the token (HS256 with a key of `MINERVA_STREAM_KEYS`) for one run of one conversation of one organization, for at most five minutes. The Worker verifies it (any fault is a 401 that says nothing), checks the conversation's organization in the recovery index, opens a hibernatable WebSocket to the Conversation DO with `after` and the token's organization, and relays frames (`id`, `event`, one-line `data`, 15 s keepalive comments, `end` when the run is inactive and caught up). A conversation the index does not bind to that organization, or marks deleted, is 404. The Worker closes the response hard at the token's expiry, and the browser resumes from its last event with a new token, so a member Laravel removed loses the stream within one token's life. CORS answers Laravel's origin (`MINERVA_LARAVEL_URL`) alone; no cookie is read. The route is off (404) unless the internal API's settings, `MINERVA_LARAVEL_URL` and `MINERVA_STREAM_KEYS` are all set.

The DO sends the backlog and subscribes in one synchronous step, so no event falls between them. Hibernatable sockets outlive the instance that accepted them, and one that died may have committed events it never sent: each socket is tagged with the instance that accepted it, and any other instance never writes to it (no frame, no `end`) but closes it with 1013, as it does every socket it inherited when it starts, so the relay opens a new socket from its last event and gets what it missed, then `end`.

- **A pruned run:** once a run's retention started (30 days after it ended, Attempts and recovery), its events may be partly deleted, so its stream sends `end` at once, whatever the cursor, and sends no event; `event_seq` is kept.
- **Backpressure:** the DO drops a socket whose backlog or buffer passes 4 MiB of frames, and the Worker closes the response when 16 MiB wait unread; either way the client resumes with `Last-Event-ID` and loses nothing.

## The internal API

Laravel's commands are one oRPC contract (`contract/src/internal/`: method, path, input, output and typed errors) served under `/internal/v1/` (`src/internal/mount.ts`), with OpenAPI documents Laravel's client follows; its design is [docs/plans/contract.md](docs/plans/contract.md). A request is refused in this order: without the four internal settings every `/internal/` path is 404; Cloudflare Access checks the service token in front of the Worker, and the Worker checks Access's assertion again (RS256, issuer, audience, the service token's client id) before reading a body (401 that says nothing, 503 when Access's keys cannot be read); the body is capped at 16 MB; each command must name this engine's environment (`WRONG_ENVIRONMENT`); then zod validates the input (422). No cookie authenticates any route, so none has a CSRF check.

- **Commands:** `catalog` (the connectors this engine serves and the price table it charges by), `startRun`, `cancelRun`, `replayFacts`, `describeAccount`, `listResources`, `checkGrantEdit`, `folder`, `resolveDownload`, `deleteConversation` and `listConversations`; `admission` answers 501 `NOT_IMPLEMENTED` and stays unused, since the emergency stop is Laravel's (`minerva:stop` and its admin page). Every command but the catalog, `admission` and `listConversations` names the environment, organization and workspace, and the conversation where it has one; the recovery index refuses a conversation bound to another scope (`SCOPE_MISMATCH`).
- **The engine's requests to Laravel** (`src/laravel/client.ts`): `leaseToken`, `reportUnauthorized` and `deliverFacts`, with the Sanctum token `MINERVA_LARAVEL_TOKEN`, to `MINERVA_LARAVEL_URL`. The client checks Laravel's answers against the contract rather than trusting them.
- **Other routes:** the run stream at `/stream/v1` (above) and the token-gated `/api/probe` for the account tests; every other path outside `/internal/` is 404 `NOT_FOUND`, with the security headers on every answer.

## Files

Each conversation has a folder that the agent works in as on a laptop: pi's ordinary `read`, `write`, `edit` and `bash` tools on a real directory, called in parallel. A turn downloads its starting version into `/workspace`; checkpoints save it back (Checkpoints). Users attach files to a message, download any file of a version, and see each command and its output in the chat.

- **Store.** File contents are blobs in R2 under keys of their own, named by SHA-256 with a random part, so deleting an object never races a re-upload of the same contents. A folder version is an immutable manifest in the Conversation object with a parent and a digest; a conversation points at its current one.
- **Uploads.** The browser puts an attachment to a staging key under `uploads/<ws>/` in the conversation's bucket with a PUT Laravel presigned, its size and type signed; a start measures and copies it into the conversation's blobs, added at the folder's root (numbered when the name is taken) (Starting a run, step 5), and the bucket's lifecycle rule deletes every `uploads/` object a day after it was written.
- **Every object is recorded before it is written**: the Conversation DO records a blob's key (an attachment's copy, a checkpoint's file) before it or the Sandbox DO writes it, and claims it when the start or the checkpoint is recorded. Contents the conversation already stores get no key: the Sandbox DO only hashes the container's bytes (`crypto.DigestStream`), as proof the run has them, and the run is granted the stored blob, so nothing is written or recorded. Alarms delete unclaimed objects older than an hour, so a crash between the record and the write leaves nothing that is not eventually removed.
- **Downloads.** Laravel lists a version with `folder` and asks `resolveDownload` for a file's R2 key, size, hash and sniffed type; Laravel then signs a short-lived GET of that key on R2 for the browser. Laravel never derives a key from a path, and the engine serves no file itself.
- **Files are untrusted.** Attachments and agent files are parsed in the sandbox, never in the Worker (the OneDrive connector's Office reader is an exception). A run reads only blobs from its starting version, its last checkpoint, or its own uploads, and an upload is hashed even if the store has it, so knowing a hash does not reach another conversation's file. Every manifest's paths are validated, and sizes come from the store's own records.
- **Stored bytes.** What a conversation keeps is the sum over its `stored` blobs, each distinct contents once, rounded up to whole 4 KiB pages as the folder's cap counts it: every file of every version it keeps (each turn's result, each base version with attachments), and what a failed clean-up left. Copies in flight and objects waiting for the sweep's deletion are left out. Only a run changes which blobs are stored (its attachments at its start, its checkpoints' uploads, what its end deletes), so the number `run.finished` reports holds until the next run starts; deleting a file in a turn frees nothing, since the earlier version keeps it.
- **Limits** (settings): 256 MB and 10,000 entries per folder (`/workspace` is a tmpfs of that size); uploads by a run up to four times the folder size; 50 MB per attached file and 10 files per message; paths of at most 1,024 bytes and 32 levels.
- **Encryption.** Blobs use R2's own encryption. Per-workspace keys (SSE-C, proven in the spike) are a later step; keys would never appear in a signed URL.
- **Deletion** of a conversation (`deleteConversation`) marks it deleted in the recovery index first, so a start that arrives later is refused, then in its object, which answers any start still prepared, stops its run as `conversation_deleted`, closes its streams, waits until pi's work has ended (Attempts and recovery, Stopping pi) and destroys its scripts and sandbox; the command fails while any of that is left, and Laravel sends it again. A `startRun` or `cancelRun` of a conversation the index has deleted runs the object's deletion again first. Its facts stay for replay, and its folder and blobs until the purge.
- **The purge** (`conversation/retention.ts`). The `retain` job removes a deleted conversation 7 days after its deletion, once no run is active or prepared, every run is settled, no write is still dispatched and Laravel has acknowledged every fact, which the facts' own retention has deleted, so the object also outlives its last acknowledgement by 7 days. In order, each step run again from the first after a failure or a reset: the scripts and the sandbox destroyed again; the recovery index's `purged_at` set (D1 `0014`), from which the Worker answers the conversation's commands from the index alone; the R2 prefix `blobs/<ws>/<conv>/` deleted a page of 1,000 at a time, whether the folder recorded each object or not, within the pass's budget; then `ctx.storage.deleteAll()`, while the alarm still stands, and the SDK's `destroy()`, which deletes the alarm before the storage, so a reset inside it strands no data. The index's row stays for good. Afterwards a `startRun` is refused `CONVERSATION_DELETED`, an accepted start sent again included; a `cancelRun` answers `ended` and a `deleteConversation` `deleted`; a `replayFacts` answers an empty page from the index's `fact_seq`, and `FACTS_PRUNED` with `floor: fact_seq + 1` below it; the folder's reads and the stream are not found. A command that read the index before the mark makes the object again only as a deleted conversation, which purges itself after its own window. A deleted conversation whose facts Laravel never acknowledges is never destroyed, since a fact may be money: each pass that finds it so, a day apart, logs an error.

Unlike a laptop, processes left running are killed at each checkpoint, commands have no network, a crash can lose changes since the last checkpoint, and only regular files and directories are kept. Folders move between R2 and the container per file, which is slow for many small files (500 files, 50 MB: a checkpoint takes about 19 s).

These are production's names; another instance's start with its own name (cloudflare/README.md, Names). An instance's operator files live outside the checkout, in its instance directory (`~/.config/minerva/instances/<name>/`, cloudflare/README.md): `secrets.env` holds the Worker's secrets and `vars.env` a deployed build's plain settings, and neither is ever printed. The secrets are `MINERVA_SECRET_KEY` (the probe's and the fault driver's tokens, the write ids events carry), and, once set, `MINERVA_LARAVEL_TOKEN` (the engine's Sanctum token for Laravel) and `MINERVA_STREAM_KEYS` (the stream tokens' keys, `id:secret` entries shared with Laravel); a deploy uploads only those the build declares. Plain settings (`MINERVA_MODEL_*`, the folder limits, `MINERVA_RUN_TIMEOUT_SECONDS`, `MINERVA_DEBUG`, the internal API's four, `MINERVA_LARAVEL_URL`) are text bindings in `cloudflare.config.ts`, with defaults in `scripts/build-settings.ts`, checked by the Worker's own parser (`src/config.ts`) at build time. Two bindings are not settings: the build sets `MINERVA_MODEL_GATEWAY` to the instance's name, and the deploy sets `MINERVA_MODEL_PRICES` to the route's prices it read from models.dev (Budgets), which a `vars.env` may not hold. Development and tests read them from the environment; a deployed build reads its instance's `vars.env` alone, which must exist, with debug off and `MINERVA_LARAVEL_URL` https when set, so a shell's `MINERVA_*` never reach a deploy. `node scripts/instances.ts prune <name>` drops the names no build reads any more from both files. `pnpm run deploy` checks that D1, both buckets (with their jurisdiction and lifecycle rules) and the AI Gateway exist, since `cf deploy` would create a missing one with default settings, and applies D1's migrations before uploading code.

**Local development without an account** (`pnpm dev:offline` in `cloudflare/`; cloudflare/README.md, Local development). It runs `vite --mode offline`: the test build's entry with the fake model, `MINERVA_DEBUG` on, local D1 and R2 under `cloudflare/.cloudflare/state`, no Workers AI or AI Gateway binding and no remote bindings, and the sandbox container only when Docker runs (otherwise the Sandbox class has none and a tool that needs it says so). Its secrets are `cloudflare/.dev.vars` (`pnpm secrets:offline`, gitignored). The mode exists only for the dev server: `cloudflare.config.ts` refuses it unless `vite.config.ts` has marked a serve (`MINERVA_DEV_OFFLINE`), its names are `minerva-dev…` and its D1 id is a placeholder, so it cannot be built or deployed by accident (a source rule in `sources.test.ts` checks).

**Deploys and resets.** A deploy reads the model's prices from models.dev and stops without them, builds and checks (secrets, that the test build's code is not in production, buckets and their lifecycle rules, the Worker's startup CPU), stops on a Durable Object namespace on the account that the build has no class for, applies D1's migrations, checks the database's schema against them and uploads the Worker. Old and new versions run side by side for a while, so a migration adds, or drops only tables no deployed version reads (0013 dropped the account tables), and Durable Object storage changes stay additive (Spike results, Versions). Code and settings can be rolled back, except below chunk 15a's retention or 19b's one pi conversation per conversation once an instance has run them (cloudflare/README.md, Deploy); a change to the Durable Object classes cannot. Emptying an instance (`scripts/reset.ts`) retires every class so that Cloudflare deletes its objects, empties and recreates the buckets, and recreates D1. Logs are Workers Logs. Production is deployed by hand; it was reset and deployed again on 2026-10-16, when chunk 13c retired the account tables and classes, and deployed on 2026-10-17 at `e850d65` (chunk 15a) and at `e416627` (15c's listing).

## Spike results

Measured on the account on 2026-10-10 (Workers Paid, Frankfurt), with `cf` 1.0.0-beta.13, its `cloudflare.config.ts` format and Vite. Full reports are kept outside the repository.

| Spike | Result |
|---|---|
| PiHarness | Worked with pi-durable 1.1.0 and 1.0.3. Two reads in parallel then a write, from one prompt; idempotent submit; steer and follow-up; recovery after `ctx.abort()`, memory-limit resets (7 in a row, no cap) and an interrupted model stream, each about 30 s later; a redeploy mid-turn interrupted nothing; a 17-minute tool call completed. After an interrupted write, the model retried it under a new call id. First text delta 2–4 s after submit. pi-mcp works; pi-codemode does not (no `worker_threads`). `contextRetentionMs` must be 0, or every object stays active 10 minutes after each turn. |
| Sandbox | A Firecracker microVM (KVM, kernel 6.18). With `enableInternet: false` and no intercepts: ports other than 80/443 time out, 80/443 accept and reset, DNS answers nothing, metadata and other containers are unreachable. Processes have root's capabilities until `setpriv` drops them; tmpfs size and inode limits give `ENOSPC`; `/` can be remounted read-only; a cgroup bounds pids and memory and `cgroup.kill` ends strays. `standard-1`: start 0.3–0.5 s, `exec` 6 ms, 50 MiB out in 1.5 s. A root fork bomb outside the cgroup wedges `exec`. |
| Code mode | Dynamic Workers with `globalOutbound: null` block fetch, connect and WebSockets; `eval` is blocked, so each script is its own Worker (about 12 ms to load). Props on a stub cannot be read or forged. Memory is about 256 MB per guest, with no lower setting; `cpuMs` kills about 2 s late. A busy guest blocks the object that loaded it, and a guest can outlive its host's timeout until that object is reset. `@cloudflare/codemode`'s replay ran an interrupted write twice. |
| Storage and realtime | Request bodies up to exactly 100 MiB, buffered by the edge before the Worker runs. Upload hashing with `tee()` and `DigestStream`: 550 ms CPU per 50 MiB. Downloads from a second Worker keep `CSP: sandbox`; SSE-C with per-workspace keys works. SSE served by a DO keeps it awake; relayed by the Worker from a hibernatable WebSocket, the DO sleeps between events, and neither path dropped a client across deploys. D1: atomic `batch()`, triggers, FTS5, unique-row locks, no `BEGIN`. `fetch()` from a Worker answers private, loopback, link-local and non-Cloudflare IP literals with a 403 (error 1003) rather than throwing (below). |

Consequences for the design:

- **Private addresses.** The Web connector keeps its URL and host policy and its same-host redirect rule; the guard against private networks is the platform's refusal, which the connector recognises (a 403 from `server: cloudflare`, `platformRefusal` in `gateway/http.ts`) and reports as a blocked site. That refusal is measured, not documented, and has adversarial tests (rebinding names, `nip.io`, IPv6 encodings, redirects to private addresses) against the deployed Worker. It comes in two forms. A request with an empty Accept header gets the text `error code: NNNN` (1003 for a private, loopback, link-local or non-Cloudflare IP literal, 1002 for a name that resolves to a private address, 1102 for loopback names such as `localtest.me`). A request with any Accept header, which the Web connector always sends, gets Cloudflare's HTML error page instead (text/html, about 6.5 KB, headed `Error` and the code); the connector reads both.
- **Versions.** Busy objects keep their old code for minutes after a deploy and new objects may start on the previous version, so two versions run side by side: Durable Object storage changes are additive only, code accepts rows written by the previous and the next version, and a changed tool still fails through its fingerprint (`OPERATION_CHANGED`). A deploy usually reaches a busy object only once it is idle (and may reset it, which counts as a restart), so revocation, policy and security fixes can never rely on a deploy reaching running turns.
- The sandbox checks are built for this platform (network checks over HTTP and TLS, not TCP connect) and run against the deployed Worker.
- **JSON keys** (found in Node 24's V8, in workerd 1.20261006.1 and on the deployed Worker): after any JSON text with the key `"\\"` was parsed in an isolate, a later key written with an escape in the same place (`"\n"`, `"\u00e9"`) comes back as `"\\"`. `JSON.parse`, `Response.json()` and Hono's `c.req.json()` are affected, values are not. The state is per isolate, so one tenant's input could change another's parsed keys and the hashes over them; all code parses JSON with `lib/json.ts`'s `parseJson`, and a unit test refuses `JSON.parse` elsewhere in `src/`. A platform test keeps the bug visible in local workerd; on Cloudflare's edge it no longer shows since 2026-10-14 (the deployed probe checks), and `parseJson` stays while the runtimes the tests run in still have it.
- **Dates, text and numbers** follow the runtime and its libraries: `lib/dates.ts` reads RFC 3339 by a strict pattern, checks the calendar fields, reads an offsetless time as UTC (never in the runtime's zone) and checks IANA zone names with `Intl.DateTimeFormat`; Slack's `ts` stays an exact decimal string, converted through BigInt; tool inputs are strict zod objects and provider answers zod schemas, with no coercion (`z.coerce` is refused by a source rule). Identifiers are never normalized with NFKC or NFKD, which join text that should stay apart (NFKC only to refuse or redact, NFC only for file names and manifest paths; `sources.test.ts` checks), and decimal amounts stay their text (`xero/decimal.ts`, `stripe/money.ts`), never floats.

## Open questions

1. Move the executor to a separate Worker script with its own secrets, so the loop's isolate never holds a credential? (The product plan's leases narrow what the engine holds, but not where.)
2. ~~Warm containers: keep a conversation's container between turns, or start one per turn?~~ Answered 2026-10-19 (chunk 20): a completed turn parks its container for 5 minutes, and the conversation's next turn takes it (The sandbox lifecycle, Parking).
3. pi's state grows with the conversation. Since chunk 19b one pi conversation holds the whole conversation, every entry kept, compacted ones and tool results (up to 1 MiB each) included, until the conversation is deleted (Attempts and recovery). Its size against a Durable Object's 10 GB is not measured. A pi session of a run from before is about 64 kB and 75 rows once the history reaches its cap (measured), and retention deletes it 30 days after its run ended, with statements over pi-durable 1.3.0's schema that each pi-durable upgrade must be checked against.
4. ~~A team's Workspace DO serializes its control plane.~~ Moot: Laravel holds the control plane.
5. Retention, narrowed: a run's events, ledger and page tokens go 30 days after its end, facts 7 days after their acknowledgement, and the conversation's pi conversation only with the conversation (owner, 2026-10-19). Left open: version manifests and the Sandbox object's per-run rows, which only the conversation's deletion removes, and whether a very long turn approaches the 10,000 subrequests of one invocation.
6. ~~Email Sending is in beta and limited to 1,000 messages a day.~~ Moot: Laravel sends the mail.
7. Compliance scope: Containers, Dynamic Workers and Secrets Store are missing from Cloudflare's published SOC 2 and HIPAA lists.
8. ~~Residency of an EU workspace beyond its Durable Objects and bucket.~~ Answered 2026-10-17 in [docs/data-processing.md](docs/data-processing.md): only the Durable Objects and the EU bucket are EU by guarantee. 9. ~~Queries across objects.~~ Answered by the product plan: queries across conversations and workspaces run on Laravel's database, which holds the transcripts and usage built from the engine's facts, the audit log (chunk 15b) and search (chunk 18).
